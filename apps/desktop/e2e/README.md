# Desktop e2e

The app's end-to-end tests, against the fake Slack server. Fixtures and the options a file can `test.use` are in `fixtures.ts`, `launchApp` is in `launch.ts`, and the page objects are in `driver/`. Setup, commands and the remote runner are in `docs/development.md`.

## Browser lane

Most specs run in the `browser` Playwright project: the real renderer in Chromium's headless shell, against the engine and agent in a Node host, with no Electron. The `electron` project runs what needs main or the OS. `e2e/lanes.ts` lists the files that run in the browser; every other file runs in Electron.

- **Commands.** `bun run test:browser` and `bun run test:electron` run one project; `bun run test:desktop` runs both. `bun run affected` routes its selected files through both projects, and `bun run verify:main` records separate browser and Electron steps. `JUNO_BROWSER_WORKERS` sets the browser project's workers (default one per allocated remote thread, `JUNO_RUNNER_JOB_CORES`; otherwise one per two local threads), `JUNO_E2E_WORKERS` the electron project's (default 1). Neither desktop lane retries, and no project records a trace; rerun a failure with `JUNO_E2E_TRACE=1` to keep a trace of each failing test. Each project writes `test-results/<project>/`, and a step of a `test:plan` run `test-results/step-<n>/<project>/`, so one step does not empty another's.
- **CPU per test.** `JUNO_E2E_TIMINGS=1 JUNO_E2E_CPU=1` adds `cpu-<kind>` phases to each test's timing line: the CPU milliseconds the Playwright worker (the test and its fake Slack), the host, the browser and its renderer, or Electron and its processes burned during the test (`e2e/cpu.ts`). `node scripts/e2e-timings.mjs <run.log>` sums them.
- **What a test gets.** Each worker owns a browser context and a pool of loaded Node hosts (`browser/host.ts`). Each test gets a new page, fake Slack, data folder, engine, agent and shell services. After a test, the page leaves its document, all origin storage and cookies are cleared, permissions and network state are reset, and the page closes. The context keeps only its immutable HTTP asset cache. Files that install Playwright’s clock set `test.use({ freshContext: true })`: the clock changes the whole context, so these tests discard it. The page’s clock also runs the engine socket’s 5 s pings and 10 s open timeout, so a step of more than a few seconds can drop and redial the socket, and a command sent while it is down fails. A flow that needs a write at the end of a long step runs the last seconds in real time after `expectEngineLive` (`home.spec.ts`, the visit). The host stops the engine, agent and sockets before returning to the pool; failed cleanup discards it. Its listening port stays warm so the next test can use cached hashed assets. Dynamic files and HTML are never cached. Coverage uses a process per test to keep function offsets separate. `browser-isolation.spec.ts` checks fresh sign-in, settings and browser storage on reuse.
- **Host services.** The host runs the engine and main’s Notifier, dock-badge rules, activity watch and huddle-page registry on the test's data folder with the e2e scheduling profile. Memory OS boundaries record notifications and dock actions. The page’s shell socket uses the existing input schemas, including staging-failure logs and notification settings. The host keeps main's part of the session in `web-session.json`, and serves the built renderer (`dist/`, from `vite.web.config.ts`), the `/__juno/` files and the engine socket on an OS-assigned port. The fake stays in the Playwright worker so specs control it directly.
- **Agent.** `agentOptions` starts the real `startAgent` beside the engine. The host uses main’s provider store, memory keychain and credential stores, Codex home checks, model picker and backup configuration. `/__juno/agent` carries the same worker messages as Electron’s renderer port. The QuickJS worker and wasm ship in `dist/host`; `codemode.spec.ts` runs in both lanes. Provider changes start or stop the agent, and a restore restarts it on the restored database. The shared-folder backup and restore flow runs in both lanes; the browser supplies folder selections at the shell boundary. Electron keeps what main does for the agent's processes: port brokering after the engine and then the agent are killed, and three utility-process crash points (durable inbox replay, an outward write before its receipt, a database swap during restore). The full crash matrix stays in agent package tests.
- **Agent flows.** Each juno-agent spec is a few user flows, not one test per check: chat, panel, states (a run, steering, failures), cards, writes, memory, schedules, connections and auto-review, T3 Code, backup and transfer. A behaviour the agent package's flow tests already check (`packages/agent/test`) is not repeated here unless the UI adds something; add a step to the flow it belongs to rather than a new test.
- **One driver.** `Juno` reaches what the page does not show through an `AppSurface` (`driver/surface.ts`): main's `junoTest` hooks on Electron, and on the web the page's test seam (`web/page/testSeam.ts`) and the host. The seam answers context menus as main's does, with the same `chooseNextMenuItem` and label format, records links, and takes app-menu commands. Specs use `juno.surface`, `juno.setWindowSize` and `relaunch` instead of `app.evaluate`.
- **Relaunch.** The `relaunch()` fixture quits and opens the app again on the same data folder and returns the new driver; `relaunch({ whileClosed })` runs a step in between, for a test that edits `user.db` or `agent.sqlite` as the next launch finds it. The browser project leaves the page, stops the host’s agent and engine, starts them again and loads the page; localStorage keeps the launch preferences as launch.json does. What main alone keeps (launch.json itself, the window) is tested in Electron.
- **`juno://` addresses.** The page loads them from `/__juno/` on its own origin. Use `schemeSrc('files')` and `schemeUrl('files')` from the driver in selectors and assertions.
- **Electron tests in a browser file.** Tag a test `@electron` and only the electron project runs it; `@canary` runs in both. A test that reads `app` in the browser project fails with a pointer to the tag. Native zoom, window swipes, CSP and protocol-handler checks stay in Electron. Browser contexts keep native scrollbars visible so real thumb drags work; a device scale factor alone does not exercise Electron zoom.

Eight canaries run in both lanes: pasted-image upload, sending a reply, navigation history, notifications, a Home agent question, provider setup, codemode and shared-folder backup/restore. Electron otherwise covers native sessions/keychain, CSP/protocols, windows/menus, PDF and HTML frame keys, Quick Look and image clipboard, web panels, privacy/screen sharing, updates, crash supervision and the portable idle smoke flows. Manual screenshot tools are discovered only with `JUNO_SCREENS=1`; Mac performance specs use `bun run perf` and are excluded from this project. Renderer file viewing, image peeks, privacy and shell styling run in the browser; damaged-cache recovery is an engine flow (`packages/engine/test/flows/gap-and-restart.flow.test.ts`). Diagnostics owns the process table and content-free report; the live-update restart flow owns engine port recovery. The obsolete raw provider RPC and duplicate hello/crash specs were deleted; provider UI flows now cover model selection, custom endpoints and removal.

Coverage is off by default. `JUNO_COVERAGE=1` records renderer and host function offsets and maps the browser and Electron builds to source files. Plan steps preserve separate partial maps. The JSON reporter always records per-test durations; traces require `JUNO_E2E_TRACE=1`.

The former Resolve spec is part of the approval/double-click/restart flow in `juno-agent/break-pass.spec.ts`. The same flow covers AI-off with a pending card; Budget behaviour lives in `cards.spec.ts`. Disabled schedule-notification and T3 sparkle cases were removed from the executable suite: agent notification delivery is not implemented. They remain product gaps, not passing coverage.

## Scheduling and setup timings

Ordinary fake-Slack launches use the engine unit harness's 1:20 scheduling scale and disable periodic discovery in favour of explicit catch-ups. Dependency polling, socket pings, and hello and pong deadlines keep their production values because Electron and the fake run in separate real processes. The engine host accepts it only with both e2e mode and a fake Slack URL; a normal launch keeps production defaults. `test.use({ timing: 'production' })` or `launchApp(dir, { timing: 'production' })` keeps real timing for a test of a window itself; no spec uses it now (the reaction-versus-edit-backoff check runs in `outbox-actions.flow.test.ts` on a test clock). Staying active while at the Mac runs in `apps/desktop/test/activity.test.ts`, main's activity watch on a fake idle time against the engine; socket spacing is covered in the Slack package. Paced sync launches, `perf.spec.ts`, `idle-cpu.spec.ts`, feel scenarios and tests tagged `@mac` keep production timing automatically.

For a negative AI or Automated assertion, `await juno.workPass('title')` (also `art`, `home` or `automated`) requests a pass through the job's existing serial consumer. The engine acknowledges only a pass started after that request, including a pass that chooses not to call the model. It fails after 10 seconds instead of accepting an unfinished pass. AI jobs still need `aiJobs: true`.

`bun run remote --env JUNO_E2E_TIMINGS=1 test:desktop <specs>` prints separate fake-start, Electron-launch, sign-in, sync-wait and close durations in milliseconds. These are setup observations, not the Mac performance budgets. Related checks with the same starting state share one launch with labelled `test.step` calls. Each flow owns its fake and user-data directory; cold starts, different fixtures and failure scenarios remain separate. Timing budgets live in `*.perf.spec.ts` and run through `bun run perf` on the Mac. The `@heavy-idle` portable resource smoke check uses short real CPU and memory windows; app diagnostics remain the primary way to find field spins.

## Synced start

Most tests begin signed in to the default seed with the first sync done. `test.use({ synced: true })` in a file, or `syncedTest` from `fixtures.ts` for single tests in a file whose other tests sign in themselves, starts the app that way without signing in. The test body then starts where `juno.signIn()` and `juno.waitForSync()` used to leave it.

- **Browser project:** one snapshot per run for each set of engine options (`browser/snapshot.ts`), made by the first worker that needs it while the others wait on a lock, and kept for five minutes. A fake made to match it uses the seed's time and sessions on a port of its own: the host maps the snapshot's fake origin, which its stored avatar and file addresses name, to the test's fake (`aliases` in `web/host/fakeMain.ts`), and the state guard compares the fakes with that origin taken out. The copy is an APFS clone on the Mac.
- **How (Electron):** each worker signs in once to a fresh default seed, waits for the sync, quits, and keeps that user-data directory (`synced.ts`). Each synced test gets a copy and a fake made to match it: the same seed run at the same seed time (`seedTime`), on the same port (the seed's avatar and file URLs name it), accepting the same sessions. The app then boots warm, as after a relaunch, and the fixture waits for `waitForSync()`.
- **Never stale:** the key includes `out/.inputs-hash`, which `build-cached` verifies before Playwright starts. That fingerprint covers source inputs, including the fake seed, store schemas/migrations, engine/sync code, dependency lockfile, toolchain and built output bytes. Copies live only in their worker, and are rebuilt after five minutes. A copy kept between runs would save one sign-in per worker (2–3 s) and could go stale, so none is kept. The effective timing profile and `fakeAiDelayMillis` are also in the key. AI jobs cannot use a snapshot.
- **Guard:** before and after the warm boot, the fixture compares the fake's workspace hash with the state captured after the snapshot app quit. It includes ids, timestamps, mutation markers, read pointers and subscriptions. Only the clock and self presence are omitted; presence follows the current time at session start. The fake must have no sockets before launch and exactly one after sync. A mismatch fails setup. Socket URLs and reconnect state are process-local, so a new fake and engine start a new socket session; no old connection is reused.
- **Real sign-in stays** for tests whose subject is sign-in, the first sync, quick start, sync convergence or boot: `session`, `layout-shift`, `app`, `engine`, `realtime`, `cache-update`, `sidebar-first-sync`, the first-sync tests in `break-pass-1017`, tests that change the fake before signing in, perf, idle and feel. They keep the default, `synced: false`. Established Juno Agent flows use `synced: true` and `readySynced`; provider setup, custom seeds, backup transfer and first-sign-in flows keep cold starts.
- **Not with AI jobs:** `synced` refuses `aiJobs: true`. The jobs keep writing titles and art after the first sync, so a copy holds results a fresh sign-in has not made yet (`home.spec.ts` read the AI title where it expected the message text). `art`, `automated`, `home` and the follow-up review card sign in.

Each Electron test gets a fresh app process. Browser workers reuse loaded hosts and contexts with the reset described above; engines and pages remain fresh. Both lanes get an isolated user-data directory. The earlier Electron process-reuse experiment and its limits are in [Test speed round 4](../../../docs/test-speed-4.md#worker-app-reuse-experiment).

## Sidebar trace

A sidebar test that fails because a row did not appear, or did not move, needs to say whether the sidebar held its order or was given no new list. The sidebar trace records both.

- **On:** `test.use({ sidebarTrace: true })` in a spec file, or `launchApp(dir, { sidebarTrace: true })`. The sidebar specs (`automated`, `automated-record`, `sidebar`, `sidebar-first-sync`, `sidebar-hold`, `views`, `layout-shift`) have it on. The fixture puts an empty `globalThis.__junoSidebarTrace` on the main window, which turns the recording on (`packages/state/src/sidebarTrace.ts`).
- **Off:** the app records nothing. A change of the hold's inputs costs one property read, and a topic list value another.
- **What it records:**
  - `hold`: the last 60 changes of the order hold's inputs (SPEC 5, "Holding the order"). Each entry names the change (`list entered (pointer true, keyboard false)`, `left`, `sheet opened`, `sheet closed`, `flushed`, `resumed`, `released a topic`) and the state at that moment: `engaged`, `paused`, `sheets` (open sheets) and `released` (topics shown at once while held). `list entered` and `list left` come from the list itself, before the hold takes them in; the entry after says what changed. The list holds while `engaged || sheets > 0`, unless `paused`.
  - `list`: how many topic list values the sidebar was given (`values`), how many said the engine's run failed (`errors`), and the last of each (`seq`, row count, filter, error).
- **When a test fails:** the `running` fixture attaches the trace as `sidebar-trace` and prints it on one line, `sidebar trace (<test>): {...}`, so a remote run's `run.log` has it.

Reading it: a row that never appeared with the hold still on (`engaged` or `sheets > 0` and not `paused` in the last entry) points at the hold. A `list.last` older than the change the test made, or a rising `errors`, points at the engine's `topics.list`.

## Send trace

A test that sends from Home and then misses the message in a tab needs to say where the message got to. The send trace records the send's path through the renderer.

- **On:** `test.use({ sendTrace: true })` in a spec file, or `launchApp(dir, { sendTrace: true })`. `break-pass-1017` and `home-send-tab` have it on. The fixture puts an empty `globalThis.__junoSendTrace` on the main window, which turns the recording on (`packages/state/src/sendTrace.ts`).
- **Off:** the app records nothing. Each traced point costs one property read.
- **What it records**, the last 120 entries, each with `at` (`Date.now()`), ids, states and counts, never message text:
  - `send asked` and `send answered`: the send command (`sendMessage` in `@juno/state`), its target, the first 8 characters of its `clientMsgId`, and the topic it answered with.
  - `background`, `background opened` and `background window`: Home's open of the topic behind it (`openTopicInBackground`), with `reused` when a tab already showed it.
  - `switch`, `tabs asked`, `tabs applied` and `tabs dropped`: a tab change the navigation was asked for, with its ticket, the one it applied (the active tab after it), and one a newer change replaced.
  - `tab mounted` and `tab unmounted`: a tab's topic view.
  - `window`: each new message window a topic view got (`view` is `<topic>@<tab>`): its `seq`, row count, newest row, the spec, and in `sent` each of the last rows sent from this app as `<clientMsgId>:<sending|failed|stored>:<ts or pending>`.
- **When a test fails:** the `running` fixture adds the fake's `chat.postMessage`, `conversations.open`, `chat.update` and `chat.delete` calls (`posts`: time, method, channel, answer) and attaches the whole as `send-trace`, and prints it on one line, `send trace (<test>): {...}`, so a remote run's `run.log` has it.

Reading it: no `posts` entry for the channel means the send never left the engine. A `window` for the tab's view whose `sent` stays at `pending` while `posts` shows an answer points at the engine's reconcile. No `window` for the tab's view after the send means its subscription did not run again. A `tabs dropped` or no `tabs applied` with the tab active after `switch` means the tab never showed.

## Relaunch frames

The relaunch check in `session.spec.ts` attaches `relaunch-frames` JSON before its assertions. It records the total frames, sidebar and sign-in counts, and each frame without a sidebar. Each missing frame includes its index, time since navigation, root child count, whether an earlier sample had the sidebar, and whether the bundle and shell-paint marks exist. `hadShell: false` with an empty root identifies a gap before the first shell. `hadShell: true` identifies a later disappearance. The test still requires the sidebar in every sampled frame and no sign-in frame.

Check the failing run's commit before diagnosing a new startup regression. Worktrees created before `fd8ae4f7` can still run the old delayed initial render after that fix lands on main.

## Heavy tests

A test that is slow because of what it checks, and whose code rarely changes, is tagged `@heavy` and its area's tag: `test('...', { tag: ['@heavy', '@heavy-sync'] }, async () => ...)`. `HEAVY_AREAS` in `scripts/test-areas.mjs` lists the areas and the files each covers; add a file there when a heavy test starts to cover it. `bun run affected` skips an area's heavy tests unless the change is in that area, by setting `JUNO_SKIP_TAGS`; a full run (`bun run verify:main`) and a run by hand keep them. See `docs/development.md`, "Affected tests".

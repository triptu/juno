# Desktop e2e

The app's end-to-end tests, against the fake Slack server. Fixtures and the options a file can `test.use` are in `fixtures.ts`, `launchApp` is in `launch.ts`, and the page objects are in `driver/`. Setup, commands and the remote runner are in `docs/development.md`.

## Which lane

| A test that checks | Goes in | Runner |
| --- | --- | --- |
| A protocol, merge, parser or state machine rule | a unit test in its package | `bun run test` |
| Engine or agent behaviour with no UI (sync, read state, the outbox, Home's rules) | `packages/engine/test/flows/`, `packages/agent/test/` | `bun run test` |
| What the app shows and sends after a user's steps: send, edit, fail and retry, unread and read state, filters, tabs, search, the palette, menus through the seam, Settings forms, the agent's chat and cards, Home | the DOM lane, `apps/desktop/dom/` ([README](../dom/README.md)) | `bun run test:dom` |
| Layout, scroll, virtual lists past their overscan, shift, drag, pointer coordinates, paint, the CSS cascade, images | the browser lane (below) | `bun run test:browser` |
| Main, windows, native menus, protocols, keychain, packaging | the Electron lane | `bun run test:electron` |
| One component's look and states | the gallery | `bun run test:gallery` |

A DOM test costs about a third of a browser test's CPU. When a browser test's flow moves to the DOM lane, delete the browser test in the same change; a check in it that needs layout moves to the gallery or to the browser test it belongs with.

A browser test is there only for layout, scroll, focus or paint, and guards something a user would notice breaking or a bug that happened. Tests that start the same way are one journey with labelled steps: an empty browser test costs about 1.45 CPU-s before its body, so a new check joins the journey with its start rather than adding a test. Checks of copy, labels and counts, and repeats of an engine flow test, do not belong here.

## Browser lane

Most specs run in the `browser` Playwright project: the real renderer in Chromium's headless shell, against the engine and agent in a Node host, with no Electron. The `electron` project runs what needs main or the OS. `e2e/lanes.ts` lists the files that run in the browser; every other file runs in Electron.

- **Commands.** `bun run test:browser` and `bun run test:electron` run one project; `bun run test:desktop` runs both. `bun run affected` routes its selected files through both projects, and `bun run verify:main` records separate browser and Electron steps. `JUNO_BROWSER_WORKERS` sets the browser project's workers (default five per eight allocated remote threads, `JUNO_RUNNER_JOB_CORES`; otherwise five per sixteen local threads). On a four-core job (eight threads, one run each) eight workers took 96 s and 525 CPU-s, five 85 s and 472, four 99 s and 419: hyperthreads share a core, so a worker per thread costs CPU and gains no time, `JUNO_E2E_WORKERS` the electron project's (default 1). Neither desktop lane retries, and no project records a trace; rerun a failure with `JUNO_E2E_TRACE=1` to keep a trace of each failing test. Each project writes `test-results/<project>/`, and a step of a `test:plan` run `test-results/step-<n>/<project>/`, so one step does not empty another's.
- **CPU per test.** `JUNO_E2E_TIMINGS=1 JUNO_E2E_CPU=1` adds `cpu-<kind>` phases to each test's timing line: the CPU milliseconds the Playwright worker (the test and its fake Slack), the host, the browser and its renderer, or Electron and its processes burned during the test, as each process stood before the app closed (`e2e/cpu.ts`). `cpu-all` is the whole test, close included, and `cpu-launch`, `cpu-sync`, `cpu-close` and `cpu-synced-build` its phases. With several workers these count the worker's process tree, which loses Chromium's helpers and the utility processes that outlive main as an app quits; with `JUNO_E2E_WORKERS=1` on Linux they read the job's cgroup and count everything. Compare changes with one-worker runs: eight workers on four physical cores burn about 60% more CPU for the same tests than one worker does. `bun scripts/e2e-timings.mjs <run.log>` sums them. With a synced start, `cpu-ready-<kind>` phases count the part before the test's first step. `JUNO_E2E_RPROF=1` adds one `e2e rprof:` line per browser test (`browser/rprof.ts`): the renderer's main-thread JS profile grouped into the app bundle, Playwright's injected script with `evaluate` calls, and native work, split at the synced start's `ready` mark. The profiler adds about 15% to a test's CPU, so compare profiled runs only with profiled runs.
- **What a test gets.** Each worker owns a browser context and a pool of loaded Node hosts (`browser/host.ts`). Each test gets a new page, fake Slack, data folder, engine, agent and shell services. After a test, the page leaves its document, all origin storage and cookies are cleared, permissions and network state are reset, and the page closes. The context keeps only its immutable HTTP asset cache. Files that install Playwright’s clock set `test.use({ freshContext: true })`: the clock changes the whole context, so these tests discard it. The page’s clock also runs the engine socket’s 5 s pings and 10 s open timeout, so a step of more than a few seconds can drop and redial the socket, and a command sent while it is down fails. A flow that needs a write at the end of a long step runs the last seconds in real time after `expectEngineLive`. The host stops the engine, agent and sockets before returning to the pool; failed cleanup discards it. Its listening port stays warm so the next test can use cached hashed assets. Dynamic files and HTML are never cached. Coverage uses a process per test to keep function offsets separate.
- **Host services.** The host runs the engine and main’s Notifier, dock-badge rules, activity watch and huddle-page registry on the test's data folder with the e2e scheduling profile. Memory OS boundaries record notifications and dock actions. The page’s shell socket uses the existing input schemas, including staging-failure logs and notification settings. The host keeps main's part of the session in `web-session.json`, and serves the built renderer (`dist/`, from `vite.web.config.ts`), the `/__juno/` files and the engine socket on an OS-assigned port. The fake stays in the Playwright worker so specs control it directly.
- **Agent.** `agentOptions` starts the real `startAgent` beside the engine. The host uses main’s provider store, memory keychain and credential stores, Codex home checks, model picker and backup configuration. `/__juno/agent` carries the same worker messages as Electron’s renderer port. The QuickJS worker and wasm ship in `dist/host`; `codemode.spec.ts` runs in Electron, against the built worker. Provider changes start or stop the agent, and a restore restarts it on the restored database. The shared-folder backup and restore flow runs in both lanes; the browser supplies folder selections at the shell boundary. Electron keeps what main does for the agent's processes: port brokering after the engine and then the agent are killed, and three utility-process crash points (durable inbox replay, an outward write before its receipt, a database swap during restore). Only the outward write runs on every run, as the crash canary; the others are nightly tests (below). The full crash matrix stays in agent package tests.
- **Agent flows.** The agent's flows (chat, panel, states, cards, writes, memory, schedules, connections and auto-review, search, backup and transfer) run in the DOM lane (`dom/juno-agent/`). T3 Code stays here until its sign-in works on a reused DOM host (`docs/backlog.md`). The rest that stays needs the browser and is one journey in `panel.spec.ts` (the Home question's picks and field position, a read the IntersectionObserver decides, the panel's widths, first frame, emoji list and bottom, a selection the open panel follows), plus the badges and caret lines in `chat-reactions`, images (their thumbnails are sized from the decoded picture) and source-link scrolling. Each spec is a few user flows, not one test per check. A behaviour the agent package's flow tests already check (`packages/agent/test`) is not repeated here unless the UI adds something; add a step to the flow it belongs to rather than a new test.
- **One driver.** `Juno` reaches what the page does not show through an `AppSurface` (`driver/surface.ts`): main's `junoTest` hooks on Electron, and on the web the page's test seam (`web/page/testSeam.ts`) and the host. The seam answers context menus as main's does, with the same `chooseNextMenuItem` and label format, records links, and takes app-menu commands. Specs use `juno.surface`, `juno.setWindowSize` and `relaunch` instead of `app.evaluate`.
- **Finding elements.** The driver and the shared helpers find elements by attribute, tag or visible text (`[data-topic-row]`, `button[aria-label="…"]`, `locator('button', { hasText })`), never by `getByRole`, `getByLabel` or accessible name. A role or name query makes Playwright's injected script walk the page and compute names on every `expect` poll; it was about a fifth of the renderer's CPU. Tests do not check roles or accessible names (Tushar: accessibility checks can go, especially slow ones); they check the text the user reads and the state attributes the app's behaviour uses (`aria-selected`, `aria-current`, `aria-busy`, `aria-pressed`). New specs follow the same rule. The DOM lane keeps its role queries (`dom/find.ts`): checking roles and computing names is about 1% of its CPU, and the tree walk any query needs is the rest.
- **Relaunch.** The `relaunch()` fixture quits and opens the app again on the same data folder and returns the new driver; `relaunch({ whileClosed })` runs a step in between, for a test that edits `user.db` or `agent.sqlite` as the next launch finds it. The browser project leaves the page, stops the host’s agent and engine, starts them again and loads the page; localStorage keeps the launch preferences as launch.json does. What main alone keeps (launch.json itself, the window) is tested in Electron.
- **`juno://` addresses.** The page loads them from `/__juno/` on its own origin. Use `schemeSrc('files')` and `schemeUrl('files')` from the driver in selectors and assertions.
- **Electron tests in a browser file.** Tag a test `@electron` and only the electron project runs it; `@canary` runs in both. A test that reads `app` in the browser project fails with a pointer to the tag. Native zoom, window swipes, CSP and protocol-handler checks stay in Electron. Browser contexts keep native scrollbars visible so real thumb drags work; a device scale factor alone does not exercise Electron zoom.

One canary runs in both lanes, with a native part the browser fakes: pasted-image upload (the image clipboard). Settings' notification permission line and test notification run only in Electron (`notifications.spec.ts`); what that flow saves in the engine is in its flow tests, and the dock dot's rules are in `packages/engine/test/flows/notifications.flow.test.ts`. Shared-folder backup/restore runs in Electron (`juno-agent/backup.spec.ts`, the folder picker and keychain) and in the DOM lane. Codemode runs only in Electron, where the QuickJS worker runs in a utility process. A flow with nothing native, such as sending a reply, navigation history, a Home agent question or provider setup, runs only in the browser or the DOM lane. Electron otherwise covers native sessions/keychain, CSP/protocols, windows/menus, PDF and HTML frame keys, Quick Look and image clipboard, web panels, privacy/screen sharing, updates and crash supervision. One engine kill in `juno-agent/crash.spec.ts` checks everything that must survive it: the AI key main sends again, the agent's and the window's ports, the open topic and its draft, the sidebar and the dock dot; add a check there rather than another kill. It is a nightly test. The image route's address rules are a `bun test` (`apps/desktop/test/publicImage.test.ts`). `idle-cpu.spec.ts` runs a short walk of the real processes in Electron (`idleJourney.ts`, `@nightly`); its large-seed walk with the fine Mac budgets is `@mac` and runs only by hand. Every run also counts the engine's work passes at rest under a test clock (`packages/engine/test/flows/idle.flow.test.ts`) and checks that nothing on screen moves after a Juno answer (`juno.expectAtRest()`, in `juno-agent/panel.spec.ts`). Manual screenshot tools live in `e2e/screens/` (and `screens.spec.ts`) and are discovered only with `JUNO_SCREENS=1`; Mac performance specs use `bun run perf` and are excluded from this project. Renderer file viewing and shell styling run in the browser, and privacy mode and Open from an image menu in a peek in the DOM lane; damaged-cache recovery is an engine flow (`packages/engine/test/flows/gap-and-restart.flow.test.ts`). Diagnostics owns the process table and content-free report; the live-update restart flow owns engine port recovery. The obsolete raw provider RPC and duplicate hello/crash specs were deleted; provider UI flows now cover model selection, custom endpoints and removal.

The JSON reporter always records per-test durations; traces require `JUNO_E2E_TRACE=1`.

The former Resolve spec is part of the approval/double-click/restart flow in `dom/juno-agent/break-pass.test.ts`. The same flow covers AI-off with a pending card; Budget behaviour lives in `dom/juno-agent/cards.test.ts`. Disabled schedule-notification and T3 sparkle cases were removed from the executable suite: agent notification delivery is not implemented. They remain product gaps, not passing coverage.

## Feel scenarios

The feel scenarios (`e2e/feel/*.feel.ts`, `docs/development.md`, "The feel suite") are the `feel` project: the browser lane's setup, in parallel, in `test:browser`. Every test in it is `@nightly-feel`, so it runs in each nightly full run, in a release's reach (`scripts/nightly-reach.mjs`) and in `bun run affected` plans for a changed scenario, a change to their harness, or the scenario of a changed interaction (`PERF_INTERACTIONS`). Each films its interaction through the CDP screencast and checks it frame by frame. On this shared machine a passing scenario keeps only its checks, a failed one its frames, filmstrip and video in `test-results/feel-report/`, and a long animation frame only warns: timing belongs to `bun run perf`. They use the fixtures (`relaunch`, `juno.setWindowSize`, `juno.surface`), so `bun run test:feel` still records them in Electron on the Mac with every video, for a feel review. A feel scenario does not repeat a check the browser lane makes: Home's and the session's first-sync frames are in `layout-shift.spec.ts` and `session.spec.ts`. Scenarios with the same start share a launch, and most start from the synced snapshot.

## Scheduling and setup timings

Ordinary fake-Slack launches use the engine unit harness's 1:20 scheduling scale and disable periodic discovery in favour of explicit catch-ups. Dependency polling, socket pings, and hello and pong deadlines keep their production values because Electron and the fake run in separate real processes. The engine host accepts it only with both e2e mode and a fake Slack URL; a normal launch keeps production defaults. `test.use({ timing: 'production' })` or `launchApp(dir, { timing: 'production' })` keeps real timing for a test of a window itself; no spec uses it now (the reaction-versus-edit-backoff check runs in `outbox-actions.flow.test.ts` on a test clock). Staying active while at the Mac runs in `apps/desktop/test/activity.test.ts`, main's activity watch on a fake idle time against the engine; socket spacing is covered in the Slack package. Paced sync launches, `perf.spec.ts`, feel scenarios, `idle-cpu.spec.ts` and tests tagged `@mac` keep production timing automatically.

For a negative AI or Automated assertion, `await juno.workPass('title')` (also `art`, `home` or `automated`) requests a pass through the job's existing serial consumer. The engine acknowledges only a pass started after that request, including a pass that chooses not to call the model. It fails after 10 seconds instead of accepting an unfinished pass. AI jobs still need `aiJobs: true`.

`bun run remote --env JUNO_E2E_TIMINGS=1 test:desktop <specs>` prints separate fake-start, Electron-launch, sign-in, sync-wait and close durations in milliseconds. These are setup observations, not the Mac performance budgets. Related checks with the same starting state share one launch with labelled `test.step` calls. Each flow owns its fake and user-data directory; cold starts, different fixtures and failure scenarios remain separate. Timing budgets live in `*.perf.spec.ts` and run through `bun run perf` on the Mac. The fine idle budgets in `idle-cpu.spec.ts` are `@mac`; app diagnostics remain the primary way to find field spins.

## Synced start

Most tests begin signed in to the default seed with the first sync done. `test.use({ synced: true })` in a file, or `syncedTest` from `fixtures.ts` for single tests in a file whose other tests sign in themselves, starts the app that way without signing in. The test body then starts where `juno.signIn()` and `juno.waitForSync()` used to leave it.

- **Browser project:** one snapshot per run for each set of engine options (`browser/snapshot.ts`), made by the first worker that needs it while the others wait on a lock, and kept for five minutes. A fake made to match it uses the seed's time and sessions on a port of its own: the host maps the snapshot's fake origin, which its stored avatar and file addresses name, to the test's fake (`aliases` in `web/host/fakeMain.ts`), and the state guard compares the fakes with that origin taken out. The copy is an APFS clone on the Mac.
- **How (Electron):** each worker signs in once to a fresh default seed, waits for the sync, quits, and keeps that user-data directory (`synced.ts`). Each synced test gets a copy and a fake made to match it: the same seed run at the same seed time (`seedTime`), on the same port (the seed's avatar and file URLs name it), accepting the same sessions. The app then boots warm, as after a relaunch, and the fixture waits for `waitForSync()`.
- **Never stale:** the key includes `out/.inputs-hash`, which `build-cached` verifies before Playwright starts. That fingerprint covers what the app bundles (store schemas and migrations, engine and sync code), the locked packages it imports, the toolchain and the built output bytes. The fake seed is not in `out/`: the fake runs in the test process, which loads its source once per run, and copies live only in their worker. The browser and DOM lanes' keys (`dist/` and `dom/dist/`) do cover the seed, since their host bundles the fake. Copies live only in their worker, and are rebuilt after five minutes. A copy kept between runs would save one sign-in per worker (2–3 s) and could go stale, so none is kept. The effective timing profile and `fakeAiDelayMillis` are also in the key. AI jobs cannot use a snapshot.
- **Guard:** before and after the warm boot, the fixture compares the fake's workspace hash with the state captured after the snapshot app quit. It includes ids, timestamps, mutation markers, read pointers and subscriptions. Only the clock and self presence are omitted; presence follows the current time at session start. The fake must have no sockets before launch and exactly one after sync. A mismatch fails setup. Socket URLs and reconnect state are process-local, so a new fake and engine start a new socket session; no old connection is reused.
- **Warm boot:** the snapshot is caught up with its fake, so the warm boot fetches no history. It still makes 24 calls to the fake: session, counts, the followed-thread pages, the discovery search, and the recheck's 10 history and replies pages (`packages/sync/src/recheck.ts`, `specs/catchup.qnt`). Edits made while the app was closed send no signal, so the recheck cannot know nothing changed. Skipping it would boot tests differently from the app and save little, so it stays: in process the whole warm boot takes about 80 CPU-ms, the recheck 11 of them (10-26, Mac). What a synced start costs is the processes and renderers around the engine: about 0.55 CPU-s in the DOM lane, 1.2 in the browser lane and 2.9 in Electron (laptop, one worker, an empty test).
- **Real sign-in stays** only for tests whose subject is sign-in, the first sync, quick start, sync convergence or boot (`session`, `layout-shift`'s cold-sync checks, `engine`, `sidebar-first-sync`, `welcome`, perf, idle and feel), for tests on a seed of their own (topic300, the quiet Home, the large seed: the snapshot is the default seed's), and for AI jobs (below). A cold start costs about 1 to 3 CPU-s more than a synced one in the browser. A test that needs the fake changed changes it after the synced start: messages, DMs and replies arrive live, Slack prefs as a `pref_change` frame, and what only a boot reads (workspace emoji) before a `relaunch()`. Established Juno Agent flows use `synced: true` and `readySynced`; custom seeds and backup transfer keep cold starts.
- **Not with AI jobs:** `synced` refuses `aiJobs: true`. The jobs keep writing titles and art after the first sync, so a copy holds results a fresh sign-in has not made yet (a Home test read the AI title where it expected the message text). A test with AI jobs signs in, in either lane.

A kept page per worker was tried (branch `browser-reuse`): each test imported the bundle again under `/g/<n>/` on the same document, with every global effect tracked, put back and checked. It passed the lane and its isolation checks, but saved nothing: the renderer's start fell from 493 to 433 ms per test and the teardown and check cost the rest (4,498 against 4,496 CPU-ms per test, one run each). A page load is only 80–100 of the renderer's 270 ms start (trace); the rest is the first render with data, which a fresh test needs anyway. Resetting a booted engine instead of starting one would save at most its start, about 100 ms, of which the catch-up is 15–20 ms, and needs a reset path through the whole engine; each test keeps a fresh engine.

Browser workers reuse loaded hosts and contexts with the reset described above; engines and pages remain fresh. Both lanes get an isolated user-data directory.

## Electron lane

- **A fresh app per test.** Each Electron test launches its own app process. Keeping main alive between tests saved about 0.4 s of wall time a start without resetting everything main holds; the experiment and its limits are in [Test speed round 4](../../../docs/test-speed-4.md#worker-app-reuse-experiment).
- **What a test costs.** On one worker, an Electron test spends about 1.4 CPU-s launching, 2.3 CPU-s on a synced start's warm boot and sync, 0.2 CPU-s closing, and the rest in its body (2026-10-26, `cpu-*` phases above); the lane's 35 tests burn 229 CPU-s that way. At eight workers on four physical cores the same tests burn about 346.
- **Shared launches.** A launch and a synced start cost about as much as a short test's body, so checks that start from the same launch and only look at different native surfaces share one test: the file viewers, image menus and text menu (`file-viewer.spec.ts`); swipes, minimize and zoom (`break-pass.spec.ts`); the signed-in shell with the build line, updates off and full screen, and the preload bridge with the second launch (`app.spec.ts`); a malformed launch.json and a window on a display that is gone (`break-pass.spec.ts`). A check that needs other launch options, a cold start or its own failure stays its own test.
- **Order.** The project runs fully parallel: each test is its own group, so one file's tests spread over the workers. The files in `ELECTRON_FIRST` (`lanes.ts`) start first, slowest first (`order.ts`), so a 20-second agent test does not start last and hold the run open. Update the list from a run's `e2e-timing` lines when a test's length changes a lot.
- **GPU.** Launches keep the GPU process. Without it (`--disable-gpu`) one-worker runs burned the same CPU (239 against 240 CPU-s), so the lane keeps the default Chromium setup.

## Sidebar trace

A sidebar test that fails because a row did not appear, or did not move, needs to say whether the sidebar held its order or was given no new list. The sidebar trace records both.

- **On:** `test.use({ sidebarTrace: true })` in a spec file, or `launchApp(dir, { sidebarTrace: true })`. The sidebar specs (`sidebar`, `sidebar-first-sync`, `sidebar-hold`, `sidebar-motion`, `main-new-threads`, `views`, `layout-shift`) have it on; the DOM lane has it on for every test. The fixture puts an empty `globalThis.__junoSidebarTrace` on the main window, which turns the recording on (`packages/state/src/sidebarTrace.ts`).
- **Off:** the app records nothing. A change of the hold's inputs costs one property read, and a topic list value another.
- **What it records:**
  - `hold`: the last 60 changes of the order hold's inputs (SPEC 5, "Holding the order"). Each entry names the change (`list entered (pointer true, keyboard false)`, `left`, `sheet opened`, `sheet closed`, `flushed`, `resumed`, `released a topic`) and the state at that moment: `engaged`, `paused`, `sheets` (open sheets) and `released` (topics shown at once while held). `list entered` and `list left` come from the list itself, before the hold takes them in; the entry after says what changed. The list holds while `engaged || sheets > 0`, unless `paused`.
  - `list`: how many topic list values the sidebar was given (`values`), how many said the engine's run failed (`errors`), and the last of each (`seq`, row count, filter, error).
- **When a test fails:** the `running` fixture attaches the trace as `sidebar-trace` and prints it on one line, `sidebar trace (<test>): {...}`, so a remote run's `run.log` has it.

Reading it: a row that never appeared with the hold still on (`engaged` or `sheets > 0` and not `paused` in the last entry) points at the hold. A `list.last` older than the change the test made, or a rising `errors`, points at the engine's `topics.list`.

## Send trace

A test that sends from Home and then misses the message in a tab needs to say where the message got to. The send trace records the send's path through the renderer.

- **On:** `test.use({ sendTrace: true })` in a spec file, or `launchApp(dir, { sendTrace: true })`. `break-pass-1017` and `home-send-tab` have it on. The fixture puts an empty `globalThis.__junoSendTrace` on the main window, which turns the recording on (`packages/state/src/sendTrace.ts`).
- **Off:** the app records nothing. Each traced point costs one property read.
- **What it records**, the last 120 entries, each with `at` (`Date.now()`), ids, states and counts, never message text:
  - `send asked` and `send answered`: the send command (`sendMessage` in `@juno/state`), its target, the first 8 characters of its `clientMsgId`, and the topic it answered with.
  - `background`, `background opened` and `background window`: Home's open of the topic behind it (`openTopicInBackground`), with `reused` when a tab already showed it.
  - `switch`, `tabs asked`, `tabs applied` and `tabs dropped`: a tab change the navigation was asked for, with its ticket, the one it applied (the active tab after it), and one a newer change replaced.
  - `tab mounted` and `tab unmounted`: a tab's topic view.
  - `window`: each new message window a topic view got (`view` is `<topic>@<tab>`): its `seq`, row count, newest row, the spec, and in `sent` each of the last rows sent from this app as `<clientMsgId>:<sending|failed|stored>:<ts or pending>`.
- **When a test fails:** the `running` fixture adds the fake's `chat.postMessage`, `conversations.open`, `chat.update` and `chat.delete` calls (`posts`: time, method, channel, answer) and attaches the whole as `send-trace`, and prints it on one line, `send trace (<test>): {...}`, so a remote run's `run.log` has it.

Reading it: no `posts` entry for the channel means the send never left the engine. A `window` for the tab's view whose `sent` stays at `pending` while `posts` shows an answer points at the engine's reconcile. No `window` for the tab's view after the send means its subscription did not run again. A `tabs dropped` or no `tabs applied` with the tab active after `switch` means the tab never showed.

## Relaunch frames

The relaunch check in `session.spec.ts` (a nightly test) attaches `relaunch-frames` JSON before its assertions. It records the total frames, sidebar and sign-in counts, and each frame without a sidebar. Each missing frame includes its index, time since navigation, root child count, whether an earlier sample had the sidebar, and whether the bundle and shell-paint marks exist. `hadShell: false` with an empty root identifies a gap before the first shell. `hadShell: true` identifies a later disappearance. The test still requires the sidebar in every sampled frame and no sign-in frame.

Check the failing run's commit before diagnosing a new startup regression. Worktrees created before `fd8ae4f7` can still run the old delayed initial render after that fix lands on main.

## Heavy tests

A test that is slow because of what it checks, and whose code rarely changes, is tagged `@heavy` and its area's tag: `test('...', { tag: ['@heavy', '@heavy-sync'] }, async () => ...)`. `HEAVY_AREAS` in `scripts/test-areas.mjs` lists the areas and the files each covers; add a file there when a heavy test starts to cover it. `bun run affected` skips an area's heavy tests unless the change is in that area, by setting `JUNO_SKIP_TAGS`; a full run (`bun run verify:main`) and a run by hand keep them. See `docs/development.md`, "Affected tests".

## Nightly tests

A long journey whose code changes rarely is tagged `@nightly` and its area's tag: `test('...', { tag: ['@nightly', '@nightly-crash'] }, async () => ...)`, or `domTest(title, body, { tag: [...] })` in the DOM lane. `NIGHTLY_AREAS` in `scripts/test-areas.mjs` lists the areas (crash, huddle, idle, feel, sync) and the files each covers. A normal full run skips them; `bun run verify:main --nightly` runs them; `bun run affected` runs an area's nightly tests when the change is in that area; a release runs the nightly files its changes reach since they last passed. `bun run test:nightly [files]` runs them by hand. Before tagging a test, keep one test per rule on every run: in the crash area that is the uncertain write in `juno-agent/crash.spec.ts`, and in scroll and shift one test per rule (`docs/development.md`, "Nightly tests", lists them).

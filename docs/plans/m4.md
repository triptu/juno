# M4 plan: topic view and tabs

October 2026. Inputs: SPEC sections 3, 6, 7, 8, 10 and 17; inventory sections 4 to 7 and 15 to 21; `friendly-layer.md`; architecture sections 4, 5, 7, 8, 9 and 16; `performance.md` sections 1, 3, 4 and 5; `specs/readstate.qnt`; the package READMEs and the code on `main` at `2dce880`.

## 1. Scope

M4 makes a topic readable. Opening a row shows the topic in a tab, at the "N new" divider or at the bottom, with live messages, and marks it read in Juno and in Slack unless the tab is stealth.

In scope:

- **Topic view.** Header with the context pill, title, AI sparkle (shown when `titleSource` is `ai`), the stealth pill with Mark read, and the Subscribe action (the command exists from M3). A composer slot of the composer's final height, so M6 swaps it in with no shift.
- **Message list.** Flat style. Messages from the same sender group under one header (a quote or the divider starts a new one). Message times. Mentions as chips (person hue, `@you` in the accent with a tinted row), `#channel` chips that scope the sidebar, links opened in the browser, quote blocks, code blocks, lists, custom and standard emoji. Reactions shown read-only. File cards with reserved geometry. The "N new" divider. "N new messages" and Jump to latest when scrolled up. Older pages on scroll up. The 500-row cap.
- **Hover toolbar** as a view with fixtures only. The app does not mount it until its actions work in M6. A button that does nothing is worse than no button.
- **Main.** "#eng · Main" header, thread links under roots ("2 replies · Title ›", "1 reply", "Thread"), and the channel's active threads list with Subscribe on each (question 1). Opening a thread from Main does not add it to the sidebar; subscribing does.
- **Rendering through `@juno/richtext`.** It gains `date` inlines, `file` blocks and legacy `attachments` fallback text. Custom emoji come from `emojis/list` (sync step 6, in the backlog today).
- **Read state.** The read rule (question 2). Mirroring through `conversations.mark` for Main and `subscriptions.thread.mark` for followed threads. Unfollowed threads stay local only. Marks are coalesced, retried and acknowledged as `specs/readstate.qnt` says. The engine also gets `reads.markUnread`, because the spec covers it; its menu item is M5.
- **Stealth.** A tab attribute. It is opened from a minimal native row and tab menu with two items, Open in new tab and Open in stealth (M5 adds the rest). The stealth pill's Mark read and the tab's eye-off icon. Stealth survives a restart.
- **Tabs.** Opening uses the current tab, and ⌘-click opens a new one. An already open topic gets focus instead of a second tab. Closing a tab focuses its neighbour. Tabs persist through user.db prefs. The active tab and the 4 most recent topic tabs stay mounted in `<Activity>`, and the rest keep a `ScrollSnapshot`. ⌘W, ⌘⇧[ and ⌘⇧] are app-menu items.
- **Live messages.** New, edited and deleted messages and reactions arrive as one-row deltas. On reconnect, the topics that are open and visible are refreshed (architecture 5.8).
- **Prefetch.** Hover, focus or keyboard selection of a sidebar row warms `messagesAtom` (at most 3, 30 s TTL) without calling Slack.
- **Local FTS search, engine only.** The `search.query` route over titles, messages, channels and people, held to the 20 ms FTS budget on the large seed. Architecture 16 puts it in M4; the ⌘K UI is M9.
- **People and channels side tables.** `ListDelta.refs` as planned in architecture 7. Messages use it from the start. `topics.list` moves to it too, which closes the 346 KB snapshot item in the backlog.
- **The performance gate** (performance 3.4): open a cached 300-message topic in 50 ms or less, scroll within the frame budget, and prepend 100 rows with zero shift.

Out of scope:

- Composer, sending, edit and delete, toggling reactions, the emoji picker, quote insertion, selection Quote, Reply in thread, drafts, attachments, upload and download (M6).
- Pin, Resolve, Reopen, Rename, Use AI title, the More menu and the full context menus, the Mark as unread item, undo toasts and the ⌘Z stack (M5). The header leaves room for them.
- Catch-up card, grouping suggestion, settled hint, AI titles and the send checks (M8).
- ⌘K and search UI (M9). The All topics, For you, Juno, Notifications and Preferences pages. The tab model supports page kinds, but M4 only opens topic tabs.
- Bubble style and every other appearance tweak.
- Typing indicators and presence.
- The persisted outbox for other kinds, reconnect hardening and offline UI beyond what exists (M7).
- Thumbnail bytes, unless question 3 brings them in.
- Topic art: a separate track (section 6).

## 2. Open questions for the owner

Each of these blocks a design decision. A recommendation comes with each.

1. **Where does Main's active-threads list live?** (a) A "Threads · 12" button in the Main header that opens a popover list. (b) A section above the messages. (c) A side panel. Each entry shows the title, reply count, time, unread count and a Subscribe bell; opening one uses the current tab. *Recommend (a).* It keeps Main a plain stream and costs no width at 720 px.
2. **When does an open topic mark read?** Proposal, like Slack: mark up to the latest message on open. After that, mark new messages only while the tab is active, the window is focused and the list is at the bottom. Messages that arrive while you are scrolled up stay unread behind "N new messages" until you reach the bottom. *Recommend yes.*
3. **Images in M4?** The architecture moves thumbnails through main's `juno://files` in M6. Without them, about 1 in 6 messages shows a grey file card of the right size. Serving thumbnails is a small main-process handler (display only; download and upload stay in M6). *Recommend bringing thumbnail display into M4.*
4. **May Juno mirror read marks to your real workspace while M4 is being built?** Marks are writes. *Recommend:* engine config `mirrorReads` stays off for live runs. Marks stay local until you turn it on. Mirroring is tested against the fake, and checked live only in your self-DM and the private test channel.

## 3. Work packages

Five packages. Ownership is disjoint except for the shared one-line edits. Those are `engine/src/layer.ts`, `contract/src/routes/index.ts`, the `index.ts` barrels, `views/src/fixtures.ts` and the store migration lists. Each package appends its own lines, and the lead merges them in package order.

Order and dependencies:

1. **Day 0, contract first.** WP1 lands `contract/src/routes/messages.ts`, the `MessageBody` schema and `refs` in `live.ts` as a small first merge. WP2 lands the signatures of its domain and richtext additions. The lead reviews both before anyone builds on them.
2. **In parallel.**
   - WP1 builds the engine and state.
   - WP2 builds its rules, search, emoji and the seed.
   - WP3 starts after the `unfollow-fix` worktree merges, because both touch `sync/src/write.ts` and `events.ts`.
   - WP4 builds views against fixtures that follow the contract.
   - WP5 starts on the tab rules, the prefs route, main-process items and the driver.
3. **Wiring.** WP5 wires the containers as WP1's atoms and WP4's views land, then runs integration, e2e and the perf gate.
4. **Merge order.** WP2, WP1, WP3, WP4, WP5.

### WP1. Message data path (Opus)

**Goal.** A topic's messages, header data, thread links and the channel's active threads reach the renderer as live queries within budget. Opening a topic fetches only what is missing.

**Files owned.**
- Contract and state:
  - `contract/src/routes/messages.ts` (new): `messages.list`, `topics.get`, `channel.threads`, `topics.open`, `messages.loadOlder`.
  - `contract/src/body.ts` (new): a `MessageBody` schema with a compile-time check that it matches richtext's model.
  - `contract/src/live.ts`: `refs`.
  - `contract/src/routes/topics.ts`: rows carry person and channel ids.
  - `state/src/list.ts`, `atoms.ts`, `messages.ts` (new), `sidebar.ts` (joins refs into row objects so `TopicRow` props do not change), `state/test/list.test.ts`.
- Engine: `engine/src/messages/` (new: handlers, window query, view-model shaping, open fetch) and `engine/src/topics/query.ts` (the refs move).
- Sync: `sync/src/open.ts` (new: `fetchThread`, `fetchMainPage`, `fetchOlder`, `refreshVisible`) and the "replies refresh for open topics" step in `sync/src/sync.ts`.
- Store: a cache migration for a Main window index, plus `CACHE_SCHEMA_VERSION`.
- Tests: `engine/test/messages.test.ts`, the new cases in `engine/test/plan.test.ts`, `engine/test/bench/messages-large.test.ts`.

**Interfaces.**
- Consumes WP2's `messageBody` additions, `startsGroup` and `threadLinkLabel`.
- Provides `messagesAtom(id, window)`, `topicAtom(id)` and `channelThreadsAtom(channel)` to WP5, and the `MessageView`, `TopicDetail` and `ThreadSummary` types to WP4.
- `topics.get` carries `lastReadTs`, so the container can snapshot it for the divider.
- `messages.list` takes an anchor ts and returns up to 50 rows before it and the rest after.
- A subscription never calls Slack. Only `topics.open` and `messages.loadOlder` do, on the interactive lane. The open fetch reaches back to the read pointer, capped at 500, so the "N new" count is exact. This also covers the backlog's `unreadExact` item for opened topics.

**Tests.**
- Engine, against the fake:
  - Opening a thread whose replies are not stored makes exactly one `conversations.replies` call and delivers the rows. A second open is incremental.
  - Opening Main reads history from `synced_ranges`.
  - `loadOlder` prepends one page.
  - A reply from another client is one upserted row, with a delta under 32 KB.
  - An edit, a tombstone and a reaction each change one row.
  - A Main thread link updates when its thread gets a reply.
  - A prefetch subscription makes zero Slack calls.
  - A person's new photo is one `refs` upsert, and no row's `rev` changes.
  - Opening an uncached topic while offline gives the header and an empty list, not an error.
- Plan test: no `SCAN` for the Main window, the thread window or `channel.threads`.
- Bench on the large seed: a `messages.list` run in 5 ms or less at p95, a 300-row snapshot of 200 KB or less, deltas of 32 KB or less, encode and decode in 5 ms or less each, and the `topics.list` snapshot back under 200 KB.

**Definition of done.**
- Everything above passes.
- `pnpm typecheck`, `pnpm lint` and the engine, state and sync tests pass.
- The contract, engine and state READMEs and architecture 7 describe `refs` and the new routes.

### WP3. Read state, mirroring and stealth (Opus)

**Goal.**
- Juno's read pointer follows the read rule.
- Mirroring follows `specs/readstate.qnt`: a pending local mark wins, a newer server observation is kept while a mark is pending, fetches are guarded by generation, retries keep the intent, and acknowledged marks apply in order.
- Stealth never marks.

**Files owned.**
- `domain/src/reads.ts` and `domain/test/reads.test.ts`. Today `applyServerRead` drops events while a write is pending, but the spec keeps the newest observation and applies it after the acknowledgement if it is newer.
- `contract/src/routes/reads.ts` (`reads.markRead { id, upTo? }`, `reads.markUnread { id }`) and `engine/src/reads/`:
  - commands;
  - the mark worker on the `Outbox` seam: one `mark` row per target, coalescing to the last, retry with backoff on transient errors, acknowledgement into `local_write_ack_ts`;
  - the `mirrorReads` config flag.
- The read-state section of `sync/src/write.ts` and the mark cases in `sync/src/events.ts`.
- A user.db migration if the retained observation needs columns.
- `specs/readstate.qnt`, `specs/mirror.qnt`, the read section of `specs/README.md`, and a read-state rule table in the sync README like the follow one.
- `engine/test/reads.test.ts`.

**Interfaces.**
- WP5's container calls `reads.markRead` on open (not in stealth), on reaching the bottom, and from the stealth pill's Mark read.
- The Main mark is the latest Main message. Groups are later.
- `reindexTopics` runs in the same transaction, so the sidebar count changes with the mark.

**Tests.**
- Engine, against the fake, using `callCount` and `holdNext`:
  - mark read on Main makes one `conversations.mark` with the latest ts; a followed thread gets `subscriptions.thread.mark read=1`; an unfollowed thread makes no call;
  - five marks in a row make one call; a 5xx then success is retried once and acknowledged;
  - an older `channel_marked` during a pending mark changes nothing; a newer official mark during a pending mark is kept and applies after the acknowledgement;
  - `mirrorReads: false` makes no call and keeps local state.
- `pnpm specs:check` passes, with directed schedules for coalescing, a pending mark plus a newer official mark, retry after acceptance, and stealth then Mark read. `stealthNeverMarks`, `localUnreadProtected`, `acceptedUnreadProtected` and read `quietAgreement` hold.

**Definition of done.** The tests and the spec check pass, and any rule the code and spec disagree on is fixed in one of them, in this package.

## 5. Risks

- **The message list misses the gate.** `content-visibility` plus in-flow rows may not open 300 messages in 50 ms, or may shift on prepend. The escalation is TanStack Virtual. It costs ⌘F and selection beyond mounted rows. Budget a day in WP5 and decide on numbers, not taste.
- **The open position with estimated row heights.** Rows above the divider are not rendered yet, so placing it 80 px from the top relies on anchoring to the divider itself, not on `scrollTop` arithmetic.
- **Writes to the real workspace.** Marks change the owner's real read state. Mirroring stays off for live runs until he says otherwise (question 4).
- **Read-state races.** The current domain rule drops observations while a mark is pending, which the spec forbids. Rapid marks can hit Slack's rate limits. Coalescing and the per-method buckets must be in place before mirroring is on.
- **Merge conflicts in sync.** The `unfollow-fix` worktree is changing `sync/src/write.ts` and `events.ts` now. WP3 waits for it.
- **The refs move regresses the sidebar.** It is the last step of WP1, behind the sidebar e2e and the M3 perf scenarios. If it slips, messages still use refs, and `topics.list` stays as it is with the backlog item open.
- **Duplicate schemas.** `MessageBody` exists as richtext types and as a contract schema. The compile-time equality check catches drift.
- **Hidden tabs and effects.** `<Activity>` destroys effects, so any subscription or timer set outside an effect leaks. StrictMode in dev and a memory soak over 50 tab switches catch it.
- **Machine load.** Several agents share one machine. Every heavy job goes through `scripts/heavy.mjs`, and perf numbers are taken on a quiet machine with the load average recorded.

## 6. Topic art: a separate track

Topic art does not belong in M4. It is an AI generation feature: an `@juno/ai` task, an assistant job with a budget, a user.db table, a new `@juno/topic-art` package and a token palette. It changes sidebar tiles, which are an M3 surface, and the owner has not yet picked the container.

M4 keeps the 15 px tab icon slot and the header icon slot fixed in size, so art and the Tide placeholder can drop in with no layout shift. The track can start as soon as the container is chosen.

- **Its files:** the new package, `ui/TopicArt.tsx`, the art tokens, the `ai` task, the assistant job and the migration. None of them overlap M4.
- **Merge order:** its change to `TopicRow` in the contract merges after WP1.
- **Order of work:** Tide first (no AI, no cost), then the generated art.

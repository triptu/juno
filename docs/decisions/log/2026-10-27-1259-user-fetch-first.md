- 10-27 12:59 · The user's own Slack fetch goes first · Every topic fetch shared the interactive lane in arrival order, so a jump (Next and Previous in the search reader, a match far up a thread, a link) could wait seconds behind a thread's page loads. Pages read ahead of the user (older and newer pages, an open's later pages, the reconnect refresh) now run as `paging`: the same three permits and token bucket, but they wait behind any waiting interactive call and never take the last permit or the last two tokens. No concurrency or rate is added, and nothing is dropped. With Slack holding three threads' later pages, a jump was answered in 28 ms against 5,116 ms before (performance.md 6, "Priorities"). Scheduling only, so no Quint change: every paging start is also a start `requestqueue.qnt` allows.

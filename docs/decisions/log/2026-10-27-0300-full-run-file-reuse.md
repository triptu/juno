- 10-27 03:00 · Full runs reuse unchanged test files' passes and rerun a fresh 20% sample · Tushar decided that a full run reuses each test file's pass from an earlier green full run while the file's inputs are unchanged, as the gallery walk already does, in the unit (engine flows included), DOM, browser and Electron lanes, a bun test file or a spec or feel file at a time (`scripts/verify-files.mjs`). A file's key covers what affected selects it by, with whole barrels, the files and folders it names from its own folder, every data file of the packages it reaches, its lane's build, the harness (lockfile, root configs, `scripts/remote/`, the scripts that plan and run the lanes) and the lane's command. A pass is reused only from a run with the same runtime and toolchain: each job reports the Bun build, Node, Playwright, Chromium, Electron, OS, kernel, time zone and locale, and a run whose jobs report another toolchain while reusing starts again with every file fresh. Every run reruns a fresh random 20% of the reusable files (new seed, printed and recorded); a sampled file that fails fails the run as a missed input. Every file runs when the last fully fresh run is over seven days old, or with `--no-cache`; repairs keep their rules and are not reuse sources. The record keeps per lane the files that ran because they changed, were sampled, or were reused and from which run, and the release gate refuses counts, samples or commands that do not match. Jobs shrink to the work left, by each file's recorded test time. Measured on the laptop after a fresh run (143 s, the gallery walking every state): a view comment change took 102 s (147 of 184 unit files reused, 990 against 1,451 CPU-s, the unit job on two cores); an engine comment change 97 s (112 reused, 1,127 CPU-s); a change that reached no file's key 50 s on six cores. Both real changes reach the desktop app, so the desktop job still set the wall. A deliberately stale key on a recorded fixture was caught by the sample.

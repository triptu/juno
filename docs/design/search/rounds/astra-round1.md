Make Search a persistent reading workspace. Its advantage should be how quickly a manager can inspect several conversations, recover context, and return later. This proposal deliberately changes SPEC §10; it preserves the tab conventions in §6.

Seven ideas worth building:

1. **Keep results beside the conversation.** Selecting another match changes the reader, not the page. Managers can check several candidates without reconstructing their search. Cost: independent focus, selection, and scroll restoration.
2. **Collect matches by thread.** Show the strongest matching message and “3 matches loaded”; navigate those matches inside the reader. This makes a long discussion understandable without filling the list with replies. Risk: grouping can hide evidence, so provide “Show every message.” Never collapse an entire channel’s Main into one result.
3. **Make filters readable and reversible.** People, conversations, dates, and content filters work through both operators and chips. Managers need not remember syntax. Cost: one rigorous parser and reliable identity resolution.
4. **Show context without changing unread state.** The reader behaves like an expanded peek, with no composer or mark-read. Opening the conversation restores ordinary behavior. This prevents research from consuming the manager’s unread queue. Cost: a reader lifecycle separate from topic activation.
5. **Remember the investigation.** Preserve query, selected match, and both scroll positions; support named saved searches. Managers can resume after an interruption. Risk: sensitive queries require privacy treatment and clear-history controls.
6. **Translate vague requests into proposed filters.** “Maya’s contract messages last month” can suggest visible person/date chips. This saves query construction without hiding assumptions. Cost: occasional wrong interpretations; acceptance must be explicit.
7. **Summarize the selected discussion on request.** A short, cited summary helps distinguish a decision from an abandoned proposal. Cost: generation latency and incomplete threads; show coverage and never claim an unresolved question was settled.

The Search tab has a full-width query field, then From, In, Date, and More controls. Under it, a resizable results column starts at 360px, ranges from 320–480px, and leaves at least 440px for the reader. These are proposed token values. Keep the ordinary sidebar preference; below 800px of available workspace, show results or reader with “Back to results,” preserving both positions.

A result uses three compact lines: safe topic title; sender, conversation/privacy icon, and date; two-line matching excerpt. Main messages remain individual rows. Thread grouping uses actual thread identity, never model similarity. The reader opens around the exact match, with neighboring messages, a thread header, next/previous match controls, and “Open conversation.” Render term highlights in snippets and messages through the rich-text model, preserving Unicode offsets and links. Highlight positive literal terms only; semantic matches should not invent matching spans.

Start with Messages. Add Files once its endpoint and coverage are verified; do not mix people/channel navigation into message results. Those remain in ⌘K and filter autocomplete. Offer Best match, Newest, and Oldest; enable Best match only after verifying the internal endpoint’s score sort. Otherwise ship Newest rather than label an unknown order as relevance.

Arrow keys move results while focus stays in the list; optional j/k work only there. Enter opens the selected conversation using existing tab-reuse rules; ⌘Enter/⌘-click opens a new tab. Back restores the search where it was; if Enter focused an existing topic tab, the Search tab remains intact. Tab reaches the reader; Escape returns focus to results. Do not steal ordinary input keys. Announce result readiness without announcing the entire preview.

⌘K keeps quick navigation and message matches, with “Show all results” carrying the query and selected match into Search. Add a Search page command and ⌘⇧F; ⌘F from a conversation opens Search with its conversation chip. Empty Search shows recent and saved queries. Empty results distinguish “No cached matches,” “Searching Slack,” “Slack unavailable,” and a completed search with no matches. Offer removing individual filters; never broaden automatically.

**One query model** must serve Search, ⌘K, and the agent’s local search. Define a schema-backed `SearchQuery` with version, workspace, clause tree, resolved identity references, date interpretation/timezone, scope, and sort. Keep raw text and source spans alongside it for editing. A pure domain parser produces unresolved references; the engine resolves them and compiles the same object into parameterized SQL and escaped Slack syntax. The contract carries this model; views receive props only.

Grammar: whitespace means AND; support quoted phrases, escaped quotes, trailing `*`, unary `-`, and `in:`, `from:`, `with:`, `before:`, `after:`, `on:`, `during:`, `has:`, `is:`. Start with one value per filter; defer OR/parentheses and reject repeated conflicting filters rather than invent semantics. Preserve incomplete tokens while typing. Resolve names through autocomplete to IDs; ambiguous names remain editable, unresolved chips. Unknown operators get a diagnostic, not silent omission. [Slack documents these core modifiers](https://slack.com/help/articles/202528808-How-to-search-in-Slack).

Chips are a rendering of query clauses, not another filter store. Clicking edits the corresponding clause; removing deletes it; copying yields equivalent operator text. Literal searches require explicit wildcards: the palette’s implicit final-word prefix may remain a clearly separate suggestion mode, not silently change submitted queries.

Compilation rules:

- Terms/phrases/prefixes become escaped FTS MATCH expressions and corresponding Slack text. Negative-only queries use relational candidates plus exclusion, since FTS needs a positive base.
- `from:` becomes `m.user_id = ?`; `in:` becomes `m.channel = ?`; negatives invert those predicates. Slack receives the verified identity syntax for the same IDs.
- Dates become timestamp ranges; `on:` and `during:` use half-open intervals. Preserve Slack’s observed exclusive `after:` day rule. Verify timezone/DST behavior before promising parity; do not assume UTC from one probe.
- `is:thread` includes replies and roots with replies. Reactions, links, and files use indexed facts/EXISTS predicates and corresponding `has:` modifiers.
- `with:` needs actual thread participation and DM membership, not merely sender equality. `is:saved` means Slack saved items, not Juno pins. Until these facts and semantics are available, mark those queries “Requires Slack” and suppress misleading local matches. Apply the same rule to unsupported pin/file predicates.

**Stable merging** should favor clarity over an invented blended score. Key messages by workspace/channel/ts; keep source provenance and freshness. Deduplicate before grouping. Newer edits and deletion tombstones take precedence over stale snippets; search responses must not overwrite fresher synchronized messages.

Paint up to three initial matches in a fixed “On this Mac” section, ranked by FTS then timestamp and identity. Freeze its membership for this query. Append a separate Slack section in server order, omitting duplicates already shown above. The sort control describes the Slack section; the local section is explicitly a shortcut, not the top of one global ranking. This costs vertical space but avoids both row jumps and pretending incomparable scores are equivalent. In offline mode, expand local results with their own paging. Refresh explicitly starts a new snapshot; preserve selected identity and scroll anchors where possible.

Fetch Slack pages sequentially, initially 50 messages, using returned page metadata. “Load more” requests one page; do not scrape until enough distinct threads appear. Keep loaded groups in place, update their counts without expanding them, and append new groups. A later stronger match cannot replace the group’s visible excerpt until refresh. Counts say messages returned or matches loaded, never claim a global topic total. Page-number pagination is not a snapshot: concurrent edits/inserts can cause omissions despite deduplication. Expose Refresh and avoid claims of completeness.

Each request carries session ID and query generation; cancel superseded work and reject late responses regardless of cancellation. Distinguish network/auth/rate-limit failures from zero results. Route reads through the existing queue and honor Retry-After.

**Tab state** belongs outside mounted components. Add `Place = { kind: 'search', sessionId }`; place equality uses session identity, so separate searches do not unexpectedly focus one another. A workspace-scoped session holds query draft/committed query, selected message, expanded groups, focus, pane width, list/reader anchors, and loaded-page references. Pure UI state lives in state atoms; execution and bounded result snapshots belong to the engine/cache store.

Submitting a changed query creates a history entry; typing and preview selection do not. Filter acceptance commits once. ⌘⇧T restores the session during the app run. Persist active sessions and recent/saved queries in user.db, including query and anchors but not result bodies. Today only the active Place survives restart; extending restoration must explicitly restore its referenced search session. Rerun on launch, label cached data, and restore a selected message only if still accessible. Five mounted tabs must not limit state survival. Use the generic tab title “Search”; protect queries, snippets, and summaries in privacy mode.

**Index investment:** existing messages already have channel, sender, thread, and timestamp columns. Add measured composite indexes for sender/date and date-only filtering; retain channel/thread indexes. Keep FTS over message and integration text; audit prefix-index configuration because the later integration migration recreates FTS without the documented prefix setting. Add normalized link, mention, message-file, and thread-participant relations as supported filters require them, maintained transactionally through edits/deletes. File search needs filename/title/type/owner plus message associations; file contents require separate extraction and coverage. Defer that extraction. Do not duplicate names into every message or add trigram/vector indexes without evidence. Try existing name matching first; trigrams help substrings, not meaning.

AI remains asynchronous and optional. After a pause, one cached structured call may propose filters, with an approximately one-second deadline; failure leaves literal search intact. Never rewrite operators already supplied. “Summarize thread” runs only on request against fetched, identified messages; use an eight-second initial deadline, cache by content version, and retain the reader on failure. For question-shaped queries, offer “Answer from results,” not an automatic expanding answer. Every factual claim needs a clickable message citation; incomplete retrieval must be stated. Generation costs scale with bounded evidence, never every keystroke. All obey AI-off and spend limits.

Defer semantic recall until lexical failures are measured: opt-in embeddings over cached thread chunks could help vague memories, but cannot search uncached history and introduce storage, deletion, provider-privacy, and incremental-index costs. Defer AI near-duplicate suppression: similar wording can contain opposite decisions. Automatic answers, confidence percentages, hidden query changes, reply drafting, and subscriptions that generate alerts would add noise rather than improve search.

Keep p95 local results within 100ms and FTS within 20ms at 100k messages under backfill. Cached preview: 50ms, prefetched preview and mounted tab switch: one frame. Start Slack after 400ms idle or immediately on submit; the recorded 300–540ms network time is evidence, not an SLA. Show loading text only after 300ms. Prefetch local neighbors only; fetch remote context after deliberate selection settles. Lazy-load Search and stop hidden-tab work.

Before implementation, verify read-only against Slack: identity syntax and duplicate names; operator combinations/exclusions; date boundaries/timezones; `with:`, saved/pinned/file semantics; explicit score sorting; page limits and moving pagination; archived/non-member access; inherited Slack search preferences; files endpoint; thread routing and match highlighting. Keep only timings, counts, and redacted shapes. Public `search.messages` documentation does not prove internal `search.modules.messages` behavior. Test stale responses, offline recovery, paging duplicates, privacy, keyboard focus, read-state preservation, and eviction/restart restoration against fake Slack. No live Slack checks were run for this proposal.

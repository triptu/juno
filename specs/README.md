# Juno sync protocols

These specs describe the protocols and their limits. They do not certify the application code. Only the model checks are tests here.

`follow.qnt` models the current follow command seam, two threads inside the quiet window, and one older thread. It includes Slack writes, socket delivery, HTTP pages, boot and hourly window passes, shorter reconnect reads, and activity lookups. Its `followProtocol` module takes constants; `follow` supplies the full simulator instance. `readstate.qnt` models read state as implemented in M4: Main and one followed thread that mirror, and one unfollowed thread that stays local. Its `readProtocol` module takes constants; `readstate` supplies the full simulator instance and `readstate-bounded.qnt` a small one. Like follow, it keeps Slack's event clock and Juno's observation clock apart. `outbox.qnt` models message sends, ambiguous failures, restart recovery and reconciliation, and edits, deletes and reaction toggles on Juno's own posts. Its `outboxProtocol` module takes constants; `outbox` supplies two draft IDs. `catchup.qnt` models messages that other clients post, edit, delete and react to while the socket is down, and the recheck after the reconnect; `catchupProtocol` takes constants and `catchup` supplies three messages.

## Follow rules and assumptions

- Values are `1` (followed), `0` (unfollowed), and `-1` (Unknown: no row). Unknown remains distinct from false. A root with `subscribed: false` does not create a row for an unknown thread; a root without the field changes nothing. A failed first Subscribe that finds false forgets its temporary row. Socket events with an explicit flag can create a row.
- `eventClock` supplies Slack event stamps and server-write order. `clock` supplies Juno request and observation times. No rule compares the two. Events apply when their stamp is at least `updatedEvent`; pages apply only when requested strictly after `observedAt`. A command stamps `observedAt` when it starts and again when its call ends (`acknowledge` or `reject`), but does not advance `updatedEvent`. An undated event queues a root lookup instead of writing a flag. A row a command wrote is `commanded`: an event stamp cannot be ordered against the command, so an event that contradicts such a row queues a root lookup instead of applying.
- Each thread has at most one pending command. Its intent stays visible. Eligible events and pages while pending only set `noted`; they do not advance either watermark. A success removes the pending row and, if noted, queues a fresh root lookup. The lookup can finish after other observations. Overlapping commands during that refresh, crashes and persistence are outside the model.
- There is no automatic command retry. An error, including a lost response after Slack accepted, ends the pending row and queues a fresh root lookup. When that lookup fails too (`failLookup`), the row keeps the command's state and the lookup stays queued, so it is tried again; the previous row is never restored without Slack's answer. The old fallbacks that restored it remain as bug modes (`restore`, `blind`).
- Boot and hourly passes page back to the quiet window. After those pages, they look up stored follows in range that were not listed and were not observed since the pass began. An omitted view row never means false by itself. Reconnect reads only the recent range and never probes its omissions. Thread 3 starts outside the window; another user's reply makes it active and queues a lookup if its stored follow is stale. An inactive old follow may remain stale indefinitely. A user's own reply follows on Slack and supplies an observation unless the local row already says followed, matching `followOnReply`.
- Fixed one-thread page slots represent a capped list spanning multiple pages. They abstract cursor movement, membership and request lanes. A thread that moves ahead of a real cursor can be missed until a later quiet pass. The model assumes all three conversations are members. It does not claim that a reconnect or an arbitrary moving pass establishes global agreement.
- `age` abstracts an observation becoming older than the quiet window; a fresh command, event or applied page clears that condition. The full instance holds at most eight socket events and two HTTP responses. Events can be delayed and reordered; disconnect drops queued events. HTTP responses can survive disconnect. A command acceptance need not have a socket echo. Fetches can return their request-start snapshot.
- `seal` stops new input and failures. An unfinished pass cursor is set aside; its queued responses still complete. Delivery settles before the next due window pass. That pass uses real snapshots and absent-root lookups; it does not assign agreement by definition. Roots then supply explicit flags. Connectivity recovers, and the hourly pass eventually runs. These are convergence assumptions, not evidence that Slack always behaves this way. A permanently missing field or failed lookup has no convergence promise.

The four reported differences are intentional protocol changes: separate clocks, failure lookup instead of retry, Unknown, and window-limited recovery. The three guards that keep an accepted Unsubscribe (stamp at the command's end, look up a contradicting event on a commanded row, keep the state when the lookup fails) are part of the protocol; each has a bug schedule that switches it off.

The follow drain covers three pending calls and their refreshes, eight events, two responses, reconnect, three window pages and three absent-root pages. Raising queue or topic limits requires revisiting the budgets.

## Read rules and assumptions

- Pointers are `0`, `1` and `2` (latest); `unread` is the Mark as unread flag. Main (1) and a followed thread (2) mirror; thread 3 is not followed and its marks stay local. Mirroring off is not a separate instance: it makes every topic's marks local like thread 3's, while Slack's changes still arrive under the same rules.
- `eventClock` stamps Slack's writes and events and orders events only (`updatedEvent`). `clock` stamps Juno's marks, their ends, event arrivals and fetch requests, and orders fetches only (`observedAt`).
- A mark (`localChange`) changes the pointer at once. A mirrored topic gets one pending row whose intent the next mark replaces (`gen`); `accept` sends the current intent and Slack may or may not echo it; `respond` ends the row unless the intent changed, records Slack's pointer (`slackSeen`) and stamps `observedAt`. `retry` is a lost answer or transient error after acceptance; `reject` is a refusal, which forgets `slackSeen` and asks Slack.
- While a mark is pending, an event or fetch that disagrees with it is only `noted`; Slack is asked when the row ends. After a topic's first mark (`commanded`), an event that contradicts the pointer asks Slack instead of applying.
- A fetch (`page`, `scan`, `lookup`) applies only when requested after `observedAt` and when its value differs from `slackSeen`. A fetch too old to apply that disagrees with the pointer asks Slack again.
- `disconnect` drops queued events; `reconnect` refreshes every mirrored topic (`scan`). Thread marks made elsewhere during a drop on a thread with no new reply wait for the next window pass in the code; the model assumes the reconnect refresh covers them.
- `seal` stops input and failures. Queued work completes.

## Outbox rules and assumptions

- `send` creates one durable `queued` row per draft, keyed by `client_msg_id`. Each ID is new and belongs to Juno. The model tracks row states `queued`, `sending`, `unknown`, `failed` and `gone`. Gone means no pending row. Slack stores a count per ID; the local mirror stores a set. The model gives Slack no deduplication guard. Each `accept` increases the count, so a repeated post is observable.
- `resend` is the network, not Juno: Chromium sends a request again by itself when a reused connection closes before any answer (ADR 0014). It applies to an accepted post whose answer has not come back, and Slack runs it again (`dup`). `held(k)` is what Slack holds: Juno's accepted submissions, plus network copies, minus deleted copies. **Assumption:** at most one network copy per post (Chromium's limit is about two; one is enough to show the rule, and the rule does not count copies).
- `observeCopy` is Juno storing a second message with a sent post's ID, by the same user (`@juno/sync` `sent.ts`): an echo, answer, page or lookup shows it. The first one stored is the message. The second is hidden in the same transaction and gets a `delete` outbox row (`copyRow` `hidden`). `deleteCopy` is that row's `chat.delete`; like the other action calls it is repeated after a lost answer and `message_not_found` counts as done, so only its success is modelled. `deleteCopyWith(k, false, _)` is the bug that matches by text instead of by ID.
- `kept` is which message Juno keeps: the first it stored, or the copy once the first was deleted elsewhere. `remoteChange` is another client changing Slack while the copy's delete waits: the user deletes the kept message on another device (`gone`, only while a copy is in Slack, since the user sees two), or someone replies to the copy (`reply`). Its event is stored in the same step while the socket is up (`seen`); otherwise the catch-up's recheck stores it. `deleteCopy` checks the store again just before the call (`check` `full`) and, after a socket drop, waits for the catch-up (`inStep`). When the check fails, `keepCopy` ends the row unsent and shows the copy (`copyRow` `kept`); if the kept message was deleted, the copy becomes the message. Reactions from others and an edit on the copy follow the reply's rule and are not modelled apart. **Assumption:** the time between Slack applying another client's change and Juno storing its event, and between the check and Slack applying Juno's delete, is not modelled. A change in that window can still race the delete.
- Repeats of action calls by the network need nothing new: the model already lets Slack apply an action call and then sends it again (`actAccept`, `actFail`, `runAction`).
- `claim` persists `sending` before one HTTP request leaves. These are one model action with a crash boundary after persistence. A crash before the call leaves is the dropped branch of `crash`. There is no HTTP retry. `accept` decides the request and may queue an echo. `refuse` decides a permanent refusal, 429 or signed-out response without posting. `refused` makes a permanent refusal `failed`; 429 and signed-out responses return the row to `queued`, due later.
- `lost` models a timeout, lost answer or undecodable answer. **Assumption:** Slack has accepted or dropped the request by the time Juno observes the failure. The request is no longer in transit. A lost refusal answer is also ambiguous to Juno and uses the same lookup. Retrying after an incomplete or stale negative lookup has no safety guarantee.
- `crash` models an engine restart at any time. It retains local storage, changes every `sending` row to `unknown`, and loses all HTTP answers, including page and lookup answers. Previously accepted messages remain on Slack. For requests still in transit, it chooses accepted or dropped before recovery starts. This extends the failure assumption to restart recovery: the old request cannot be accepted after a complete negative recovery lookup. Without that assumption, lookup before retry cannot guarantee at-most-once sending. A restart alone does not disconnect the socket in this model; `disconnect` represents that separately.
- `lookup` starts only for a due `unknown` row and returns a complete recent-history snapshot for its ID. Found stores the message and deletes the row. Absent returns a still-unknown row to `queued`. A concurrent reconciliation can already have deleted the row; an absent lookup never recreates it. `failLookup` leaves the row unknown. `wake` abstracts backoff ending. The model assumes history is complete for these recent draft IDs, and messages are not deleted or edited remotely.
- `writeMessage` stores the message and deletes its pending row in one transaction. The answer, `echo`, and positive history, replies or lookup results all use it. It is safe when the row is already gone. `page` captures Slack's snapshot when requested and can finish later. An absent page changes nothing. Two response slots bound pages and lookups together. Echoes can be absent, delayed or reordered across the two IDs. `disconnect` drops queued echoes; HTTP snapshots survive a socket disconnect. Repeated positive writes are idempotent.
- `retry` and `discard` apply only to `failed` rows. Discard records the user's choice and deletes the draft.
- `queueAction` is an edit, delete or reaction toggle on a draft's message. The model has two kinds: `change` (an edit or a reaction toggle) and `delete`. Each message has at most one action row (`act`): `waiting`, `transit`, `accepted`, then `done` or `dropped`. On a `queued` or `failed` post nothing goes to Slack: an edit rewrites the row's text, a reaction on a failed post is refused, and a delete removes the row and counts as discarded. On a `sending` or `unknown` post the row depends on the post (`depends_on`). On a stored message it carries the message's ts. A newer action replaces a waiting row. A delete replaces a pending change. While a call is out, a newer action marks the row `stale`, and the answer then sends again instead of ending the row. Nothing follows a pending or finished delete.
- `runAction` resolves the ts from the stored message with the draft's `client_msg_id` and sends one call. It runs only when that message is stored. While the post row exists and is not failed, a dependent action waits. `dropAction` ends a waiting action without a call when its post is `failed` or gone without a stored message (discarded). On a failed post a dependent delete discards the row; a dependent edit goes into the row's text and a reaction ends.
- **Assumption:** action calls are idempotent as Juno uses them. An edit sets the text. A delete of a missing message answers `message_not_found`, which counts as done. `already_reacted` and `no_reaction` count as done. So `actFail` (a lost answer, timeout or rate limit, before or after Slack applied the call) returns the row to `waiting` and the call goes out again, unlike a post. `crash` does the same for action calls in flight; the rows persist. `actRefuse` ends the row, and the view shows the stored message again.
- `actAnswer` stores Slack's answer as the socket event would and ends the row in the same transaction. The model does not track message text or reaction counts. It tracks only which messages had calls sent (`actSent`) and which Slack applied (`acted`).
- Outside this model: edits, deletes and reactions by other clients, reactions on other people's messages, the reaction row's `want` and `base` fields (an add and remove pair that cancels is a row that ends with no call), the bytes of attachment uploads (only their refusal, `uploadFail`, is modelled) and other outbox kinds.
- Socket connectivity and HTTP availability are separate. `goOffline` also disconnects the socket; `goOnline` restores HTTP access. The workers claim a post, start a lookup and run an action only while Juno sees the socket connected (`connected`), so a send made while it is down stays `queued` even when HTTP happens to work, and goes after `reconnect`. `claimWith(k, false)` is the bug mode that claims anyway. `reconnect` starts catch-up pages for the created IDs. `catchUp` ends that pass and makes every remaining `queued` or `unknown` row due. This models the catch-up's outbox flush. It does not infer absence from a catch-up page.
- `seal` stops new drafts, user actions, failures, crashes and disconnects. Already decided refusals and dropped calls still finish. Connectivity recovers, backoff ends, and workers and deliveries run. New requests succeed after sealing. With two drafts, two action rows and two response slots, this drain has a 48-transition budget. A random run with a 24-transition budget also passed. The bound counts productive model transitions, not wall-clock time or idle scheduler steps.

### Outbox bug schedules

Each `<name>Step` checks `invariants` and must finish its drain. Each `<name>BugStep` must violate the named property. Syntax, runtime and checker failures never count as counterexamples.

| --- | --- | --- |
| `blindRetry` | Accept without an echo, lose the answer, then look up the ID. The bug returns directly to queued and posts again. | `atMostOnce` |
| `crashResend` | Accept without an echo, crash before the answer, then look up the ID. The bug recovers sending as queued and posts again. | `atMostOnce` |
| `echoKeepsRow` | Deliver the echo before the answer. The bug stores the echo without deleting the pending row. | `noDoubleShow` |
| `answerAfterEcho` | Deliver the echo, then the answer. The bug writes the worker's old sending row back after reconciliation. The guarded answer leaves a deleted row gone. | `noDoubleShow` |
| `actionBeforeStore` | Queue an edit while the post is sending. The guarded edit waits until the answer stores the message, then runs. The bug calls at once with a guessed ts. | `actionNeedsMessage` |
| `actionOnDiscarded` | Queue an edit while the post is sending, then the post is refused and discarded. The guarded edit ends without a call. The bug calls anyway. | `noActionOnDiscarded` |
| `offlineSend` | The socket drops, then a send. The guarded worker waits for `reconnect`, then posts once. The bug claims the row while the socket is down. | `sendsWaitOffline` |
| `networkCopy` | Accept with an echo, then the network resends, so Slack holds two. The answer stores one; the echo of the other arrives. The guarded reconciler hides it and deletes it. The bug lists it. | `shownOnce` |
| `sameText` | Two drafts with the same text, each posted once. The guarded reconciler matches by ID and deletes nothing. The bug matches by text and deletes the second. | `keepsRealSends` |
| `keptDeleted` | Slack holds the post and its copy; the copy's delete waits, and the user deletes the kept message on another device. The check keeps the copy and makes it the message. The bug, deciding only at store time, deletes it too. | `keepsRealSends` |
| `copyReply` | Someone replies to the copy while its delete waits. The check keeps the copy. The bug deletes it. | `repliesKeepRoot` |
| `deletedOffline` | The socket drops while the copy's delete waits, and the user deletes the kept message meanwhile. The guarded delete waits for the catch-up, whose recheck stores the deletion, then keeps the copy. The bug checks the store at once on the reconnect and deletes the copy. | `keepsRealSends` |

The corrected `echoKeepsRow` and `answerAfterEcho` schedules cover echo before answer. Corrected `blindRetry` covers a lost answer followed by a found lookup. Six additional corrected schedules cover `answerBeforeEcho`, `lostLookupAbsent`, `reconnectPage`, `dependentDelete`, `actionRetry` and `uploadRetry`. The absent case drops the first call, loses its answer, confirms absence, and posts once. `reconnectPage` accepts, loses the answer, disconnects, then reconnects and holds a lookup answer. A catch-up page reconciles first, the catch-up flushes, and the lookup answer safely writes the message again. The seven post schedules cover all five delivery and recovery orderings. `dependentDelete` queues a delete while the post is sending; the post is refused and the delete discards the failed row. `actionRetry` edits a stored message; Slack applies it, a newer edit arrives while the call is out, and the answer is lost. The worker sends again and the row ends. `uploadRetry` refuses a post's upload, retries it, and shares the post with an answer that has no message, so the lookup stores it.

## Catch-up rules and assumptions

- Another client posts (in ts order, so a later key is a later ts), edits (a new version), deletes, and toggles a reaction on messages 1 to 3. Each change has a stamp from one clock and an event; `disconnect` drops queued events and nothing is sent while the socket is down. The code compares Slack's event ts with Juno's request ts the same way.
- `deliver` applies an event as `events.ts` does: a post stores the message, an edit takes the newer version, a delete is a tombstone that always wins, and a reaction change applies when its stamp is newer than the message's `last_event_ts` (`jStamp`).
- `requestPage(false)` is any fetch of the conversation (an opened topic); `requestPage(true)` is the recheck, due after `reconnect`. A page is Slack's state at the request (`requestedAt`) and lands later; HTTP answers survive a drop. `finishPage` merges it: newer versions apply, and its reactions apply to messages whose `jStamp` is older than `requestedAt`.
- The recheck page records the messages the store held at the request (`known`); a known message missing from the page is deleted (`knownGuard`). Other pages infer no deletion. The recheck is requested only when no other fetch is in flight (`waitGuard`): the code runs rechecks one at a time under the work permit and waits for the opened topics' and roots' fetches requested before it (`awaitEarlierFetches`).
- The model's pages are complete for all three messages: the recheck's topic limit and lookback are outside it, and so is a page's span (`has_more`). `seal` stops new changes and drops; the drain bound is 32 transitions.

| Quint name | Plain meaning |
| --- | --- |
| `noFalseDelete` | Juno shows a message as deleted only when Slack deleted it. |
| `quietAgreement` | Once quiet after `seal` (connected, no recheck due, no events or pages left), every message Juno holds is deleted as in Slack, or has Slack's version and reaction. A message posted and deleted while the socket was down may never be stored. |
| `drainBound`, `reachedAgreement` | As for the outbox. |

| Schedule | Ordering and guard | Broken property |
| --- | --- | --- |
| `newerThanPage` | After a reconnect the recheck's page is requested; a new message is posted and its event stores it; the page lands without it. The guard deletes only messages known at the request. The bug deletes the new message. | `noFalseDelete` |
| `dropChanges` | An edit, a reaction and a delete while the socket is down. The guarded reconnect rechecks and Juno agrees with Slack. The bug reconnects without the recheck, the gap Juno had before M7: the old text, the old reaction and the deleted message stay. | `quietAgreement` |
| `olderPage` | An opened topic's page is requested, the socket drops and the message is deleted. The guarded recheck waits for that page, then finds the message gone. The bug asks at once; the older page lands last and brings the deleted message back. | `quietAgreement` |

The random simulation (10,000 traces of at most 160 transitions) found two forms of the `olderPage` race before the wait was added: an opened topic's page, and an earlier recheck's page, landing after a later recheck. Four seeds of 10,000 traces each pass with it. `pnpm specs:check` runs the random traces and the three pairs with the other protocols.

## Conversation metadata

`metadata.qnt` models name, membership and archive fields, socket observations during a snapshot, and full refresh after a gap. `staleRename`, `staleMembership` and `staleArchive` each disable the observation fence in their broken mode and violate `eventWins`. `missedRename` disables the gap refresh and violates `quietAgreement`. Every corrected schedule must reach `reachedAgreement`. The runner also samples 10,000 random traces of at most 160 transitions; after input stops, recovery has a 16-transition drain bound.

The model serializes snapshot reads, matching the sync work permit. As with M7's older-page guard, an older read must finish before a later refresh can start. Events update the store and record the affected fields atomically. The implementation retains per-read patches until success, failure or interruption; it compares no Slack timestamp with a local timestamp. Membership snapshots cover absent members as well as listed ones. A rename leaves unrelated snapshot fields eligible to refresh.

Assumptions: a successful full snapshot covers the relevant conversations, events are applied in socket order, and connectivity and reads eventually recover. Event creation and delivery are collapsed into one action; delayed or reordered events and local commands are outside this model. HTTP snapshots can survive a socket gap. This is simulation and directed regression coverage, not an unbounded proof.

## Accepted Unsubscribe: three races and their guards

Each race is a directed schedule with a fixed mode (`<name>Step`, must satisfy `invariants`) and a bug mode (`<name>BugStep`, must violate `acceptedUnfollow`). The bug modes are the rules Juno had before the guards.

`lateEvent` (`accepted-unsubscribe-late-event`): `officialFollow(1, 1)` creates a followed event at Slack stamp 1 and its delivery is delayed; `unsubscribe(1)`, `accept(1)` and `acknowledge(1)` follow, with no echo. The delayed event passes the event watermark (`1 >= updatedEvent = 0`). In bug mode it applies and local becomes 1 while Slack says 0. The guard: the row is `commanded` and the event contradicts it, so it queues a root lookup, which reads 0. This can happen on an ordered socket too, since a command need not have an echo.

`pendingPage` (`accepted-unsubscribe-pending-page`): `unsubscribe(1)` writes local 0; a page starts while Slack still says 1; Slack accepts and Juno acknowledges; the page completes with 1. Its request started after the command's first stamp. In bug mode it applies. The guard: `acknowledge` stamps `observedAt` again, so the page is older than the row.

`failedLookup` (`accepted-unsubscribe-failed-lookup`): `unsubscribe(1)`, `accept(1)`, then `reject(1)` for the lost response, then `failLookup(1)`. In bug mode the compare-and-swap fallback restores the previous follow although Slack says 0. The guard: the row keeps the command's state and the lookup is retried; under `seal` it succeeds and reads 0.

The stale-page regression (`stale-follow-page`) is the older race: a page requested before the command. The command's first stamp stops it; its bug mode has no page guard at all.

## Juno Agent memory (WP2)

`agent-memory.qnt` describes [plan v3](../docs/juno-agent/plan-v3.md), sections 3–5 and 15. It is a protocol contract for the future implementation, not a claim about existing application code. `memoryProtocol` supplies every transition; `agent_memory` supplies the simulator and directed schedules, and `agent_memory_bounded` supplies the small Apalache instance in the same file.

### Records, transactions and abstractions

- A durable inbox count precedes ordered projection into a dense archive. A source ID denotes an immutable opaque byte string. Redaction replaces its payload with a tombstone without reusing the ID. Each ID represents one chunk, up to 16,000 bytes; attachment storage and byte-page iteration are abstracted by that exact payload. Archive incarnations and two-journal power loss belong to WP4.
- Tree keys are aligned `(start, width)` intervals. Immutable node versions record source IDs, exact child versions and raw context source IDs. `deps` caches the transitive source closure of those recorded reads. The separate `read` field records what the job actually saw, so a missing dependency is detectable. Model output may omit every fact, copy a read source, invent a fact, exceed 512 bytes, or fail. Provenance is conservative even when the output omits a source. Nothing here proves recall, factual accuracy, or instruction authority.
- `start`, `complete`, and `publish` are separate transitions. New messages, pin edits, removal and crashes can intervene. Publication revalidates inputs, the live cutoff, redaction generation, then reads the current head revision in the same transaction as node insertion and head advancement. Stale results leave durable work queued. A crash loses jobs and request preparation but preserves the archive, queue, deadlines, pins and exact committed head.
- The persisted head names exact node versions, ordered lines, a coverage watermark and a generation. Masked lines retain their intervals and render a fixed placeholder. The tail is everything after the published prefix. Out-of-order completed leaves wait until the prefix reaches them. Only sibling lines with a clean built parent can merge. Priorities use integer cross multiplication, age from the pair's inclusive last message, and oldest-start tie breaking.
- A compaction reads raw archive sources before its interval, newest first, stopping before the first source whose size plus framing would exceed 16,384 bytes. Removed sources are skipped. Context IDs are recorded and have no transitive inputs. Compaction reads no pins. Direct compaction input is at most 32,768 bytes; all compaction calls also pass an admission bound. The model keeps the shortest of at most five output attempts. A stored node is at most 16,384 bytes: oversized leaves copy their source, and oversized parents cut their shortest attempt. A parent therefore reads at most 32,768 bytes. Compaction admission uses a 131,072-token model window. Each shortening call reuses the bounded original input and fixed template, revalidates freshness, and passes the same provider bound; it does not accumulate previous attempts into a transcript. Deadlines use two abstract clock ticks instead of the production backoff ladder; the clock and worker advance without new messages.
- Pins are trusted copies of an owner source span (at most 280 bytes) or explicit owner edits. Edits preserve source lineage and supersede the previous version. Admission enforces 4,096 active bytes atomically. A removal deactivates matching pins immediately, including owner-edited descendants; delayed edits recheck lineage. The span's integer payload abstracts exact byte slicing, not its implementation or UTF-8 validation.
- Removal increments the generation, masks precisely the affected published lines, queues affected node keys, removes pins, invalidates prepared requests and clears affected live report/retrieval handles in one transaction. Clean versions outside the dependency closure remain usable. Rebuilds get new identities; purge removes obsolete text-bearing node records. Local journal/Codex files, grant and action invalidation, backups and the 24-hour purge deadline belong to WP3/4/16. Already sent provider copies and independently stored later replies are outside this memory guarantee.
- Requests capture pins, head, generation and cutoffs in one snapshot. Historical coverage, tail and active source IDs partition the selected prefix. A large tail has **one** bounded range placeholder. Uncollapsed tail items keep their exact source payload. Active tool-result paging preserves IDs and metadata; a modeled call/result pair must stay ordered and paired. Request cost includes fixed system/tools/framing, a 16,384 output reserve, pins, view, tail and active input. The final result is admitted or locally blocked. The provider guard rechecks the generation and pin revision, a trusted stamp over the complete request, and the budget. Spend reservations belong to WP3.

### Memory bounds and plan clarifications

The simulator instance has ten possible source IDs and aligned widths 1, 2, 4 and 8. Random admission stops at four sources (seven possible built intervals); the ten-source fixture exists for the exact due-order witness. Worker capacity remains eight. View watermarks are reduced to 2,048/1,024 bytes so short histories exercise batching; pin, context, input, tail, active and output-reserve limits keep their production byte values. Random model outputs are 512, 2,048, 8,192 or 20,000 bytes, with arbitrary provenance subsets and an invented marker. This exercises both soft-target failures and the hard cut/copy cap.

The runner takes 1,000 samples of up to 140 transitions with seed `20261013` and two simulator threads. Directed schedules take at most 80 transitions. The 28 corrected schedules share one 512-sample run; the runner requires a completed witness for every case, so a missing sample is a failure. Each broken schedule runs separately and writes its own counterexample. This avoids paying checker startup twice for every pair. A 64-transition drain covers up to seven pending intervals, outstanding/stale jobs, retry deadlines, projection, ordered publication, removal rebuilds, purge and feasible merges. It assumes no new inputs, edits, crashes or failures after `seal`; successful draining outputs are 512 bytes. Quiet recovery is exercised through the actual worker actions. A positive directed trace must end with `label = finished`.

Apalache uses two sources, two workers and the same actions. It checks archive projection, removal, queue durability and restart (`boundedSafety`) for four transitions. Separate broken/corrected `boundedRace` schedules check the six-transition `redactionRace` through the same worker actions. The symbolic schedules omit the general string-command decoder. Quint otherwise sends type metadata for unused declarations and exceeds Apalache’s 20 MB JSON-string limit. The runner uses the pinned Quint compiler in a timed child, retaining only analysis metadata whose IDs occur in the compiled main module. It leaves the compiled module, expressions and types of all live IDs unchanged before calling the normal Apalache backend. No transaction is replaced by a proof-only action. These are shallow bounded checks, not exhaustive verification of every invariant. The simulator covers requests, pins, context closure, batches and longer recovery schedules. `pnpm specs:check --memory` selects these checks during development; the ordinary `pnpm specs:check` includes them with the existing sync checks. `pnpm specs:check --memory --bounded` reruns only the memory symbolic checks. ## Juno Agent actions (WP3)

`agent-actions.qnt` models plan v3 §§6 and 15. `actionsProtocol` supplies the shared transactions; `agent_actions` uses two child actions and `agent_actions_bounded` one. WP15 implements it in `packages/agent/src/{actions,grants,policy}` (see that package's README, "Actions"); the code is tested against the same rules, not verified by this model.

Intents, clicks, consumed authorizations, attempts and receipts are distinct durable records. Executable identity is the complete `Payload` record: connection, account, destination, tool, schema, canonical arguments, precondition and ordered operations. Equality abstracts collision-free JCS hashing. Fresh integer identities stand for globally unique UUIDs, not a shared cross-device allocator; UUID generation itself is outside the model. Edits append immutable revisions. A batch click stores the exact ordered child intents and expands child approvals with a shared batch ID. Authorization checks that expansion against the stored order; each child retains its own consumed authorization and outcome. `batchOrderRace` rejects a reordered expansion. The card preview is assumed to render the stored payload; this spec cannot check pixels or serialization.

`authorizeDispatch`, `transportSend`, `destinationAccept` and `recordReceipt` are separate. A consumed authorization permits one handoff. A crash before handoff still becomes unknown at startup. A negative lookup explains the uncertainty without clearing it. A card runs once: a child whose destination does not deduplicate is authorized at most once (`noRepeatAuthorization`), whatever its first attempt's outcome, because the chat offers no retry (plan v3 O2). A deduplicated child may be authorized again under its key; no v1 card offers that. Deduplication is assumed only for the explicit local destination contract, with stable payload and destination-scoped key for the entire modeled history; it is not asserted for Slack, T3 or generic MCP. Remote traffic already authorized may complete after Pause. Cancellation cannot erase earlier success. Evidence is per attempt: success from an earlier attempt never hides an interrupted retry of the same child (`attemptEvidence`).

Grant scope includes target, operation class, source and revision. Reports and wakes taint a run. No-click grants require a clean owner run and a source in that run; later taint forces a card. The model includes revocation on Pause, removal and schedule deletion. A removal revokes only the grants whose minting run saw the removed content (the ghost `saw`, set by `see`) and carries the rest into the new generation. Resume (or AI assist back on) clears Pause and restores no grant: every live grant was minted since the last Pause (`pauseRevokesGrants`). A click that waited through Pause is authorized once after Resume, if it is still current (`resumedClickWitnessStep`). A persisted occurrence is keyed by schedule, revision and due time; admission and starting it both revalidate the live grant. Quiet hours gate notifications, not authorizations. All billable paths use one reservation ledger, kept per local day as WP9 keeps it; unknown spend retains its reservation on its day. Eight abstract cost units are the initial total cap, and a dollar is four units. Admission keeps compaction within 25% of the cap plus owner raises; chat may use the whole cap. Each call reserves two units, or zero for a free model. A settled reservation counts its true cost, compaction included; an open or unknown one counts its full amount. A day at or over its cap admits nothing. A ghost `charged` records what the provider billed, and `capHard` requires that no reservation records less than that. Random exploration settles with reported costs up to one unit above the reservation, refusals, and losses with any charge up to the reservation; it also raises the limit, starts new days and lowers the cap.

**Auto-review of connection tools (10-16).** A connection tool not on its read list (`proposeConn`, an intent with `conn`) may run with no click when the reviewer and the owner's rule allow it. The reviewer (`reviewWith`) is one decision-model call per intent revision; it answers how explicit the owner's intent was (`explicit`, `implied`, `notAsked`, or `failed` when the call failed or timed out) and whether the call can be undone. The owner's rule for the tool is `auto`, `always` (ask) or `never` (ask). Auto runs only an explicit, reversible review; Always ask never runs without a click; Never ask runs a call from a clean run, or one the owner's words at least implied. Each intent records whether its run was clean, and a ghost `cause`: `untrusted` when only text the run read asked for the call, which needs a tainted run. The reviewer sees only the owner's words, so it answers `notAsked` for such a call. `reviewGated` checks every no-click connection authorization against the rule and the review of that exact revision; `untrustedNeverAuthorizes` checks that none came from untrusted text alone, under any rule. Assumption: the reviewer's risk answer is taken as given; the code adds a floor (a tool or operation named like a delete is never reversible), which the model does not check. `allWritesGated` now names the three authorities a write may run under: a click, a Tier 2 grant, or a passing review of a connection tool.

All 25 named WP3 safety properties in §15 are in `safety` (the plan calls the original list “22” but replaces its quiet-hours entry). Relational checks read the actual ghost pre-state. They cover immutable intents; exact/current/consumed approvals; no hidden retry; no repeat authorization; uncertainty; stable dedupe identity and effects; receipt binding; grant scope and clean runs; destructive-operation refusal; all write paths; local ownership; Pause and off; notifications; schedules and occurrence races; independent children; evidence retention; and the hard cap. WP15 adds `pauseRevokesGrants`. WP16 adds `redactionRevokesExposed` and `redactionKeepsUnrelated`. Auto-review adds `reviewGated` and `untrustedNeverAuthorizes`. `currentOwnerAuthorizes` checks the local authority only. The stronger cross-machine claim is intentionally refuted by WP4.

## Juno Agent recovery (WP4)

`agent-recovery.qnt` uses `recoveryProtocol` for simulator, schedules and the bounded instance. Two local processes contend for one SQLite `owner.lock`; devices A and B have independent local ownership records. The model uses the S5 exclusive SQLite connection named in plan §2.2. Its handle stays strongly referenced until owned I/O stops. Process death closes it. Collection of an unreferenced connection and early shutdown are separate failure pairs.

Inbox admissions are authoritative before acknowledgement. Reset, journal submission, submitted marking, projection and crashes are distinct transitions. Stable operation IDs deduplicate a resubmission after a crash between pi submit and the inbox update. The serial bridge looks up the operation first and skips reset and submit if pi already holds it. A reset before resubmission would end a resumed tool round. A crash before the first submit can leave an extra idle reset, which is harmless. Projection appends the next entry commit and advances the incarnation's cursor atomically. Partials and task-state commits add no entries; their sequence numbers leave gaps and do not move the cursor. A drain means no entry commits remain after the cursor, not `cursor == nextSeq - 1`. The model represents an entry commit by one archive marker, not one message row. Reset transcript records and entry rendering are abstracted. In code, an entry commit can render zero or many messages/chunks and still advance the cursor. An entry's `(incarnation, position)` stands for archive, task and action-origin references. Rotation never reuses an incarnation or its cursor. Existing archive entries survive it; abandoned submissions remain interrupted. All Juno authority commits survive ordinary crashes. FULL here assumes the spike's macOS `fullfsync` and `checkpoint_fullfsync` settings; this is not a disk durability test.

A rolled-back journal is a separately injected older file. Juno reads `durable_metadata.next_seq`, treats the last committed position as `next_seq - 1`, and compares it with the same incarnation's archive cursor before resume. The spike stores an exclusive `next_seq` watermark in its test variable; production must compare the same convention on both sides. A journal at or ahead of projection resumes; a journal behind it rotates and interrupts submitted work. The file must also record the expected incarnation. Each authorization also raises the incarnation's authorized position to the journal's last commit (`authorizedSeq`), and a journal behind that rotates too. The cursor alone detects lost projected commits, not lost trailing pi state; the replay slice below checks why the authorized position is needed. Unsupported schemas stop without replay. `journalAheadStep` and `unsupportedSchemaStep` are explicit positive witnesses.

Cooperative transfer stops admissions, classifies unsettled attempts as unknown, drains projection and local I/O, commits local release, captures the final checkpoint containing that release, publishes release, then installs the successor at the next epoch. The successor reads the released artifact; it cannot read the predecessor’s current local ownership record. `cooperativeTransferStep` exercises that full drain. Restores use a fresh staging database and a new incarnation; approvals are void, pending work is quarantined, and attempts without receipts remain unknown. Review and owner attestation are separate from activation. Activation requires a completed staged install when restoring. Trusted deletion records come from the local keychain, a code-confirmed move or the current strict recovery phrase. Without one, Review discloses that the newest authenticated backup in the folder may restore removed content. `reviewedRestoreStep` witnesses a valid reviewed activation. Forced recovery does not pretend that the attestation shuts down the old machine: the two expected stale-owner counterexamples deliberately leave it alive. Their safe counterparts actually turn it off. Cooperative transfer is the alternative that does not depend on a false attestation.

Backup positions count captured data transactions; export bookkeeping does not recursively create another delta. Backup writes encryption output, publishes an authenticated manifest, then persists the export cursor. A segment is keyed by generation, exact from/to positions and predecessor hash. Integers abstract collision-free hashes; a Boolean abstracts successful authentication; a monotone nonce allocator abstracts fresh random nonces across crashes. Restore stages a gap-free chain and atomically installs only after rechecking the deletion generation. A manifest may arrive before its segment; that is a wait, not permission to skip a gap. Sanitized generation snapshots exclude removed sources and use a fresh generation key. Old keys can be destroyed only after the replacement snapshot is available. Cipher implementation, SQLite changesets, migrations, keychain atomicity, iCloud trash and the five-minute recovery-point service objective need implementation tests. No forensic or cloud erasure claim is made.

All ten WP4 names appear in the model. The nine achievable original properties are in `safety`. The two stated limits, `staleOwnerCannotAuthorize` and `staleFolderCannotRestoreRemoved`, are excluded from unconditional safety. Their expected failures are `partitionedOwnerBugStep` (also `epochReadRaceBugStep`) and `staleFolderBugStep`. Corrected and random runs use `cooperativeSafety`, which includes both. Additional invariants check retained lock handles and a held lock before local store writes, rollback-before-resume, bridge dedupe, export ordering, nonce uniqueness, release inside the checkpoint, stopping after observing a newer owner, uncaptured export bookkeeping, recording deletion before removal, sanitized snapshots and key availability.

### WP8 alignment

These verdicts apply to the code in `packages/agent/src/{runtime,store,inbox,projection,recovery}`. The specs model each departure as the code does it, with a bug schedule for the old rule.

1. **Cursor: safe with the spec change.** `commitsAfter` selects entry commits, and `projectCommit` commits archive rows, memory keys and the cursor together. `projectionPrefix` now compares ordered entry prefixes, using a ghost history that survives file rollback; it no longer equates a sequence number with a row count. `cursorGaps` projects positions 2 and 4, leaves a trailing state commit at 5, crashes, resumes and projects again without duplication. It then completes transfer with cursor 4 and `nextSeq` 6. The old equality drain stalls and violates `drainBound`. State-only commits also take part in random exploration. Drain still assumes the producer has stopped before the final checkpoint.

2. **Trailing-state rollback: unsafe as WP8 shipped it, fixed here.** `agent-recovery-replay.qnt` models pi's tool task as `harness/tool.js` in pi-durable 1.2.0 runs it. The call phase commits an execute intent, a state commit with no transcript entry, before `execute()`. On recovery, a call with an intent and the default `replay: "unsafe"` settles as interrupted; a call without one runs its call phase again. WP8 allocates a fresh authorization on every `authorize`.

   In `trailingState`, the model's tool call is projected (cursor 1) and a copy of the journal is taken. pi commits the intent (2), the tool authorizes and sends, and a receipt is recorded. The copy is then restored over the file. It lost only the intent, so `1 >= cursor 1` and WP8 resumed. pi saw no intent, ran the call again, and the tool obtained authorization 2 and sent a second time. `trailingStateBugStep` violates `authorizedOnce`, and the same trace violates `noRepeatedEffect`. The incarnation check does not help: the copy is of the same incarnation. Reusing authorization 1 could not send again (`replayUnknown`): the hole is the fresh authorization, not `recordAttempt`.

   **Fix.** `authorize` takes the journal position, read by the tool inside `execute()` after pi committed the intent (`Core.position()`). The same transaction raises the incarnation's `authorized_seq` to it, and refuses if the incarnation has been retired. Recovery rotates a journal whose last commit is below `max(cursor, authorized_seq)`, as it does for one behind the cursor. A resumed journal therefore holds the intent of every call that was authorized, and pi settles such a call as interrupted instead of running it again. `trailingStateStep` rotates with one authorization and one effect. `copyAfterIntent` restores a copy taken after the intent and resumes: the check is no stricter than it needs to be. The main recovery model applies the same floor in `openJournal`.

   This is the simplest safe option. Recording every pi commit in `agent.sqlite` would need a write per commit, and it still races: an effect can happen after the intent commit and before the watermark write. Binding authorizations to a stable call identity would need WP15's dispatcher and a key that survives a lost model turn. The authorized position needs one column, one update in a transaction that already exists, and one comparison at open.

   The fix rests on two conditions, each with a bug schedule. A tool with an effect must keep pi's default `replay: "unsafe"`; `unsafeReplayBugStep` declares it safe, and an ordinary crash then authorizes twice. The tool must read the position after the intent commit, that is, inside `execute()`; `earlyPositionBugStep` reads it one commit earlier and authorizes twice. The fix does not restore lost partials or other lost pi state, and it does not detect a copy of a different branch of the same incarnation that is ahead of the authorized position. Such a branch never held the authorized call, so it cannot run it again, but its own model turns may repeat reads and cost.

3. **Publication revision: safe with the spec change.** `publish` validates generation and the exact input digest inside `BEGIN IMMEDIATE`, inserts the node, then reads and advances the head in that transaction. Parallel jobs may start at the same revision and both publish. `parallelLeaves` refutes the old start-revision rejection; `casRace` refutes reusing that revision for the new head. `parallelRedaction` publishes one leaf, removes its source, then tries the other leaf whose raw context included it: the generation/input check discards the stale result. All existing taint, child-input, masked-view and stale-request invariants remain enabled. Job revisions in the model are diagnostic witnesses for the old rule, not a production job requirement. Separate model `extend`/`merge` steps abstract the view work that WP8 batches inside publication.

4. **Bridge reset: safe with the spec change.** `bridgeToolReplay` crashes after submission during a tool round, opens the journal, delivers the same op, marks it submitted and projects twice. The corrected path keeps the tool round, one journal admission and one archive entry. The old fresh-reset path violates `bridgePreservesRun`. `bridgeReplay` still refutes missing request-ID dedupe. This assumes WP8's single writer and serial delivery; it does not authorize concurrent reset calls or resets for a different op during a live run.

The agent checks now contain **113 broken/corrected pairs: 30 memory, 48 actions and 35 recovery** (31 main recovery plus four replay pairs). The `trailingState` trace checked against `noRepeatedEffect` is a second failure witness, not another pair. The replay suite samples 64 traces, requires all four final-state witnesses and checks every replay property in every corrected case. The main recovery suite still samples 1,024 corrected traces; the memory suite samples 512. Existing random runs, finite drains and 19 bounded checks remain. The replay slice is directed simulation only, not an exhaustive or unbounded proof. `packages/agent/test/recovery.test.ts` runs `trailingState` and `unsafeReplay` against the real core and pi.

### WP9 spend alignment

These verdicts apply to `packages/agent/src/spend/` and the settlement calls in `packages/agent/src/providers/guard.ts`. Each departure has a pair. `parallelBudget`, `unknownSpend` and `compactionBudget` still refute their bug modes, and the corrected model keeps `capHard` as restated below.

1. **Settled compaction counts its actual cost: safe.** The compaction sub-budget sums actual costs of settled compaction reservations and full amounts of open or unknown ones, as the `spend.snapshot` query does. `compactionSettle` reserves a compaction, settles it at one unit and is refused a second reservation (`1 + 2 > 2`). The bug mode forgets the settled actual, admits the second reservation and violates `capHard`.
2. **A refusal before output settles as a known zero: safe, if the provider does not bill such refusals.** The guard settles zero only when the request failed locally before it was sent, or failed with a rate limit or rejected key before any output. `refusedSpend` fills the day, settles one refusal at zero, loses a stream after output, and fits one more reservation in the freed space; the lost stream keeps its full amount. The bug mode settles the lost stream as a refusal; the provider charged it, and `capHard` fails.
3. **Daily reset and the once-per-click raise: safe.** A reservation belongs to the local day it was made on, and its settlement stays on that day. A new day starts at the default cap. `dailyReset` fills day 0, loses one stream, fills day 1, then settles a day-0 reservation: day 0 keeps the unknown amount and gains the actual cost, and day 1 stays full. The bug mode settles onto the current day and puts day 1 over its cap. `allowDollar` inserts one row per click id; `raiseClick` delivers the same click twice and gets one dollar. The bug mode counts both deliveries and violates `oneRaisePerClick`. `capHard` measures against one dollar per distinct click. Lowering the cap (`setCap`) is allowed below existing obligations. Random exploration checks that new reservations still obey the current cap; a ghost records removed allowance for earlier reservations.

**Over-report: the ledger keeps the true cost and stops admitting.** `settle` records the provider's reported cost, even when it is more than the reservation. The reservation prices input at the highest rate and output at the full output reserve, so this needs the provider to count more input tokens than the byte bound allowed; the guard then raises that provider's multiplier to 1.25 for later requests. Decision (WP11 implements it in `packages/agent/src/spend/`): the ledger never records less than was charged, and once the day is at or over its cap every new reservation is refused until the next day or a raise. `capHard` states what then holds: the ledger records at least the charge; no reservation is admitted while the day is at or over its cap (`noAdmissionOverCap`); and the day, and its compaction share, exceed the owner's limit only by allowance removed through cap reductions and costs reported beyond reservations. Only requests already in flight when the day filled can add to that overrun. `overReportStep` keeps the counterexample to the old rule `strictCap` (the cap is never passed): four two-unit reservations fill the day and one settles at three units, nine against eight. `overReportCap` continues that day: a two-unit and a zero-cost reservation are both refused; its bug mode admits them. `capReached` fills the day exactly and refuses a zero-cost reservation; its bug mode is the previous check, which only compared the sum and admitted it. Random exploration reports costs up to one unit above the reservation and includes zero-cost reservations. One limit remains: a stream whose usage is never reported keeps exactly its reservation, so the model assumes the provider billed it at most that. An over-charge on such a stream cannot reach the ledger.

## Background request pacing

`requestqueue.qnt` models independent method clocks, admission after a lane wait, and Retry-After with a doubled method interval. Its time units abstract the production intervals. `invariants` checks that dispatch never crosses a pause and a tier never becomes faster after a 429. The simulation does not model HTTP latency, lane fairness or Slack's actual limits; fake-server tests check the dispatch timestamps. Existing follow/read/catch-up models already permit reordered HTTP responses and make no fixed-spacing assumption.

`discovery.qnt` describes a partial search page with a root and reply, or a reply alone. Applying root metadata first avoids a lookup only in the first case. Search leaves reaction and follow state unchanged. The model abstracts the counters and lookup success; it does not prove search completeness or replace the merge tests.

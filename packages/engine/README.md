# @juno/engine

The engine: all of Juno's business logic and I/O, as Effect services in one Node program. It runs in Electron's utility process and under plain Node for tests and the web shell. See `docs/architecture.md` sections 1, 2.5 and 2.6.

`startEngine` accepts scheduling overrides in `options.timing`; `src/config.ts` holds the typed fields and unchanged production defaults. The unit harness uses a fast profile and observable work completion; see [test/README.md](test/README.md).

## What it owns

- `startEngine(transport, config, { host, httpTransport, agentTransport, agentWrites, notifications })`: builds the app layer, serves the RPC protocol, returns `{ stop, commandIdle, wake, setPresence, currentPresence }`. Services and the server come up before any boot work, so the first live query is answered from local state. `host` is the parentPort line to main (`memoryHost()` in tests); `httpTransport` is the Slack HTTP seam (`net.fetch` in the app, Node `fetch` by default); with `agentTransport`, the engine also serves the AgentHost group from `@juno/agent-contract` to the agent process on those ports (`src/protocol/agentHost.ts`, handlers from `@juno/agent-juno`, ADR 0012). `agentWrites` is `disabled` unless a test turns the agent's sends on.
- The protocol (`src/protocol`): the `RpcServer` over a worker-runner platform that accepts every port a `Transport` hands it, or the web shell’s `SocketTransport`, the serve helpers, and `HostLink` (`src/protocol/host.ts`), the service feature folders use to talk to main.
- Feature folders (`src/<feature>/`), each with its route handlers and services. `src/status/` is the worked example; `src/session/` owns the sign-in state, `auth.test`, sign-out, and `SyncRunner`, which runs `@juno/sync` inside the session's scope for every ready session; `src/topics/` serves `topics.list` and `topics.counts` from the open store and runs the `topics.subscribe` and `topics.unsubscribe` commands (top-level `follow.ts`, shared with notifications: one local transaction with a pending outbox row, the mirror to Slack, a root lookup after a failure or when Slack said something meanwhile, the undo in the result), and the topic actions (`../topicActions.ts`: `topics.resolve`, `topics.reopen`, `topics.pin`, `topics.unpin`, `topics.rename`, `topics.restore`, `channels.ignore` and `channels.unignore`, each one local transaction with its undo; resolve marks read through `marks.ts`); `src/messages/` serves the topic view (`messages.list`, `topics.get`, `channel.threads`) and runs `topics.open` and `messages.loadOlder` (see "The topic view" below).
- `src/search/` serves `search.query` over local FTS indexes for titles, messages, channels and people (ignored and non-member channels are excluded before the limit), `search.slack` through `searchMessages` in `@juno/slack`, and `search.command`: the grammar in `@juno/domain` first, then the `parseCommand` model task for text of three words or more. `src/prefs/` serves durable JSON preferences through `prefs.get` and `prefs.set`, and owns the durable emoji recency commands and the final picker ranking from local choices, Slack usage counts and quick reactions described in architecture section 7.
- `src/reads/`: the `reads.markRead`, `reads.markUnread` and `reads.mirror` handlers. The mark itself is top-level, because the topics feature marks too: `src/marks.ts` is one transaction that moves Juno's pointer, re-indexes the topic, clears the Reopened tag on a mark read and writes or replaces the topic's `mark` outbox row, with the undo in the result; `src/readCatchUp.ts` queues the one-time forward catch-up and exposes its progress; `src/readSetting.ts` is the `reads.mirror` preference, on by default for every workspace; `src/markWorker.ts` is `MarkWorker`, which sends pending marks to Slack with coalescing, backoff and lookups (architecture 5.6, specs/readstate.qnt).
- `src/send/`: sending and drafts (architecture 5.7, specs/outbox.qnt). `commands.ts` runs `messages.send` (a DM opened first for a person never messaged, then one transaction that queues the pending row and clears the topic's draft), `messages.retry` and `messages.discard`; `worker.ts` is `PostWorker`, which posts each queued row once through `Outbox.sendOnce` in the order sent per channel, settles a lost answer by looking the `client_msg_id` up in Slack, turns `sending` rows into `unknown` after a restart and flushes when a boot or catch-up ends (`SyncLink.caughtUps`); `drafts.ts` serves `drafts.get` and `drafts.set`. `messages.list` shows a topic's pending rows after its newest message (`messages/query.ts`).
- `src/aiCredentials.ts` holds main's OpenRouter key (`aiKey`) in memory; a change cancels provider calls under way and wakes the jobs (`aiWakes`). `src/aiSpend.ts` is `AiSpend`: every engine model call reserves its upper cost in the agent's daily cap over the AgentHost port and settles the reported cost; with no agent to ask, the call is blocked. A call under `AiBackground` (art for older topics, Home) asks as the backlog, which the ledger stops at three eighths of the cap. Custom chat endpoints do not change the engine's provider. `src/titleJob.ts` titles recent sidebar threads once Home is ready in the first sync (`home/ready.ts`), from the cache only, 2 calls at a time within 200 calls per workspace per day, skipping renamed ones. No topic needs to be opened.
- `src/art/` draws topic art (architecture 10, "Topic art"): `job.ts` is the background job (a debounced live query over the sidebar candidates without a finished attempt, newest first, 4 at a time, 500 calls per workspace per day, nothing while `aiAssist` is off), `draw.ts` builds one topic's input, calls `topicArt` and stores the attempt in `topic_art`, `handlers.ts` serves `art.redraw`, which returns the old `topic_art` row as an `art.restore` undo, and `art.restore`, which writes it back. Rows and headers get the recipes through `refs.art` and `TopicDetail.art`; the sidebar query joins `topic_art` in `topicRows.ts`.
- `src/home/` serves Home (SPEC 12; architecture 10, "Home"): `query.ts` reads the items from the cache (Tidy up also reads each proposal's last messages for its reason with `settledEvidence`, skips topics kept open, and follows the `tidyUp` preference; `reviewCards.ts` reads follow-ups that look done, each promise's later messages with `followUpDelivery`, and old drafts, `drafts` with `isOldDraft`; `suggested.ts` reads Mentioned, a direct mention in an ignored channel, and Unfollow and Ignore with `unfollowEvidence` and `ignoreEvidence`, its `suggestedStatements` in the plan test; `rows.ts` holds the row and clauses the queries share) (`home.view`, a live value; `homeStatements` are in the plan test), `job.ts` is the background job that stores `settledScore` and `followUps` answers in `ai_cache` and `follow_ups`, `assist.ts` holds the budget (300 calls per workspace per day) and the cached call, and `handlers.ts` serves `home.view` (asking `homeTitle` for the items shown while Home is subscribed), `home.visit`, `home.markDone`, `home.movesShown` (Automated's record was shown: wait a day), `home.movesSeen` (its moves were opened or dismissed), and the reviews' undoable `followUps.*` and `drafts.discard`, `drafts.keep` and `drafts.restore`.
- `src/socketEvents.ts`: `SocketEvents`, which hands each socket event to engine services after the sync's write attempt for it. A service subscribes in its own layer with a start that runs in each sync's scope, in a fiber of its own, while its queue already collects events; each subscriber has a queue of 1024 events, drained in order by one fiber. Publishing never waits: a subscriber that falls that far behind loses its queued events and gets `Overflowed` in their place.
- `src/notificationRuntime.ts`: the session-scoped notification job and host controls. `NotificationControl` subscribes it to `SocketEvents`, so it reads each event after sync applies it, detects mentions with the domain parser, watches notification prefs, ticks at local minute boundaries, and sends the dock badge while an eligible item is unread. `dockBadge.ts` makes an indexed existence query; `sidebarUnread.ts` shares the sidebar count eligibility and All exclusions with it. `dockBadgeActive` in the domain owns the badge policy and uses the alert decision. Unknown read state is held. `notifications.notifier` supplies OS delivery and focused-topic state; without it `hostNotificationHost` sends them to main over `HostLink`, and main's `viewing` and `wake` messages come back the same way. See `@juno/notifications` for delivery semantics.
- `src/notifications/`: the `notifications.*` routes: the settings, the page's lists and today's counts, every decision today for Details, the presence line, and the setters (levels, the Always notify switches, instructions). `notifications.setLevel` on a thread follows or unfollows it through `follow.ts`. `notifications.checkInstruction` asks `instructionRule` whether an added instruction is one person's or channel's level. `notifications.useJunoHours` writes the hours to Slack's schedule again after a change there.
- `src/slackSchedule.ts`: `SlackSchedule`, which writes the notification hours into Slack's own notification schedule (the `dnd_*` prefs) with `users.prefs.set`: on by default, once per change of the hours after a debounce, never when Slack already holds them, with Slack's previous schedule kept for Restore (architecture, "Slack's schedule").
- `src/ai.ts`: the `AiProvider` the engine runs, from `EngineConfig.ai` (`fake` or `live`) with the live config read from `aiModels` in prefs on every call, and `aiAssistOn`, the global switch. An input a model refused for good (`isFinal` in `@juno/ai`: its policy, a bad request, too long, no credits) is kept per task and key in `ai_refusals`, and the same input gets that refusal back with no call and no log row until it changes; a later answer for the key removes it. The title job also leaves a refused thread out of its candidates until it has activity after the refusal, and the art job stores such a refusal as a finished `failed` attempt. `src/aiFallback.ts` holds the fallback slug the agent sends over `host.ai.fallback` (Settings › Juno); until it does, `defaultModelPrefs.fallback` applies.
- `src/activity.ts`: `OwnerActivity` keeps when main last said the owner is at the Mac (`active`, from `powerMonitor`'s idle time); through `SocketEvents` it runs in each session next to the sync and sends a socket `tickle` on each one and on each connect, unless the presence is `away`. `SlackSocket` paces it to one per 19 s.
- `src/presence/` is presence as Slack shows it to colleagues (SPEC 7, "Presence in a DM"; SPEC 14, "Show who is active in the sidebar" and "Your own dot"). `OthersPresence` (`service.ts`) runs in each session through `SocketEvents`: it always follows the user, whose answer it keeps apart in `SelfPresence` (`src/selfPresence.ts`) for `notifications.status`; it reads the partners of the open 1:1 DMs (from `SyncLink`'s shown topics) and, while the `showPresence` pref is `true`, of the 100 DMs with the latest activity; it sends them sorted as one `presence_sub` when that set changes (after 100 ms of quiet) and on each connect, and keeps who Slack shows active or away from `presence_change` batches, in memory only, cleared when the socket drops or the session ends. `handlers.ts` serves it as `presence.people`.
- `src/aiAudit.ts` is `AiAudit`, the AI activity log: `record` queues a call (from the engine's provider wrapper in `ai.ts` or the agent's `host.ai.record`) and one fiber writes the queue to `ai_calls` in the open workspace, keeping the newest 500. `src/aiActivity.ts` serves `ai.activity` to Settings › AI activity, with topic names looked up on every run.
- `src/devLog.ts` is `DevLog`, the developer log (architecture 2.7): a ring buffer of the newest 2,000 Slack calls, socket events and sync steps, in memory only. `src/devLogText.ts` is the one place that removes secrets and cuts values short; `src/devLogRoutes.ts` serves `devLog.list` and `devLog.entry`. Never log, save or send its entries.
- `src/workspace.ts`: the `Workspace` service, the store of the signed-in team. The session opens it before any Slack call, so the first live query is answered from the cache; handlers follow `Workspace.changes`. A top-level module because the session, the runner and the handlers all need it and feature folders do not import each other.
- `src/sessionClient.ts`: the `SessionClient` service, the ready session's `SlackApi` and workspace url as top-level modules see them. The session feature provides it (`src/session/client.ts`); `layer.ts` wires it. It exists so the outbox can reach Slack, and a forward can build its source's permalink, without importing the session feature.
- `src/agent-host/`: the engine's `JunoHost` for `@juno/agent-juno` (`host.ts`): reads from the open store (`reads.ts`), the `agent_attempts` ledger (`attempts.ts`), the single-attempt send and the Slack lookup that reconciles it, and presence. The engine phase comes from the status feature through `PhaseSource`, which `layer.ts` provides.
- `src/outbox.ts`: the `Outbox` seam between a command's local change and Slack (architecture 5.7). Today `send` calls the method at once on the ready session's `send` lane and maps the client's errors to the contract's, `sendChecked` does the same for a call whose `beforeSend` check runs holding the lane and may fail with `NotSent` (a copy's delete), `sendOnce` does the same in one exchange with no retry (the agent's single-attempt mode), `lookup` does the same on the interactive lane for an authoritative read after a change, and `exclusive(key)` runs commands on one target one at a time; the persisted outbox replaces this module later without changing the commands.
- `src/syncLink.ts`: the `SyncLink` service, what the topic view and the send worker need from the running sync: its `TopicFetcher` for opened topics and sent messages (the session's `SyncRunner` hands it in while a sync runs), the topics on screen (a `topics.get` subscription marks its topic), which the sync fetches again after a reconnect, and `caughtUps`, one element each time a boot or catch-up ends. Top-level for the same reason as `sessionClient.ts`.
- `src/topicRows.ts`: a `topic_index` row joined with its overlay, conversation and follow flag, and the glue to the domain's `Topic` and the wire's `ChannelRef` and `Person`. The sidebar query and the topic header shape topics through it.
- `src/layer.ts`: the one place that merges feature `Services` and `Handlers`, and folds the session status and the sync phase into `engine.status`.

## Public API

- `startEngine`, `EngineHandle`, `EngineHostOptions`. `commandIdle()` waits for scheduled background command recovery, including its store writes. Host options can observe sync cycles and override the sync schedule. See [the test harness](test/README.md).
- `Host`, `memoryHost`, `silentHost`, `HostLink`: the parentPort line to main and its test doubles.
- `electronTransport`, `memoryTransport`, `Transport`, `EnginePort`: where ports come from.
- `listTopics(filter, options, cache?)`, `makeRowCache()`, `SIDEBAR_WINDOW`: the sidebar query, for the live dry run (`scripts/sync-live-dry-run.ts`) and the benchmark.

Inside the engine, `src/protocol/live.ts` has the serve helpers feature handlers use: `serveLiveValue(runs, options)` and `serveLiveList(runs, { encodeRow })` turn a stream of query runs (`liveQuery(keys, timed(query))` from `@juno/store`) into `meta`-stamped messages and row deltas, and send nothing for a run that changed nothing; `retryFirstRun(label)` starts a served stream again with backoff when its first run fails, for a route with no error of its own to show.

`serveLiveList` also sends the side tables (`ListRun.refs`, architecture 7): a run returns every person and channel its rows name, and the helper sends one only when the subscription has not been sent it or it changed since.

Renderer command middleware marks writes through `CommandWrite`. Live queries carry that cause through debounce and expose it as `meta.own` on list updates, so the sidebar distinguishes own actions from sync without a time window. Queries that change nothing emit nothing and do not tag the next independent update.

## The sidebar query

`src/topics/query.ts`. Four indexed statements read the window; the pure rules in `@juno/domain` place, sort and shape the rows. A Main row also counts the threads started in its channel since Main's read pointer (`newThreads`), with one range probe on `topic_index_channel_activity`: a thread started after the pointer was also active after it. Threads you started are left out, by `started_threads` and by the root's sender (a primary key lookup on `messages`). Rows name their channel and people by id (`TopicListRow`); the run returns the channels and people as refs, so a new photo changes no row's `rev`. Each `topics.list` subscription keeps a `RowCache` per workspace. It checks the topic version first, reuses parsed columns in a parallel array, and collects user ids again only when their columns or the user cache changed. The people map survives unchanged runs, so an unrelated update does not discard those identities. A topic whose joined columns and people did not change keeps its parsed topic and shaped row; the users it has read are kept until the `users` table changes (the handler forgets them from a synchronous invalidation handler). Each subscription also re-runs once a minute by itself so a topic turns quiet on time. A failed run reaches the renderer as the last value with `meta.error`. Its `windowCovered` metadata becomes true once the cold boot's quick start (`sync_state.quickStart`) or a whole boot (`sync_state.boot`) is stored (`rowsCovered`); the sync fires `sync_state` with each marker, so the query re-runs even when no row changes. All topics also emits this coverage flag. The renderer holds empty-cache topic lists until then; afterwards rows fill in as the sync stores them, and `SyncRunner` sorts each clear bot channel into Automated as its history lands (`onHistory`).

## The topic view

`src/messages/`. No live query calls Slack except `reactions.who`, which is never prefetched, so a prefetch is one local query.

- `messages.list` (`query.ts`, statements in `window.ts`): Main reads the partial index `messages_main` (roots and broadcast replies), a thread reads `messages_thread`, plus its root by key while the root has no reply and so no `thread_ts`; up to `before` rows older than the anchor, then the anchor and newer rows, `limit` in all (500 at most). Then the reactions by key and, for Main, one earliest local reply per linked root through `messages_thread`. A preview is shown when the root has exactly one reply, or `thread_cursors` establishes coverage from the root or complete replies; tail-only caches show the count alone. Main subscribes to channel message writes and thread coverage so arriving replies fill the preview without a Slack fetch. Each subscription keeps a `MessageCache`: a message whose version, reactions, group start and thread link are unchanged keeps its row object; bodies are parsed with `@juno/richtext` from the names, channels and custom emoji the cache holds, and only the ids a body asked for that the cache lacked are read and that body parsed again. The cache drops those lookups when `users`, `conversations` or `emoji` change, which rebuilds every row once; `rev` is a hash of the shaped row, so a rebuilt row that looks the same does not travel. Senders are refs. Group starts come from `startsGroup`, thread link labels from `threadLinkLabel` (`@juno/domain`). Images get a `juno://files/<id>/<variant>?url=` thumbnail with the box the view reserves (at most 360 px on the long side).
- `topics.get` (`detail.ts`): the index row by key with the read pointer, or, for a topic the index does not hold yet, a header from the conversation alone, so an uncached topic opened offline still has a header. Main also counts its threads with activity in the quiet window.
- `channel.threads` (`detail.ts`): the channel's threads with activity in the quiet window through `topic_index_channel_activity`, newest first, with participants as refs.
- `reactions.who` (`reactors.ts`, handler in `reactorsHandlers.ts`): one message's reactions, everyone stored on each (you first when you reacted), the people the store knows as `Person`s, and `loading`. The message, its reactions and the team by key, the channel's outbox rows, then users and custom emoji by id. A subscription asks the sync's fetcher once per incomplete stored snapshot for the full list, retries a response superseded by a concurrent write, forked so the stored value goes first, and asks `wantUsers` for reactors the store lacks.
- `topics.open` and `messages.loadOlder` (`handlers.ts`): the sync's `TopicFetcher` from `SyncLink`, on the interactive lane. Slack's answer comes back as `outcome` (`fetched`, `cached`, `offline`, `rate-limited`, `signed-out`, `rejected`), never as a failure; only an id that is not a topic fails, with `NotFound`.

## Must not

- Import `electron`, React, `@juno/state` (except in tests) or `@juno/views`. The host adapts Electron ports to `Transport`.
- Let one feature folder import another, or `layer`, `startEngine` or `index` (`check-deps` enforces it).
- Import `effect/sql`, `effect/reactivity` or other unstable modules outside `src/protocol`. Reach the database through `@juno/store`.
- Hold domain rules. Those belong in `@juno/domain`.
- Let a `@juno/slack` or `@juno/store` error reach a route unmapped (architecture 2.6, "Error mapping").

## Testing

`bun run --cwd packages/engine test`. The tests start the real engine on a `memoryTransport` and talk to it with the real `@juno/state` client over a Node `MessageChannel` (`test/harness.ts`), so they cover the wire end to end.

- `test/live.test.ts`: the serve helpers, and recovery from SQL errors on a real store.
- `test/flows/*.flow.test.ts`: user journeys against the fake, most starting warm on the synced default workspace (`test/synced.ts`): `first-sync` (sign-in to live, cold), `live-events`, `gap-and-restart` (drops and restarts), `follow` and `follow-races` (specs/follow.qnt), `rate-limits`, `mutation-repair`, `sidebar` (filters, the participant stack, views, Automated), `quiet-window`, `search` (local and Slack search, New chat pickers), `ai-jobs` (titles, drawings and Home with the fake AI). `test/convergence.test.ts` is the randomised sync test.
- `test/sidebar-rule.test.ts`: the sidebar and counts SQL against `sidebarPlacement` over a table of every topic status.
- `test/reads.test.ts`: the read commands against the fake: the calls each kind of topic makes, coalescing, retries and a restart with a pending mark, marks from other clients during and after a pending mark, the mirror setting, and that nothing marks by itself.
- `test/session.test.ts`: sign-in, sign-out and session expiry. `test/plan.test.ts` checks the query plans of the sidebar and the topic view.
- `test/send.test.ts`: sending against the fake: the pending row at once, the answer before and after the echo, a lost answer settled by the lookup, an error Slack may give after posting, a reconnect and a restart in between, Retry and Delete draft, order per channel, the flush at a catch-up, threads, a first DM, and drafts across a restart.
- `test/slack-schedule.test.ts`: Slack's notification schedule against the fake: the first write once and none on restart, none when Slack already holds the hours, one write for two quick changes, Restore and the switch, and a change made in Slack left alone until Use Juno's hours.
- `test/who-reacted.test.ts`: `reactions.who` against the fake's 40-reactor seed: the stored list at once, then everyone after one `reactions.get` `full`, names arriving for new people, the window still at ten per chip, no second fetch while the store lists everyone, socket adds and removes, a same-count truncated snapshot replacing stale names, shared concurrent reads, a response raced by an event, a refused fetch, the user's own unsent reaction, and an unknown message.
- `test/messages.test.ts`: the topic view against the fake: the first and the incremental open of a thread (one replies call each), Main read from its synced range, an uncached topic opened offline, a prefetch with no Slack call, an older page, a live reply as one row in a small delta, an edit, a reaction and a deleted root as one row each, a thread link that follows its thread, a new photo as one ref with no row changed, image thumbnails, and Main's active threads.

Tests run on `bun test`, a file per process in parallel; a test has 30 s and a harness wait 15 s (`WAIT_MS`). See `test/README.md`.

`bun run bench:engine` (or `bun run perf --unit` with the other perf files) runs the large-seed benchmarks in `test/perf/*-large.perf.ts`, fails them on their budgets, and prints the numbers with the load average: the query alone (with and without the row cache), `meta.queryMs` inside the engine while events land, the snapshot (rows and refs apart) and delta sizes, and the encode, clone and decode times. `messages-large.perf.ts` does the same for a 300-message thread built like the M4 gate's fixture, and times opening it uncached and cached. Measured in October 2026 at a load of 4 to 8: `topics.list` 175 KB of rows and 92 KB of refs (was 321 KB of rows), query p95 2.5 ms; `messages.list` on 300 rows 167 KB of rows and under 1 KB of refs, a first run (every body parsed) 3.7 ms median and 5.3 ms p95, a re-run 0.8 ms median and 3.3 ms p95, 1.2 ms p95 inside the engine while replies land, deltas under 1 KB, encode and decode 0.9 ms; opening the uncached thread 0.68 s to the 300 rows (three replies pages from the fake), a new subscription to a cached window 18 ms to its first snapshot. Inside the engine the CPU is often idle between events, and the first run after an idle gap is about twice as slow as the same run on a busy CPU, so read both numbers.
`test/perf/search-large.perf.ts` is the WP2 FTS gate: 100 k stored messages and about 5 k topic titles, with 200-row backfill batches committing while search runs. It asserts p95 at most 20 ms and reports the sample range, row counts and load average.

Reply watches use `host.schedule.check` (cached metadata or a complete Slack
refresh), `host.schedule.hours` (saved notification hours and local timezone),
and `host.schedule.changes` (message-store invalidations). The check includes
the owner's identity and verifies the source author for the menu command.
No message text crosses these routes. Account checks surround refreshes, and
incomplete or limited Slack history fails rather than reporting no reply.

`src/viewCommands.ts` holds the shared sidebar view commands, used by the sheet
handlers and `agent-host/views.ts`. Saving captures the previous and resulting
view in the same writer transaction. AgentHost Undo compares that snapshot
before restoring it, so a later edit is not overwritten.

Message windows publish `meta.windowCovered` from `src/messages/coverage.ts`. Main uses synced history ranges; threads use stored reply counts or the cursor coverage. Coverage-only changes are emitted even when no message changed. The renderer uses this to avoid positioning isolated cached messages before history arrives.

Channel and group DM roots sent from Home use `startedThreads.ts` to resolve durable outbox topic identities. The thread view stays mounted through acknowledgement; dependent replies wait for the root in the normal post worker.

The ⌘K Conversations tab's `newChat.ranked` live query ranks conversations by own sends and topic visits (`topic_visits`) over 30 days, each use counting half as much per week, then by activity, before its 12 rows; archived and ignored channels are excluded and it never calls Slack; with text it ranks the conversation picker's matches, names that start with the text first among the unused. It re-runs on conversation, user, ignore and visit changes, not on messages, so a send re-ranks it on the next open. The renderer reads it as `paletteConversationsAtom`.

`EngineHostOptions.logger` lets the process entry supply a content-safe Effect logger. `engine.outbox` reads counts by kind and state only; no payload or error text leaves the store.

Home reads missed huddles from indexed local `huddle_history`, ranks one after mentions and acknowledges opening through `home.huddleSeen`.

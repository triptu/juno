# @juno/sync

Slack into the store. Cold and warm boot, thread discovery, the merge rules, socket event application, read-state seeding and `reindexTopics`. See `docs/architecture.md` sections 4.4, 5 and 6, and ADRs 0004 and 0011.

## Public API

- `runSync({ onPhase, onFetcher?, openTopics? })`: the whole sync for one session, until interrupted. Needs the Slack client (`SlackApi`, `SlackEdge`, `SlackSocket`, `SlackSession`) and the store (`StoreWriter`, `StoreReader`, `Invalidation`) in its context, plus a `Scope`. It opens the socket first, boots cold (empty cache) or warm (`sync_state.boot` present), then stays live: every event is one transaction, a reconnect runs the catch-up, a discovery sweep runs every ten minutes. It fails only with `SlackAuthRequired`; the engine then ends the session.
- `SyncPhase`: `booting`, `catching-up { done, total }`, `live`, `offline`. `onPhase` is called on every change; the engine folds it into `engine.status`.
- `SyncConfig` / `syncConfigLayer({ ... })`: the quiet window, page sizes, sweep interval, `discovery: 'search' | 'history'`.
- `reindexTopics(ids, { me })`, `reindexAll`: the one writer of `topic_index`. Call it at the end of any transaction that touched a topic's messages, reads or coverage. `topicsOfMessages(rows)` gives the ids a set of message rows belongs to.
- `mergeMessage`, `mergeTombstone`, `mergeRootCounters`, `stubRoot`, `toMessageRow`: the pure merge rules, for tests and for the outbox work to come.
- `threadSub`, `setThreadSub`, `clearThreadSub`, `beginPendingFollow`, `endPendingFollow`, `readMessage`, `readState`: the writer-side reads and writes the engine's commands share with the sync, so a command's transaction uses the same rows and fires the same keys. `setThreadSub` takes a `ThreadSubSource` (`event`, `page` or `command`) and applies the ordering rule below.
- `syncKeys`: the invalidation keys the sync fires (`topics`, `{ topics: [id] }`, `{ messages: [topicId] }`, `conversations`, `users`, `team`, `channel_reads`, `thread_subs`, `{ topic_reads: [id] }`, `{ topic_overlay: [id] }`). A message write, and a change to its reactions, fires `{ messages: [...] }` for every topic that shows the message (`messageTopics`): Main and the thread for a root with replies, the thread and Main for a broadcast reply.
- `TopicFetcher` (from `onFetcher`) and `fetchTopic`, `fetchOlder` (`open.ts`): what an opened topic needs from Slack, in the sync's context. See "Opening a topic" below.

## What it decides

Beyond the architecture document, these are the rules the code settled:

- **Lanes.** `userBoot`, `prefs`, `counts` and the `getView` pages with activity inside the window (at a reconnect, since the store was last in step) run on the interactive lane (the sidebar is usable after them); the complete `getView` pass, history, replies, search and users on the background lane.
- **Membership.** `client.userBoot` is metadata only: live it lists every channel of the workspace without `is_member`, `last_read` or `latest` (research section 2), so `toConversationRow` never sets `is_member` and `upsertConversations` keeps the stored flag. `client.counts` decides: a full answer (cold and warm boot, no `counts_last_fetched`) replaces the member set with its entries (`replaceMembership`), an incremental one (reconnect) only adds (`setMembership`). Events keep it current: `channel_joined`/`group_joined`, `member_joined_channel` for self, `im_open`, `im_created`, `mpim_open`, `mpim_joined` set it; `channel_left`/`group_left`, `member_left_channel` for self and `channel_deleted`/`group_deleted` clear it; `im_close`/`mpim_close` only refresh metadata. The sidebar query, `activeConversations` and discovery all filter on `conversations.is_member`.
- **Read pointers.** The first time Juno sees a topic it takes Slack's pointer (`counts.last_read` for Main, the root's `last_read` for a followed thread). After that Juno's `topic_reads` is the state, and a server mark (a `*_marked` event, or a pointer in `counts` or `getView` seen after a disconnect) applies through the conflict rule of architecture 5.6; `counts` is stamped with the time before the call, so a mark that lands while it is in flight wins. A thread the user does not follow has no pointer in Slack: at cold boot it starts read at its latest reply before the boot started, so a first boot does not light up every old thread while a reply during the boot stays unread; one discovered later starts unread.
- **Follow state.** `thread_subs` is Slack's follow flag for a thread and decides whether the thread is a sidebar row. Every source writes it: `getView` rows; a root on a history, replies or lookup page, which carries `subscribed` (`true` sets the flag, `false` clears a stored follow, a root without the field changes nothing, and `false` for a thread Slack never mentioned stays unknown so the sidebar's mention rule still applies); `thread_subscribed`, `thread_unsubscribed` and `thread_marked` events; a reply by the user and a reply to the user's own root (`followOnReply`), because Slack follows for you in both cases; and the engine's commands. The order is the rule of specs/follow.qnt: an event applies unless an event with a newer `event_ts` has been applied (`updated_event_ts`); a page applies only when its request started after the row was last observed or changed (`observed_at`, Juno's clock), so a page in flight during an unfollow cannot bring the follow back; a command always applies and stamps `observed_at`, and stamps it again when its call ends, so a page requested while it was pending cannot apply either; while a command on the thread is pending (an `outbox` row of kind `follow`) events and pages do not change the flag but are noted, and the command looks the root up afterwards. Slack's `event_ts` cannot be ordered against Juno's own command (a frame Slack sent before it accepted the call can arrive after the answer), so an event that contradicts a row a command wrote (`thread_subs.commanded`) is not applied: the root is looked up instead. A failed command never puts the old state back unasked, since Slack may have accepted the call before its answer was lost: the root is looked up, and while that fails the row keeps the command's state and the lookup is retried with backoff. `getView` lists followed threads newest activity first, so pages read back to a moment list every followed thread active since then. Boots read back to the start of the quiet window and then look up, by root, every stored follow active in that range that the pages left out; absence alone never means unfollowed. A reconnect reads back to the last sync only. With a catch-up or sweep, at most hourly after the last boot or pass (`followPassMillis`; every catch-up when the engine runs against the fake), `followPass` reads the window again on the background lane and looks up what it left out. No pass reads the whole list: measured live, an account follows over 9,000 threads (more than 930 calls had not reached the end). A follow last seen before the window is checked when its thread next gets a reply: the root is looked up, and its `subscribed` applies.
- **Exact counts.** A thread's `unread_count` is exact when every reply since the read pointer is stored: `thread_cursors.complete_from` records where coverage starts (a thread view stores every unread reply, so it is Slack's pointer), and a reply received as an event keeps it. A socket drop clears `complete_from` for threads the user does not follow, because replies during the gap may never arrive; followed threads keep it, since the reconnect reads every followed thread with activity since the store was last in step. "Complete" means the stored replies reach the root's `reply_count`; `replies_complete` is written but not trusted for the count. Main is exact when a synced range covers everything since the pointer; otherwise the row carries `has_unreads` as a floor of one and `unread_exact = 0` (a dot, not a number).
- **Counters.** A root's `reply_count` and `latest_reply` take the maximum of what pages and events say and never go below the replies the store holds. A reply from a page that the root's counters never saw (a `message_replied` lost during a drop) queues a refetch of the root (`conversations.replies`, `limit: 1`). A deleted reply recounts the root from the store when the thread is complete, else drops the count by one.
- **Index rows carry what the row shows.** `preview_json` holds the sender, the stripped text, the sender id (so a rename applies at read time) and the first 240 characters of the root (the fallback title), so `topics.list` joins no `messages` row.
- **Discovery.** `search.modules.messages` with `is:thread after:<day before the gap>`, `sort=timestamp` newest first (without it Slack orders by relevance and the pages are a sample), at most three pages of 50, members-only. A match is a partial message (`MergeSource` `partial`): it creates rows the store lacks, fills stub roots and moves counters, but never replaces stored content, because it carries no files, no reactions and sometimes no blocks. A reply's thread comes from `thread_ts` or from the `thread_ts` of its permalink (live, matches carry no `thread_ts`: items hold their messages in `messages[]`, research section 10); a match that names no thread is dropped. A failed sweep is logged and does not fail the boot or catch-up; `lastSyncAt` stays where it was, so the next sweep searches the same gap. The sweep also runs at the end of a cold boot over the window, so Main knows about replies to roots older than the window. `discovery: 'history'` is the fallback of architecture 5.3 (replies since the stored ones for roots whose `latest_reply` moved).
- **Cold boot.** A boot that fails half way is retried after 30 s and skips the conversations whose synced range already covers the window (seen live: the retries took 25 s instead of 6 minutes). A conversation whose history Slack refuses (`SlackRejected`, for example deleted between `counts` and the call) is skipped instead of failing the boot. Membership: an incremental `counts` entry for a conversation the store has never seen (joined while the socket was down) is fetched with `conversations.info` first. `channel_rename` and `group_rename` carry a partial object and patch only the name.
- **Users.** Ids referenced by messages and DMs with no `users` row are fetched from the edge in chunks of 100 after the history pages; the topics whose preview waited for a name are re-indexed when the users land. Ids the edge reports in `failed_ids` (bots, Slack Connect users) are not asked for again in the session. The user groups the user belongs to (`userBoot.subteams.self`) count as mentions.
- **Emoji.** After boot reaches live, `syncEmoji()` reads every edge `emojis/list` page on the background lane and replaces the `emoji` table, then invalidates `emoji`. Both cold and warm boots refresh it. A failed refresh keeps the old table and logs only the error tag. The schema follows the bundle-referenced `name`, `url` and `alias_for` fields; its full live response remains unverified (research section 3).
- **Live shapes.** `hello.start` is a boolean live and is not read; `reconnect_url` arrives after `hello` and again every 30 to 60 s, and the socket keeps the latest one; `getView` pages by `current_ts = latest_reply` of the last root on the page; `unread_replies` is absent when nothing is unread. The fake sends the same shapes.
- **Errors.** `SlackAuthRequired` from any step (the socket, a boot, a catch-up, the sweep, a root fetch) ends the sync; the catch-up and reboot fibers run in a `FiberSet` that `runSync` joins, so their failure reaches the engine. Any other boot failure sets the phase to `offline` and retries after 30 s; any other catch-up failure is logged and the phase settles. A store error while applying one event is logged and the event is skipped, so one bad frame does not end the stream.

## Opening a topic

`open.ts`, called only by the engine's `topics.open` and `messages.loadOlder` commands and by the reconnect step, never by a live query (architecture 5.5, M4):

- A thread whose replies are not all stored: `conversations.replies` from the root, pages of 100, at most 500 messages (`OPEN_FETCH_MAX`); a thread longer than that starts at the read pointer, so every unread reply is stored. When the pages reach the end, `thread_cursors` records complete coverage from where they started, so the unread count is exact. Once every reply is stored, an open asks only for replies after the newest stored one.
- Main: `conversations.history` since the newest synced range (one page of 50 when there is none), then older pages until history reaches the read pointer, at most 500 messages. Each page records its range in the same transaction as its messages, so the "N new" count is exact once the range reaches the pointer. A page with nothing more and no `oldest` bound covers back to the start of the conversation (`HISTORY_START`).
- Older pages: a Main page is fetched only when the synced range that holds the first row has fewer than 100 stored messages before it; a thread page only while the stored replies have a gap at the start.
- `runSync` hands the engine a `TopicFetcher` that runs these on the interactive lane in the sync's context, so stub roots it finds are fetched and unknown senders named in the background. When Slack rate-limits the call, the same fetch is queued on the background lane and the caller gets the error. After each reconnect and sweep, the topics `openTopics` names (the engine's open tabs) are fetched again.

## Follow state against `specs/follow.qnt`

The rule in one place, with the spec action or property each part implements. `observed_at` and `updated_event_ts` are columns of `thread_subs`; `setThreadSub` (`src/write.ts`) applies them. The spec models the current command seam, including its failures; it does not certify application code.

| Rule | Code | Spec |
| --- | --- | --- |
| A command writes the flag and pending `follow` row in one transaction before the Slack call, stamping `observed_at` and `commanded`. Pages requested before it cannot apply. | `engine/topics/commands.ts` `setThreadSubscribed`, `beginPendingFollow` | `localChange`, `observedAt`, `commanded`; `pendingIntentWins` |
| The end of the call, success or failure, stamps `observed_at` again. Pages requested while the command was pending cannot apply. | `endPendingFollow` | `acknowledge`, `reject` (`restamp`); `acceptedUnfollow`, `pendingPageStep` |
| Commands on one thread run one at a time. | `Outbox.exclusive` | At most one pending command; overlapping refreshes are outside the model |
| Eligible events and pages while pending only note an observation. They do not change the flag or either watermark. | `notePendingFollow` | `deliver`, `finishFetch`, `noted` |
| After success, a noted observation makes the command look up the root. | `endPendingFollow`, `refresh` | `acknowledge`, then a `success` fetch |
| Every command error asks for the root, even after Slack accepted. A false after a failed first Subscribe restores Unknown. When the lookup fails too, the row keeps the command's state and the lookup is retried with backoff (`Outbox.background`) until Slack answers or something newer is observed. | `refresh`, `retryRefresh` | `reject`, `finishFetch` kind `failure`, `failLookup` (`retry`); `failedCallReverted`, `acceptedUnfollow`, `failedLookupStep` |
| An event applies unless a newer event stamp already applied. Its arrival stamps Juno's observation clock. | `setThreadSub` `event` | `deliver`: `e.at >= updatedEvent`, arrival updates `observedAt` |
| An event that contradicts a row a command wrote is not applied; the root is looked up. | `setThreadSub` returns `lookup`; `events.ts` queues the root | `deliver` (`verify`); `acceptedUnfollow`, `lateEventStep` |
| An undated event queues a root lookup. A missing follow field makes no flag change. | `events.ts` | `undatedEvent`, `missingRoot`; `missingChangesNothing` |
| A page applies only when requested after `observed_at`. A false root never creates a row for an unknown thread. | `setThreadSub` `page`, `applyRootSubscription` | `finishFetch`: `f.at > observedAt`; `unknownStaysUnknown` |
| Boot and hourly passes read the quiet window, then look up stored follows in range that pages left out and that were not observed since the first request. Reconnect's shorter read concludes nothing about missing rows. | `loadThreadViews`, `probeUnlisted`, `followPass` | `startScan`, `requestPage`, `advancePage`, `finishScan`, `probeAbsent`; scoped `quietAgreement`, `drainBound` |
| Another user's reply checks a stale stored follow outside the window. | `followOnReply` | `otherReply`, root lookup, activity coverage |
| The user's own reply follows its thread. | `followOnReply` | `reply` and its observation |

The spec now uses separate Slack event and Juno observation clocks, Unknown, failure lookup without retry, and window passes instead of full-list reconnect recovery. Inactive follows outside the window may stay stale. A moving cursor is abstracted by fixed page slots; agreement assumes a later pass once quiet, not that every pass sees every change.

`acceptedUnfollow` (an Unsubscribe Slack accepted is never undone by older information) is one of the checked invariants. Each of its three guards has a bug schedule that switches it off and must still produce a counterexample: a delayed pre-command followed event after the answer (`lateEventBugStep`), a followed page requested during the command and answered after it (`pendingPageBugStep`), and an accepted Unsubscribe whose answer and root lookup both fail, with the old fallback restoring the follow (`failedLookupBugStep`). See `specs/README.md` for the traces and bounded-check limits.

## Known gaps

- Edits, deletes and reactions that happen during a disconnect are recovered for threads by the search sweep (text) and otherwise only when the topic is opened or is open at the reconnect, and then only for messages newer than the stored ones (the open fetch asks for what is new, not for the whole window). ADR 0011's `cached_latest_updates` path waits on the live smoke.
- A message first stored from a search match has no reaction state, files or blocks until a page or an event brings it.
- A follow changed elsewhere during a drop, on a thread with no activity since the last sync, waits for the next window pass (at most an hour). A follow older than the window waits for its thread's next reply.
- The sweep reads at most 150 matches per gap; a longer outage in a busy workspace misses older thread activity until the next sweep or open.
- The outbox, read-state mirroring and send reconciliation are later milestones; the tables and the conflict rule are in place.

## Must not

- Render anything or call AI. It depends on `@juno/slack`, `@juno/store`, `@juno/domain` and `@juno/slack-schema` only.
- Write `topic_index` anywhere but `reindex.ts`, or increment a counter in place.
- Let a socket event move `synced_ranges`; only pages extend them.
- Import `effect/sql` or `effect/reactivity`; the store's services are the only way to the database.

## Testing

`pnpm --filter @juno/sync test` runs the merge rule table (`test/merge.test.ts`). The sync itself is tested end to end in `packages/engine/test`: `sync.test.ts` (cold boot rows, exact call budgets, membership from counts and events, warm boot, realtime, read marks, reopen, edits and deletes, offline and back, follow state against stale pages and pending commands, an accepted Unsubscribe against a late event, a page from while it was pending, and a lost answer with a failed lookup, every `getView` page, search matches, an expired session found by the catch-up, failed commands, cold boot details, workspace events), `reconnect.test.ts` (what changed offline, with an exact call budget, and events that land while a page is in flight), `convergence.test.ts` (seeded random events with drops, follows and unfollows, and follow events held back across commands; an accepted Unsubscribe is never undone, the store and the follow state equal the fake's and a full re-index changes nothing) and `plan.test.ts` (the sidebar statements never scan the guarded tables). The follow protocol they exercise is specified in `specs/follow.qnt`. `JUNO_BENCH=1` adds the large-seed benchmark in `test/bench`. `JUNO_LIVE=1 pnpm sync:live` runs the real cold boot read-only against your workspace into a temporary directory and prints aggregate numbers (`docs/development.md`, "The live sync dry run").

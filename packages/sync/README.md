# @juno/sync

Slack into the store. Cold and warm boot, thread discovery, the merge rules, socket event application, read-state seeding and `reindexTopics`. See `docs/architecture.md` sections 4.4, 5 and 6, and ADRs 0004 and 0011.

## Source layout

`sync.ts` wires the session together. `run/runtime.ts` owns its shared state and work
permit; `run/boot.ts`, `run/reconcile.ts` and `run/socket.ts` handle boot, catch-up
and socket events. `run/fetcher.ts` exposes topic fetches and `run/lookups.ts` runs
root and read lookups. `counts.ts` reads counts through the metadata fence;
`mutationRepair.ts` repairs dirty cached ranges after a gap; `recheck.ts` retains the bounded fallback.

`write.ts` re-exports the table writers in `write/`: messages, users, conversations,
team, channel reads, subscriptions, coverage, read state, overlays and sync state.
Each writer still uses the caller's transaction and fires the same invalidations.

## Public API

- `runSync({ onPhase, onCycle?, onStep?, onFetcher?, openTopics?, onEvent? })`: the whole sync for one session, until interrupted. Needs the Slack client (`SlackApi`, `SlackEdge`, `SlackSocket`, `SlackSession`) and the store (`StoreWriter`, `StoreReader`, `Invalidation`) in its context, plus a `Scope`. It opens the socket first, boots cold (empty cache) or warm (`sync_state.boot` present), then stays live: every event is one transaction, a reconnect runs the catch-up, a discovery sweep runs every ten minutes. It fails only with `SlackAuthRequired`; the engine then ends the session.
- `onEvent(event, me)`: a nonblocking observer after socket event application. The engine passes `SocketEvents`' publisher here, which queues the event for each subscriber. This does not change merge, follow, or read-state rules.
- `onCycle`: reports `started` and `finished` around boot, reboot and reconnect/sweep reconciliation, including the follow pass after `live`. It also finishes on failure or interruption; it does not drain socket events or command recovery. Tests use it to await completion rather than infer it from API traffic.
- `onStep`: a synchronous observer told when each cold boot, warm boot, catch-up, sweep and follow pass starts, and how it ended (`finished`, `failed` with a one-line cause, `interrupted`) with its duration. The engine's developer log uses it (architecture 2.7). Observation only.
- `SyncPhase`: `booting`, `catching-up { done, total }`, `live`, `offline`, `failed { reason }`. `onPhase` is called on every change; the engine folds it into `engine.status`.
- `SyncConfig` / `syncConfigLayer({ ... })`: the quiet window, page sizes, sweep interval, `discovery: 'search' | 'history'`. `sweepIntervalMillis: 0` disables the periodic timer; boot, reconnect and `force_reload` still run their passes.
- `reindexTopics(ids, { me })`, `reindexAll`: the one writer of `topic_index`. It also stores per-message notification attention from the same parsed unread bodies, keeping sender and mention eligibility together. Call it at the end of any transaction that touched a topic's messages, reads or coverage. `topicsOfMessages(rows)` gives the ids a set of message rows belongs to. A topic none of whose inputs changed since its row was computed is not computed again: `topic_inputs` in cache.db marks up-to-date rows, store triggers clear a mark when an input in cache.db changes, and the mark keeps the rule's version, the user and the read state, compared each time (`topicInputs.ts`). A row that looked for a person, user group or sender not stored is never marked. A new input to the rule needs a trigger or a field in the mark; `test/reindexInputs.test.ts` checks each input against a rebuild. `writeMessage` writes nothing when a page brings a stored message unchanged, so a re-fetched page leaves its topics marked.
- `mergeMessage`, `mergeTombstone`, `mergeRootCounters`, `stubRoot`, `toMessageRow`: the pure merge rules, for tests.
- `threadSub`, `setThreadSub`, `clearThreadSub`, `beginPendingFollow`, `endPendingFollow`, `readMessage`: the writer-side reads and writes the engine's commands share with the sync, so a command's transaction uses the same rows and fires the same keys. `setThreadSub` takes a `ThreadSubSource` (`event`, `page` or `command`) and applies the ordering rule below.
- `readState`, `observeRead`, `writeLocalMark`, `pendingMark`, `pendingMarks`, `endMark`, `rejectMark`, `deferMark`, `dropMark`: the read state and the `mark` outbox rows, shared by the sync and the engine's read commands and mark worker. `observeRead(topic, read)` applies Slack's pointer from an event or a page by the read rule below and says whether to ask Slack. `storedMe` is the user and their groups as the last boot saw them, for a command that re-indexes.
- `writeLocalDraft`, `sendDraft`, `observeDraft`, `draftSyncRow`, `pendingDrafts`, `beginDraftSave`, `endDraftSave`, `deferDraftSave`, `recoverDraftSaves`, `settleDraftFinds`, `endSentDraft`, `dropDraftSave`, `draftClientMsgId`, `linkedDrafts`, `topicOfSlackDraft`, `draftTopicId`, `draftDestination`: topic drafts synced with Slack (`write/drafts.ts`, `write/draftSaves.ts`, specs/drafts.qnt): the `drafts` and `draft_sync` rows and each topic's one `draft` outbox row. The rules are `observeSlackDraft` in `@juno/domain`; the engine's `DraftSync` makes the calls and turns Slack's blocks into the composer's text.
- `queuePost`, `pendingPosts`, `claimPost`, `postUnknown`, `requeuePost`, `deferLookup`, `failPost`, `retryPost`, `discardPost`, `recoverPosts`, `flushPosts`, `postTopic`: the send outbox's rows (`posts.ts`, architecture 5.7, specs/outbox.qnt), the only writers of `pending_messages`, for the engine's send commands and `PostWorker`. Each move names the states it may start from, so a row the echo reconciled meanwhile, or one the user changed, is left alone. `writeMessage` deletes the pending row with the stored message's `client_msg_id` in the same transaction: that one place is the reconciliation for the answer, the echo, pages and the lookup. `TopicFetcher.opened` stores a DM Juno opened for a send through the running metadata fence.
- `syncKeys`: the invalidation keys the sync fires (`topics`, `{ topics: [id] }`, `{ messages: [topicId] }`, `conversations`, `users`, `team`, `channel_reads`, `thread_subs`, `{ topic_reads: [id] }`, `{ topic_overlay: [id] }`). A message write, and a change to its reactions, fires `{ messages: [...] }` for every topic that shows the message (`messageTopics`): Main and the thread for a root with replies, the thread and Main for a broadcast reply.
- `TopicFetcher` (from `onFetcher`) and `fetchTopic`, `fetchOlder`, `fetchNewer`, `fetchAt` (`open.ts`): what an opened topic needs from Slack, in the sync's context. See "Opening a topic" below.

## What it decides

Beyond the architecture document, these are the rules the code settled:

- **Lanes.** After a socket gap, workspace metadata, full counts and any unknown-conversation lookups run on the background lane. At boot, `userBoot`, `prefs`, `counts` and the `getView` pages with activity inside the window (at a reconnect or periodic sweep, since the store was last in step) run on the interactive lane; the complete hourly `getView` pass, history, replies, search and users run on the background lane. The background lane paces each method on its own clock (`@juno/slack` `queue.ts`), so steps that call different methods run side by side: the cold boot reads history beside the remaining `getView` pages and beside the thread previews (`conversations.replies` for the unfollowed threads history finds, woken by each history page), and user groups and emoji beside the whole boot.
- **Thread-list failures.** Each getView row decodes independently. Dropped rows retain their list identity for follow reconciliation, and paging uses the original last row's `latest_reply`. A missing or nonadvancing cursor stops the scan without probing absent follows; an unknown row identity also disables absence probes for that scan. A cold boot logs non-auth Slack failures from the thread list and finishes channels, DMs and history. It then retries a full follow pass after becoming live. A failed pass remains due for the next reconnect or periodic sweep. Authentication and store failures still fail the boot.
- **Quick start.** A cold boot is usable before it is complete. `userBoot` with `prefs` beside it, `counts` and the people of the DMs run first, then the first `getView` page is attempted; then `sync_state.quickStart` is written (`QUICK_START_KEY`) and fires `sync_state`, and the sidebar and All topics show rows from then on (`windowCovered`). Every `setSyncState` fires `sync_state`, so the markers reach live queries that started before them. Then the preview search (`searchPreviews` in `discovery.ts`, beside the rest of the boot, which records itself only after both) reads the newest messages of the window, newest first, at most `previewSearchPages` (2) pages of 50, and stores the plain messages and roots by people as partial messages, so the busiest channels and DMs show a preview within seconds. A match older than the window, a reply, a post by a bot or by someone the edge could not name, and anything in a conversation whose history has landed are left to history. It is paced like any search (10 a minute) and a failure is logged. Until a conversation has a synced range, its Main keeps at least the activity `client.counts` reported, so a preview older than that does not move the row down. `counts` also gives every conversation active in the window a provisional Main row (`reindexTopics` with `provisionalMain`): `latest` is its activity, unread is a dot, the preview is empty. A Main row with `message_count = 0` is provisional; it follows `channel_reads` until a message replaces it, and goes when a synced range exists and holds no Main message. `onHistory(channel)` runs after each conversation's history page so the engine sorts clear bot channels into Automated while rows already show.
- **Membership.** `client.userBoot` is metadata only: live it lists every channel of the workspace without `is_member`, `last_read` or `latest` (research section 2), so `toConversationRow` never sets `is_member` and `upsertConversations` keeps the stored flag. `client.counts` decides: a full answer (cold and warm boot and reconnect after a gap, no `counts_last_fetched`) replaces the member set with its entries (`storeMembership` through the metadata fence), an incremental one (periodic sweep) only adds through the same fence. Events keep it current: `channel_joined`/`group_joined`, `member_joined_channel` for self, `im_open`, `im_created`, `mpim_open`, `mpim_joined` set it, and so does a live message in a DM or group DM, because Slack sends no event when a message opens a closed group DM again (a conversation the store has never seen is fetched with `conversations.info` first); `channel_left`/`group_left`, `member_left_channel` for self and `channel_deleted`/`group_deleted` clear it; `im_close`/`mpim_close` only refresh metadata. The sidebar query, `activeConversations` and discovery all filter on `conversations.is_member`.
- **Metadata fence.** `metadata.ts` records only fields carried by socket events and Juno’s own DM-open answers for every metadata read in flight. Workspace and unknown-conversation snapshots retain those patches; full and incremental membership answers leave observed membership alone. Reads start before the HTTP call and end after the store transaction, including errors and interruption. The work permit serializes these reads, so an older snapshot cannot land after a newer refresh (the same ordering as M7’s recheck). After a socket gap, one `userBoot` and one full `counts` run on the background lane; ordinary sweeps stay incremental. The reconnect still reads followed threads only back to `lastSyncAt`.
- **Read pointers.** The first time Juno sees a topic it takes Slack's pointer (`counts.last_read` for Main, the root's `last_read` for a followed thread). After that Juno's `topic_reads` is the state, and Slack's marks from other clients apply by the read rule below (specs/readstate.qnt). A thread the user does not follow has no pointer in Slack: at cold boot it starts read at its latest reply before the boot started, so a first boot does not light up every old thread while a reply during the boot stays unread; one discovered later starts unread.
- **Follow state.** `thread_subs` is Slack's follow flag for a thread and decides whether the thread is a sidebar row. Every source writes it: `getView` rows; a root on a history, replies or lookup page, which carries `subscribed` (`true` sets the flag, `false` clears a stored follow, a root without the field changes nothing, and `false` for a thread Slack never mentioned stays unknown so the sidebar's mention rule still applies); `thread_subscribed`, `thread_unsubscribed` and `thread_marked` events; a reply by the user and a reply to the user's own root (`followOnReply`), because Slack follows for you in both cases; and the engine's commands. The order is the rule of specs/follow.qnt: an event applies unless an event with a newer `event_ts` has been applied (`updated_event_ts`); a page applies only when its request started after the row was last observed or changed, so a page in flight during an unfollow cannot bring the follow back. The observation clock is the later of durable `observed_at` and the workspace session's `FollowFence`. A no-change `getView` page moves only the session fence, while an event, a command, or a material page change writes `observed_at`. Restart can drop the session fence because no request from the old process can then return. A command always applies and stamps `observed_at`, and stamps it again when its call ends, so a page requested while it was pending cannot apply either; while a command on the thread is pending (an `outbox` row of kind `follow`) events and pages do not change the flag but are noted, and the command looks the root up afterwards. Slack's `event_ts` cannot be ordered against Juno's own command (a frame Slack sent before it accepted the call can arrive after the answer), so an event that contradicts a row a command wrote (`thread_subs.commanded`) is not applied: the root is looked up instead. A failed command never puts the old state back unasked, since Slack may have accepted the call before its answer was lost: the root is looked up, and while that fails the row keeps the command's state and the lookup is retried with backoff. `getView` lists followed threads newest activity first, so pages read back to a moment list every followed thread active since then. Boots read back to the start of the quiet window and then look up, by root, every stored follow active in that range that the pages left out; absence alone never means unfollowed. A reconnect and each ten-minute sweep read back to the last sync only. At most hourly after the last boot or pass, `followPass` reads the whole window again on the background lane and looks up what it left out. Production keeps that cadence. Accelerated tests (the engine harness and the desktop's fast profile) disable the periodic sweep and keep the follow pass at its scaled cadence, so a boot's own pass is the only one; timing and idle checks keep production settings. Focused engine tests can override either value, and set `followPassMillis: 0` to reconcile follows on each catch-up. No pass reads the whole list: measured live, an account follows over 9,000 threads (more than 930 calls had not reached the end). A follow last seen before the window is checked when its thread next gets a reply: the root is looked up, and its `subscribed` applies.
- **Thread coverage.** Like Main's `synced_ranges`, `thread_ranges` records the replies pages proved (`threadRanges.ts`, specs/threadranges.qnt): each `conversations.replies` page from its `oldest` bound (the root without one) to its last reply, or to its `latest` bound when it has nothing more, in the page's transaction (`pageReplies`, `addThreadRange`); the recheck's thread pages too, after the deletions they showed (`recheck.ts`). A page that reached the newest reply on a socket connection with no drop since (`connectionOf`, `stillConnected`) has a live tail. A `getView` row's range (`viewRange`, `kind = 'view'`) counts for the unread count only: the replies after Slack's read pointer, or after the oldest of its `latest_replies` when that is earlier; a sweep whose rows add nothing to the ranges writes nothing (`addsNothing`). The cold boot's read seed for an unfollowed thread proves the replies after it when the socket has been up since the pointer was set (`connectedSince`), and a root that arrived as a posted event on the current connection the replies after it once its thread gets one (`liveRoots`). A range ends at its last reply, never at Juno's clock. Ranges merge only where pages of the same kind touch, so a live tail never joins the ranges above it. A drop, and the start of every run, end the live tails (`endEventCoverage`): each keeps showing and counting the replies up to the newest one the socket delivered for it (`hearReply`, `heard_ts`, sound because events arrive in Slack's order) while `to_ts` stays where pages proved it, so the next open reads them again; followed threads keep a held tail, unfollowed ones none; unfollowing ends a held tail (`endHeldTail`). The topic view's page steps wait five seconds after one Slack could not answer or one that changed nothing (`useStepStall`). Existing threads from before ranges start unknown.
- **Exact counts.** A thread's `unread_count` is exact only when one range reaches from the read pointer (the root when never read) to the end, through a live or held tail or up to the root's `latest_reply` (`countExact`); `reply_count` and the number of stored replies prove nothing. A held tail counts because the reconnect reads every followed thread with activity since the store was last in step and its `getView` row brings every unread reply. An unfollowed thread whose tail ended shows a dot until a page proves it again. Main is exact when a synced range covers everything since the pointer; otherwise the row carries `has_unreads` as a floor of one and `unread_exact = 0` (a dot, not a number). The boot's history page for a conversation reaches back to Main's read pointer when that is older than the window, so a short unread stretch is exact after one page.
- **Counters.** A root's `reply_count` and `latest_reply` take the maximum of what pages and events say and never go below the replies the store holds. A reply from a page that the root's counters never saw (a `message_replied` lost during a drop) queues a refetch of the root (`conversations.replies`, `limit: 1`). A deleted reply recounts the root from the store when one range proves every reply from the root to the latest, else drops the count by one.
- **Index rows carry what the row shows.** `preview_json` holds the sender, the stripped text, the sender id (so a rename applies at read time) and the first 240 characters of the root (the fallback title), so `topics.list` joins no `messages` row.
- **Recheck.** After a socket drop (`runSync` notes when it began) and at a warm boot (from `lastSyncAt`), `catchUp` runs `recheck` (`recheck.ts`, specs/catchup.qnt): the topics on screen, then the most recently active member topics, at most `recheckTopics`, each one history or replies page back to `recheckLookbackMillis` before the gap, on the background lane. The page merges as any page, except that a message without `reactions` has none. A message the store held when the page was requested, inside the page's span, that the page lacks becomes a tombstone (`writeDeleted` with a page source); one stored after the request is never inferred deleted, and a thread page leaves its root to Main's page. It first waits for the fetches outside the work permit (opened topics, roots: `trackFetch`) requested before it, so no older answer lands after its own and brings back a message it found gone. A drop during a catch-up is rechecked by the next; a failed catch-up keeps the gap and runs again after the rate limit that stopped it or `bootRetryMillis`.
- **Discovery.** `search.modules.messages` with `is:thread after:<day before the gap>`, `sort=timestamp` newest first (without it Slack orders by relevance and the pages are a sample), at most three pages of 50, members-only. The exact match cutoff starts five minutes before `lastSyncAt`, so a reply Slack indexes late, or whose Slack timestamp trails Juno's clock, remains eligible on the next sweep. A match is a partial message (`MergeSource` `partial`): it creates rows the store lacks, fills stub roots and moves counters, but never replaces stored content, because it carries no files, no reactions and sometimes no blocks. A row a match created or filled has `messages.partial = 1` until a page or an event brings the whole message; opening a thread counts only full replies as stored, so a reply discovery found is fetched in full, reactions included, when its thread opens (specs/discovery.qnt `openedHasFull`). A reply's thread comes from `thread_ts` or from the `thread_ts` of its permalink (live, matches carry no `thread_ts`: items hold their messages in `messages[]`, research section 10); a match that names no thread is dropped. A failed sweep is logged and does not fail the boot or catch-up; `lastSyncAt` stays where it was, so the next sweep searches the same gap. The sweep also runs at the end of a cold boot over the window, so Main knows about replies to roots older than the window. `discovery: 'history'` is the fallback of architecture 5.3 (replies since the stored ones for roots whose `latest_reply` moved).
- **Cold boot.** The order is in `boot.ts`'s header and architecture 5.2. A boot that fails half way is retried after 30 s and skips the conversations whose synced range already covers the window (seen live: the retries took 25 s instead of 6 minutes). A conversation whose history Slack refuses (`SlackRejected`, for example deleted between `counts` and the call) is skipped instead of failing the boot. Membership: an incremental `counts` entry for a conversation the store has never seen (joined while the socket was down) is fetched with `conversations.info` first. `channel_rename` and `group_rename` carry a partial object and patch only the name.
- **Users.** Ids referenced by messages and DMs with no `users` row are fetched from the edge in chunks of 100 after the history pages; the topics whose preview waited for a name are re-indexed when the users land. The call carries the flags Slack's client sends (`include_profile_only_users`, `check_interaction`); without them the edge lists Slack Connect people it has only a profile for in `failed_ids`. Ids in `pending_ids` (those same people, while the edge fetches them) are asked again up to three times, 0.5, 1 and 1.5 s apart, then left for the next sweep. Ids in `failed_ids` or `invalid_ids` are not asked for again in the session. The edge sends no photo urls, only `avatar_hash`, so a user's photo urls are built from `client.userBoot` `team.avatar_base_url` (kept in `sync_state.avatar_base_url`), the team, the user id, the hash and the size (research section 10, "Profile photos"). The background sweep at the end of a boot or catch-up also asks, once a session, for stored users with no photo, so rows written before this fill in without a re-sync. The user groups the user belongs to (`userBoot.subteams.self`) count as mentions; `subteam_self_added`/`subteam_self_removed`, and `subteam_members_changed` naming the user, change that list from then on.
- **User groups.** Message text carries a bare `<!subteam^S…>` (research section 3), so `syncUsergroups` reads `usergroups.list` with `include_disabled` on the background lane beside the first boot (and after a forced reboot), once per boot, into the `usergroups` table (deleted groups keep their row and handle). `subteam_created` and `subteam_updated` events write the group too. A write that changes nothing fires no invalidation. A preview that met a group with no row records its topic in `ctx.usergroupTopics`; those topics are re-indexed when groups are written.
- **Emoji.** After boot reaches live, `syncEmoji()` reads every edge `emojis/list` page on the background lane and replaces the `emoji` table, then invalidates `emoji`. Both cold and warm boots refresh it. A failed refresh keeps the old table and logs only the error tag. Each result's `value` is an image url, `alias:<name>`, or per-vendor urls (observed live 2026-10-16, research section 3); `customEmojiRow` stores it as `url` and `alias_for`.
- **Live shapes.** `hello.start` is a boolean live and is not read; `reconnect_url` arrives after `hello` and again every 30 to 60 s, and the socket keeps the latest one; `getView` pages by `current_ts = latest_reply` of the last root on the page; `unread_replies` is absent when nothing is unread. The fake sends the same shapes.
- **Late thumbnails.** A file that is not ready to show (`isReady`: a copy whose `mimetype` is missing or empty, an image without `thumb_*` or a size, a video without its poster, or a partial `check_file_info` copy; an image or a video is told by `mimetype`, then Slack's `filetype`, then the name, `fileMediaKind` in `@juno/domain`) is asked about with `files.info`; if that fails or returns an incomplete file, the same attempt re-reads its exact message with `conversations.history` (Main) or `conversations.replies` (a reply, using its stored root ts), with inclusive oldest/latest equal to the message ts, on the background lane after 1, 3, 10 and 30 s at most (`run/files.ts`; `fileRetryMillis` defaults to 1,000, and test timing profiles shorten it without changing the four attempts): on a message written less than a day ago, and on the newest 200 stored messages of a topic the user opens, whatever their age (`queueTopicFiles`, from `TopicFetcher.open`). `file_shared`, `file_change`, `file_created` or `file_thumbnail_generated` for it asks at once. A file whose tries ran out is asked about again only when an event names it or its topic opens. Both calls use the same bounded attempt; recovery does not depend on `files.info` being supported. The answer is written into every stored message that carries the file (`storeFileInfo`), and the merge lets a file only get fuller (`keepFuller`). Live, a shared image's echo has no thumbnails (research section 3, "Files").
- **Errors.** `SlackAuthRequired` from any step (the socket, a boot, a catch-up, the sweep, a root fetch) ends the sync; the catch-up and reboot fibers run in a `FiberSet` that `runSync` joins, so their failure reaches the engine. Any other boot failure retries after 30 s with the phase at `offline` when the network failed (a `SlackTransportError` with no HTTP status: no connection, DNS or a timeout), else at `failed` with a `SyncFailure` (error tag, Slack method, Slack's error code or the HTTP status; `bootFailure` in `run/boot.ts`); any other catch-up failure is logged and the phase settles. A store error while applying one event is logged and the event is skipped, so one bad frame does not end the stream.

## Opening a topic

`open.ts`, called only by the engine's `topics.open`, `messages.loadOlder`, `messages.loadNewer` and `messages.loadAt` commands and by the reconnect step, never by a live query (architecture 5.5, M4):

- A thread: `conversations.replies`, pages of 100, at most 500 messages (`OPEN_FETCH_MAX`), proven back to the root, or to the read pointer for a thread longer than that, so every unread reply is stored: the first time from there on, every page landing in one transaction once the last is in, so the window that stood in with what the store held turns proven in one step; later the replies after the newest range, then those from there up to it when it does not reach back that far. Each page records its range and re-indexes the thread in its transaction, even when it changes no message. A reply stored from a search match (`partial`) is brought in full by the page that covers it.
- Main: `conversations.history` since the newest synced range (one page of 50 when there is none), then older pages until history reaches the read pointer, at most 500 messages. Each page records its range through `syncedRanges.add` and invalidates that channel’s coverage, even when it changes no message. This happens in the same transaction as its messages, so the "N new" count is exact once the range reaches the pointer. A page with nothing more and no `oldest` bound covers back to the start of the conversation (`HISTORY_START`).
- Older pages: a Main page is fetched only when the synced range that holds the first row has fewer than 100 stored messages before it. A thread step (`messages.loadOlder`) is fetched only when no range covers the first row and the message below it: a page forward from the top of the range below the gap (the root without one), and when it does not reach the first row, a page from a time bound that should hold about 90 of the gap's replies at the density the first page measured. At most two calls; no count is used. Newer replies (`messages.loadNewer`, `fetchNewer`): one page forward from the last row, when no range covers it and the next stored reply, or the latest reply; up to where the next proven range starts, else to the end while the socket is up, else to the latest reply. A window with no anchor shows the stretch around the newest row a page proved, so a reply stored across a gap (by search, or by an event after a drop) waits beyond its end instead of taking its place.
- A jump to one message (a search match, a link, a cited reply) that the store lacks in full: in a thread, one `conversations.replies` page from the newest reply stored in full before it up to it; when that page does not reach it, one more page that starts at it. So a reply any distance into a long thread costs at most two calls. Each page records its range; the replies left between stay unknown, and the topic view stops at them until it scrolls there. In Main, the one history page that ends at the message, recorded as a synced range.
- Who reacted: `TopicFetcher.reactors(channel, ts)` (`whoReacted.ts`) shares one pending `reactions.get` with `full` on the interactive lane for each message. Closing the last caller cancels it. Its answer replaces the reaction rows only if the message version and reaction rows still match their pre-request snapshot; an undefined return asks the open dialog to retry. Otherwise it returns the stored reaction snapshot. A rate limit is not retried on the background lane; an auth failure ends the sync. Truncated pages replace older full lists even with the same count, because the omitted people may have changed. See `specs/reactors.qnt`.
- `runSync` hands the engine a `TopicFetcher` that runs these on the interactive lane in the sync's context, so stub roots it finds are fetched and unknown senders named in the background. When Slack rate-limits the call, the same fetch is queued on the background lane and the caller gets the error. After each reconnect and sweep, the topics `openTopics` names (the engine's open tabs) are fetched again.

## Follow state against `specs/follow.qnt`

The rule in one place, with the spec action or property each part implements. `observed_at` and `updated_event_ts` are columns of `thread_subs`; `setThreadSub` (`src/write.ts`) applies them. The spec models the current command seam, including its failures; it does not certify application code.

`acceptedUnfollow` (an Unsubscribe Slack accepted is never undone by older information) is one of the checked invariants. Each of its three guards has a bug schedule that switches it off and must still produce a counterexample: a delayed pre-command followed event after the answer (`lateEventBugStep`), a followed page requested during the command and answered after it (`pendingPageBugStep`), and an accepted Unsubscribe whose answer and root lookup both fail, with the old fallback restoring the follow (`failedLookupBugStep`). ## Read state against `specs/readstate.qnt`

Juno's pointer (`topic_reads.last_read_ts`) is the state the sidebar shows. The rules are `observeServerRead` and the local marks in `@juno/domain` (`reads.ts`); `write/reads.ts` loads and stores their state. Two clocks, never compared: Slack's `event_ts` orders events (`last_server_event_ts`), Juno's clock orders fetches (`observed_at`).

## Known gaps

- Edits, deletes and reactions made during a disconnect or while the app was closed are repaired across cached ranges of conversations selected by counts mutation markers (below). The bounded ten-topic recheck remains a fallback for unavailable marker coverage. Conditional history/replies keep unchanged bodies out of repair responses. Uncached ranges are outside this repair.
- Search requests extra thread metadata and applies roots before replies within each page, avoiding a lookup when the root counters are present. Missing roots still need a lookup. Search fields remain partial: missing reactions never clear stored ones.
- A follow changed elsewhere during a drop, on a thread with no activity since the last sync, waits for the next window pass (at most an hour). A follow older than the window waits for its thread's next reply.
- The sweep reads at most 150 matches per gap; a longer outage in a busy workspace misses older thread activity until the next sweep or open.
- Read marks, posts, and edits, deletes, reactions and broadcasts (a reply also sent to the channel) have their own persisted workers in the engine (`markWorker.ts`, `send/worker.ts`, `send/actionWorker.ts`); follows still use the `Outbox` seam.

## Must not

- Render anything or call AI. It depends on `@juno/slack`, `@juno/store`, `@juno/domain` and `@juno/slack-schema` only.
- Write `topic_index` anywhere but `reindex.ts`, or increment a counter in place.
- Let a socket event move `synced_ranges`; only pages extend them.
- Import `effect/sql` or `effect/reactivity`; the store's services are the only way to the database.

## Quiet-window preference

`quietDays` is read before sync starts and observed by `run/window.ts`. An increase runs `window.ts` under the work permit, paging missing history on the background lane, then refreshing follows and discovery. A decrease cancels that pass and retains stored messages. Each page commits with its coverage; retries and restarts reuse it. `specs/quietwindow.qnt` models the coverage rule.

## Mutation repair after a gap

Full counts on reconnect and warm boot compare supplied `updated` and
`history_invalid` with observed markers using inequality, including backwards
moves. Missing baselines seed without a repair storm. Changed conversations
atomically enqueue cached ranges with the new observed markers. Ten-minute sweeps stage supplied markers as in-memory candidates. A later sweep
can promote a candidate only after a pong received after its counts response.
A disconnect discards candidates. A failed frame blocks its conversation for the
rest of the session (all conversations if the frame has no conversation id).
The socket stamps frames before forwarding them to sync, so a queued older pong
cannot confirm a newer candidate. Partial rows preserve absent marker fields.

After `live`, at most ten background pages run, one per queued range. Main and
cached replies start 24 hours before the gap began; old roots do not extend Main
and roots without cached replies in range get no thread job. Jobs expire 24 hours
after enqueueing, not when their messages age. Selection interleaves conversations
before taking another range from the same conversation. Pending cursors and
failures persist and rotate behind unattempted ranges for the next catch-up or
sweep. `SlackRateLimited` leaves the job queued. Conditional versions come only
from `latest_updates`, separately from Message decoding. Unchanged ids count as
present. Absence is inferred only inside proven recent page bounds, excluding
thread roots and any `is_limited` response. `thread_not_found` drops the job. It tombstones cached replies within the job
bounds only if the root is already deleted in cache, including deletion proved
by the Main page. Hidden old history is not evidence of deletion. Repair does not certify outbox coverage.

All ten ordinary fallback pages still run before `live`, including topics queued
for repair. Missing markers or versions that fail to advance cannot suppress the
fallback. Counts cannot find uncached history. The ten-minute discovery sweep,
five-minute overlap and hourly follow repair are unchanged.

Incremental counts rows update only supplied fields. `{ id, last_read }` updates
the read pointer without clearing `latest`, `has_unreads` or `mention_count`.
Before this fix those rows failed decoding and aborted the sync cycle before
any counts could be merged; the retry kept using the old cursor.

Unchanged counts fields and server-version certificates do not write to the
cache. This keeps the existing quiet-sweep no-write guarantee with partial rows.

`write/huddles.ts` projects room frames and message room objects into durable `huddle_history`. Explicit ended-room participant history from full messages or room frames establishes a missed huddle; unknown history and partial search matches do not. Joins and ends accumulate without changing message, follow or read protocols.

The first acknowledgement of a locally recorded send marks its topic invalidation as `CommandWrite`, whether the answer, echo or lookup arrived first. This carries presentation provenance to live queries; it changes no reconciliation, retry or delivery rule.

# @juno/sync

Slack into the store. Cold and warm boot, thread discovery, the merge rules, socket event application, read-state seeding and `reindexTopics`. See `docs/architecture.md` sections 4.4, 5 and 6, and ADRs 0004 and 0011.

## Public API

- `runSync({ onPhase })`: the whole sync for one session, until interrupted. Needs the Slack client (`SlackApi`, `SlackEdge`, `SlackSocket`, `SlackSession`) and the store (`StoreWriter`, `StoreReader`, `Invalidation`) in its context, plus a `Scope`. It opens the socket first, boots cold (empty cache) or warm (`sync_state.boot` present), then stays live: every event is one transaction, a reconnect runs the catch-up, a discovery sweep runs every ten minutes. It fails only with `SlackAuthRequired`; the engine then ends the session.
- `SyncPhase`: `booting`, `catching-up { done, total }`, `live`, `offline`. `onPhase` is called on every change; the engine folds it into `engine.status`.
- `SyncConfig` / `syncConfigLayer({ ... })`: the quiet window, page sizes, sweep interval, `discovery: 'search' | 'history'`.
- `reindexTopics(ids, { me })`, `reindexAll`: the one writer of `topic_index`. Call it at the end of any transaction that touched a topic's messages, reads or coverage. `topicsOfMessages(rows)` gives the ids a set of message rows belongs to.
- `mergeMessage`, `mergeTombstone`, `mergeRootCounters`, `stubRoot`, `toMessageRow`: the pure merge rules, for tests and for the outbox work to come.
- `threadSub`, `setThreadSub`, `clearThreadSub`, `beginPendingFollow`, `endPendingFollow`, `readMessage`, `readState`: the writer-side reads and writes the engine's commands share with the sync, so a command's transaction uses the same rows and fires the same keys. `setThreadSub` takes a `ThreadSubSource` (`event`, `page` or `command`) and applies the ordering rule below.
- `syncKeys`: the invalidation keys the sync fires (`topics`, `{ topics: [id] }`, `{ messages: [topicId] }`, `conversations`, `users`, `team`, `channel_reads`, `thread_subs`, `{ topic_reads: [id] }`, `{ topic_overlay: [id] }`).

## What it decides

Beyond the architecture document, these are the rules the code settled:

- **Lanes.** `userBoot`, `prefs`, `counts` and the `getView` pages with activity inside the window (at a reconnect, since the store was last in step) run on the interactive lane (the sidebar is usable after them); the complete `getView` pass, history, replies, search and users on the background lane.
- **Membership.** `client.userBoot` is metadata only: live it lists every channel of the workspace without `is_member`, `last_read` or `latest` (research section 2), so `toConversationRow` never sets `is_member` and `upsertConversations` keeps the stored flag. `client.counts` decides: a full answer (cold and warm boot, no `counts_last_fetched`) replaces the member set with its entries (`replaceMembership`), an incremental one (reconnect) only adds (`setMembership`). Events keep it current: `channel_joined`/`group_joined`, `member_joined_channel` for self, `im_open`, `im_created`, `mpim_open`, `mpim_joined` set it; `channel_left`/`group_left`, `member_left_channel` for self and `channel_deleted`/`group_deleted` clear it; `im_close`/`mpim_close` only refresh metadata. The sidebar query, `activeConversations` and discovery all filter on `conversations.is_member`.
- **Read pointers.** The first time Juno sees a topic it takes Slack's pointer (`counts.last_read` for Main, the root's `last_read` for a followed thread). After that Juno's `topic_reads` is the state, and a server mark (a `*_marked` event, or a pointer in `counts` or `getView` seen after a disconnect) applies through the conflict rule of architecture 5.6; `counts` is stamped with the time before the call, so a mark that lands while it is in flight wins. A thread the user does not follow has no pointer in Slack: at cold boot it starts read at its latest reply before the boot started, so a first boot does not light up every old thread while a reply during the boot stays unread; one discovered later starts unread.
- **Follow state.** `thread_subs` is Slack's follow flag for a thread and decides whether the thread is a sidebar row. Every source writes it: `getView` rows; a root on a history, replies or lookup page, which carries `subscribed` (`true` sets the flag, `false` clears a stored follow, a root without the field changes nothing, and `false` for a thread Slack never mentioned stays unknown so the sidebar's mention rule still applies); `thread_subscribed`, `thread_unsubscribed` and `thread_marked` events; a reply by the user and a reply to the user's own root (`followOnReply`), because Slack follows for you in both cases; and the engine's commands. The order is the rule of specs/follow.qnt: an event applies unless an event with a newer `event_ts` has been applied (`updated_event_ts`); a page applies only when its request started after the row was last observed or changed (`observed_at`, Juno's clock), so a page in flight during an unfollow cannot bring the follow back; a command always applies and stamps `observed_at`; while a command on the thread is pending (an `outbox` row of kind `follow`) events and pages do not change the flag but are noted, and the command looks the root up afterwards. The boots and every catch-up page `getView` back to the window or to the last moment the store was in step. A complete pass (`followPass`) pages to the end on the background lane and then looks up every stored follow the complete list left out by its root; absence from a page alone never means unfollowed. It runs after each boot and then with a catch-up or sweep at most once an hour (`followPassMillis`; every catch-up when the engine runs against the fake), because a workspace can follow thousands of threads: the measured account follows about 2,570, 258 calls. A thread older than the window gets only its follow flag from that pass. A follow changed elsewhere during a drop, on a thread with no new activity, is found by the next complete pass.
- **Exact counts.** A thread's `unread_count` is exact when every reply since the read pointer is stored: `thread_cursors.complete_from` records where coverage starts (a thread view stores every unread reply, so it is Slack's pointer), and a reply received as an event keeps it. A socket drop clears `complete_from` for threads the user does not follow, because replies during the gap may never arrive; followed threads keep it, since the reconnect reads every followed thread with activity since the store was last in step. "Complete" means the stored replies reach the root's `reply_count`; `replies_complete` is written but not trusted for the count. Main is exact when a synced range covers everything since the pointer; otherwise the row carries `has_unreads` as a floor of one and `unread_exact = 0` (a dot, not a number).
- **Counters.** A root's `reply_count` and `latest_reply` take the maximum of what pages and events say and never go below the replies the store holds. A reply from a page that the root's counters never saw (a `message_replied` lost during a drop) queues a refetch of the root (`conversations.replies`, `limit: 1`). A deleted reply recounts the root from the store when the thread is complete, else drops the count by one.
- **Index rows carry what the row shows.** `preview_json` holds the sender, the stripped text, the sender id (so a rename applies at read time) and the first 240 characters of the root (the fallback title), so `topics.list` joins no `messages` row.
- **Discovery.** `search.modules.messages` with `is:thread after:<day before the gap>`, `sort=timestamp` newest first (without it Slack orders by relevance and the pages are a sample), at most three pages of 50, members-only. A match is a partial message (`MergeSource` `partial`): it creates rows the store lacks, fills stub roots and moves counters, but never replaces stored content, because it carries no files, no reactions and sometimes no blocks. A reply's thread comes from `thread_ts` or from the `thread_ts` of its permalink; a match that names no thread is dropped. The sweep also runs at the end of a cold boot over the window, so Main knows about replies to roots older than the window. `discovery: 'history'` is the fallback of architecture 5.3 (replies since the stored ones for roots whose `latest_reply` moved).
- **Cold boot.** A boot that fails half way is retried after 30 s and skips the conversations whose synced range already covers the window. Membership: an incremental `counts` entry for a conversation the store has never seen (joined while the socket was down) is fetched with `conversations.info` first. `channel_rename` and `group_rename` carry a partial object and patch only the name.
- **Users.** Ids referenced by messages and DMs with no `users` row are fetched from the edge in chunks of 100 after the history pages; the topics whose preview waited for a name are re-indexed when the users land. Ids the edge reports in `failed_ids` (bots, Slack Connect users) are not asked for again in the session. The user groups the user belongs to (`userBoot.subteams.self`) count as mentions.
- **Live shapes.** `hello.start` is a boolean live and is not read; `reconnect_url` arrives after `hello` and again every 30 to 60 s, and the socket keeps the latest one; `getView` pages by `current_ts = latest_reply` of the last root on the page; `unread_replies` is absent when nothing is unread. The fake sends the same shapes.
- **Errors.** `SlackAuthRequired` from any step (the socket, a boot, a catch-up, the sweep, a root fetch) ends the sync; the catch-up and reboot fibers run in a `FiberSet` that `runSync` joins, so their failure reaches the engine. Any other boot failure sets the phase to `offline` and retries after 30 s; any other catch-up failure is logged and the phase settles. A store error while applying one event is logged and the event is skipped, so one bad frame does not end the stream.

## Follow state against `specs/follow.qnt`

The rule in one place, with the spec action or property each part implements. `observed_at` and `updated_event_ts` are columns of `thread_subs`; `setThreadSub` (`src/write.ts`) applies them.

| Rule | Code | Spec |
| --- | --- | --- |
| A command writes the flag and a pending `outbox` row (kind `follow`) in one transaction, before the Slack call, and stamps `observed_at` with its own time. The stamp does what the spec's per-command `epoch` does: a fetch started before the command no longer applies. | `engine/topics/commands.ts` `setThreadSubscribed`, `beginPendingFollow` | `localChange`, `epoch`; `pendingIntentWins` |
| Commands on one thread run one at a time. | `Outbox.exclusive` | "at most one pending command" assumption |
| While the row exists, events and pages about the thread do not change the flag; they mark the row `seen`. | `notePendingFollow` | `deliver`, `finishFetch` with the thread pending (`seen`, `seenAt`) |
| After success, a `seen` row makes the command look the root up and apply its `subscribed`. | `endPendingFollow`, `refresh` | `acknowledge` (the spec allows "refresh after acknowledgement" instead of comparing `seenAt` with the acceptance stamp) |
| After a final failure the command always looks the root up and applies it; a `false` after a failed first Subscribe is stored as "Slack said nothing" again. | `refresh(previous, true)` | `reject`, `finishFetch` kind `failure`; `failedCallReverted` |
| An event applies unless one with a newer `event_ts` already did; it stamps `updated_event_ts` and `observed_at` (arrival on Juno's clock). | `setThreadSub` `event` | `deliver` with its guard |
| An event without `event_ts` changes nothing and queues a root lookup. `thread_marked` without `subscription.active` changes no follow. | `events.ts` | "an undated event needs a fresh lookup"; a missing follow field makes no change |
| A page (a `getView` row, a root on a history or replies page, a root lookup) applies only when its request started after `observed_at`, and then stamps it. A root without `subscribed` changes nothing. | `setThreadSub` `page`, `applyRootSubscription` | `finishFetch` guard (`f.at > seenAt`); `acceptedUnfollow` |
| The complete pass pages `getView` to the end. A stored follow (in a conversation the user is in) that the complete list left out, and that was not observed since the list was requested, is looked up by its root. A partial list concludes nothing. | `followPass`, `loadThreadViews`, `probeUnlisted` (`boot.ts`) | `startScan`, `requestPage`, `advancePage`, `finishScan`, `probeAbsent`; `quietAgreement`, `drainBound` |
| A reply by the user follows the thread, from its own message event. | `followOnReply` | `reply` |

Where the code and the spec differ:

- **Two clocks, not one.** The spec orders events, fetches and commands with one change stamp. Slack's `event_ts` and Juno's request times come from different clocks, so the code orders events only against events (`updated_event_ts`) and pages only against Juno's own observations (`observed_at`). An event older than a page that already applied can still apply; on one ordered socket that only happens for an event Slack sent before the page's snapshot and delivered after it, which the next event or pass corrects.
- **No retry yet.** The spec's `retry` keeps the intent after a timeout. The seam treats every failure as final and looks the root up, which keeps Slack's answer if Slack had accepted the call. If that lookup fails too, the previous state is put back while the row is still the command's own write (a compare and swap); the spec has no such fallback. The next complete pass corrects it.
- **Unknown is a third value.** The spec's flag is 0 or 1. The store also has "Slack said nothing" (no row), which the sidebar's mention rule needs; a root's `false` never creates a row.
- **Not every catch-up is complete.** The spec's recovery pages to the end on every reconnect. The code does that at most hourly (after each boot, and with a catch-up or sweep when the last pass is older than `followPassMillis`); in between, a catch-up reads only the followed threads with activity since the last sync. An unfollow made elsewhere during a drop, on a thread with no new activity, stays until the next complete pass. Measured live: a complete pass is 258 calls on an account that follows about 2,570 threads.
- **The moving cursor.** A thread that gains activity while a pass is paging can move ahead of the cursor and be missed by that pass. The spec asks for another complete pass once quiet; the code's next one is the next due pass.

## Known gaps

- Edits, deletes and reactions that happen during a disconnect are recovered for threads by the search sweep (text) and otherwise only when the topic is opened (M4's refresh of the visible window). ADR 0011's `cached_latest_updates` path waits on the live smoke.
- A message first stored from a search match has no reaction state, files or blocks until a page or an event brings it.
- The complete follow pass costs one call per 10 followed threads (258 on the measured account) on the background lane, so it runs at most hourly; an unfollow during a drop on a quiet thread waits for it.
- The sweep reads at most 150 matches per gap; a longer outage in a busy workspace misses older thread activity until the next sweep or open.
- `emojis/list`, the outbox, read-state mirroring and send reconciliation are later milestones; the tables and the conflict rule are in place.

## Must not

- Render anything or call AI. It depends on `@juno/slack`, `@juno/store`, `@juno/domain` and `@juno/slack-schema` only.
- Write `topic_index` anywhere but `reindex.ts`, or increment a counter in place.
- Let a socket event move `synced_ranges`; only pages extend them.
- Import `effect/sql` or `effect/reactivity`; the store's services are the only way to the database.

## Testing

`pnpm --filter @juno/sync test` runs the merge rule table (`test/merge.test.ts`). The sync itself is tested end to end in `packages/engine/test`: `sync.test.ts` (cold boot rows, exact call budgets, membership from counts and events, warm boot, realtime, read marks, reopen, edits and deletes, offline and back, follow state against stale pages and pending commands, every `getView` page, search matches, an expired session found by the catch-up, failed commands, cold boot details, workspace events), `reconnect.test.ts` (what changed offline, with an exact call budget, and events that land while a page is in flight), `convergence.test.ts` (seeded random events with drops, follows and unfollows; the store and the follow state equal the fake's and a full re-index changes nothing) and `plan.test.ts` (the sidebar statements never scan the guarded tables). The follow protocol they exercise is specified in `specs/follow.qnt`. `JUNO_BENCH=1` adds the large-seed benchmark in `test/bench`. `JUNO_LIVE=1 pnpm sync:live` runs the real cold boot read-only against your workspace into a temporary directory and prints aggregate numbers (`docs/development.md`, "The live sync dry run").

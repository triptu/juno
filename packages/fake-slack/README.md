# @juno/fake-slack

A fake Slack for tests and development: an HTTP and websocket server that speaks the web client's protocol (`docs/research/slack-data-access.md`), with a control API to make things happen from "another client". See `docs/architecture.md` sections 2.2 and 13.

Live Slack wins. Each behaviour the fake copies should name the live check it comes from and its date, as the `files.info` and `client.counts` notes below do. The fake has been kinder than live Slack before, which hid bugs. Before a fix, a performance claim or a "live bug" report depends on behaviour the fake has not been checked against, run one read-only live probe (`bun run probe:live`). When the fake and live disagree, change the fake to match live, and keep the old behaviour behind a test control if a test needs it.

## Public API

```ts
const fake = await startFakeSlack({ port?, now?, seed? })
const { url, token, cookie, teamId, userId } = fake.credentials()
await fake.close()
```

- `chat.update` keeps the `blocks` a client sends, a table or other block it did not edit among them, as Slack stores what a client posts; without `blocks` it makes them from `text`. With `reply_broadcast=true` and no text or blocks it sends an existing reply to the channel, as observed live: the same message becomes `thread_broadcast` with its `root`, one `message_changed` announces it, and the answer carries the message without `ts`. Text or blocks with it is `no_dual_broadcast_content_update`; a root, a message outside a thread or a reply already sent is `cant_broadcast_message`.
- Server: multipart `POST /api/<method>` with the `token` field and the `d` cookie, `ok: false` errors, the edge API with JSON bodies, uploads, and the event socket with `hello` and ping.
- Uploads follow the official client's composer flow: `files.getUploadURL` gives `{ upload_url, file }`; the bytes go to `upload_url` as multipart with one field named `file` (a raw body works too; no token or cookie); `files.completeUpload` sets titles; `files.share` posts one message by self with the files, `client_msg_id`, blocks or a plain `comment`, in a channel or a thread (`broadcast` for a reply broadcast), with the same socket events as `chat.postMessage`. `files.share` reads `files` comma-joined, as the client sends it, or as a JSON array. `files.info` answers `unknown_method`, as observed live. Errors: `file_not_found` (unknown id or no bytes yet), `channel_not_found`, `not_in_channel`, `thread_not_found`.
- File objects carry the type (image magic bytes first, then the part's Content-Type, then the extension), the size, video files also carry `mp4`, `hls`, `thumb_video` and `duration_ms`; snippet files carry `preview` and `lines`. `files.info` returns the file by default, as the 10-18 live check did. `setFilesInfoSupported({ supported: false })` makes it answer `unknown_method`, as reported for the 10-15 probe; pass `true` to restore it. This control is also available over HTTP. For PNG, JPEG, GIF and WebP the original size read from the header plus Slack's thumbnails: square `thumb_64`, `thumb_80`, `thumb_160`, `thumb_360` always, and each of 480, 720, 800, 960 and 1024 only when the long side is above the size before it, each fitted to its box and never upscaled. Thumb urls serve the original bytes. `GET /files/<id>/<name>` requires the `d` cookie (no cookie or a bearer token alone redirects to sign-in) and serves the bytes; `?download=1` adds `content-disposition: attachment`.
- The default seed has an image (`early-access-flow.png`, 960 x 640), a PDF (`q4-plan.pdf`), an invented video and an invented Markdown snippet in the #product thread "Proposal: cut offline mode and public API v3 from Q4", exported as `EARLY_ACCESS_PNG` and `Q4_PLAN_PDF`.
- Who reacted: pages, `message_changed` events and `reactions.get` list at most `REACTORS_LISTED` (25) people per reaction, with `count` exact; `reactions.get` with `full` lists everyone. 25 is a fake choice: live, every reaction up to a count of 25 listed everyone, and where Slack starts to cut is not known (research section 10, "Who reacted"). `seedManyReactions({ channel?, user?, text?, silent? })` posts a message with 40 people on 👍 (you third), 28 on 🎉 and ten more emoji, four of them custom (`hello_juno` an alias), from 39 new people with long names, and returns `{ channel, ts, text, reactions, names }`. The reactions send no socket events, so the app stores them from the next page of the channel (opening its Main); without `silent` the post itself does. Also a control over HTTP.
- `usergroups.list` returns every group, deleted ones (`date_delete` > 0) only with `include_disabled`, with no `users` and no paging, as live. The default seed has two live groups and one deleted; messages mention them as the bare `<!subteam^S…>` Slack sends.
- Channels (research `slack-channels.md`, live 2026-10-27): `conversations.create` checks the name as Slack does with `validate_name` (`invalid_name_required`, `invalid_name_maxlength`, `invalid_emoji_not_allowed`, `invalid_name_specials` for uppercase, spaces and punctuation, `invalid_name_punctuation`, `name_taken` among channels) and sends `channel_created` first for a public channel, then `channel_joined` with the whole channel and `member_joined_channel` to self, for a private one too. `conversations.rename` sends `channel_rename` or `group_rename`; #general is `not_authorized`. `conversations.invite` with `force` adds whom it can and lists the rest in `errors` (`user_not_found`, `already_in_channel`, `cant_invite_self`), and refuses the call when no one could be added; without `force` one bad user refuses all. `conversations.kick` removes one user (`cant_kick_self`, `cant_kick_from_general`, `not_in_channel`). `conversations.members` pages by cursor. Each change sends `member_joined_channel` or `member_left_channel`. A DM, a group DM or an archived channel is refused.
- Drafts (`src/drafts.ts`, `src/features/drafts.ts`), as observed live on 10-27 (research `slack-drafts.md`): `drafts.list` (newest first, `is_active`, at most 100 a page with `has_more`, `next_ts` exclusive), `drafts.create`, `drafts.update` and `drafts.delete`. One attached draft per channel or thread: a second create there answers `attached_draft_exists`. Deleted and sent drafts stay as records; updating one answers `draft_update_invalid`, deleting one `draft_delete_invalid`, an unknown id `draft_not_found`. An update or delete whose `client_last_updated_ts` is not plausible epoch milliseconds (below 2e9, as `0` or a time in seconds) answers `draft_has_conflict`, as live; any later value is accepted, in any order. Every write sends `draft_create`, `draft_update` or `draft_delete` to every socket, the writer's too, and `chat.postMessage` or `files.share` with `draft_id` (the draft's id or its `client_msg_id`) retires it with `draft_send`. Controls for another device: `putDraft({ channel, threadTs?, text, files?, at? })` types in the place's attached draft (an update, or a new one; `files` attaches that many invented files, and `text: ''` with files is a draft of files alone; `at` backdates the write) and `removeDraft({ channel, threadTs?, sent? })` clears or sends it; `draftText(channel, threadTs?)` reads the live draft's text and `draft(channel, threadTs?)` its text and file ids.
- `presence.set` accepts `active` or `away` and emits `manual_presence_change` for the self user.
- Presence as colleagues see it (`selfPresence()`): the self user is active while one of their sockets is open, their `manual_presence` is `active` and a `tickle` came within `AUTO_AWAY_MILLIS` (10 minutes on the fake's clock; Slack's real timeout is unknown). When that changes, sockets subscribed to the self user with `presence_sub` get a `presence_change`, as for anyone else; the fake checks at each `tickle`, socket open and close, `presence.set` and clock change, so the timeout shows when a test moves the clock past it. Every frame a client sends other than `ping` is recorded in `received`, apart from `calls`.
- Other people's presence: `setPresence({ users, presence })` sets it (everyone else starts away). Each `presence_sub` replaces its socket's list and is answered at once with the current presence of those users, one `presence_change { presence, users }` batch per value; later changes reach each subscribed socket as one batch. `presenceSubscriptions()` lists the ids the open sockets follow. As live (research section 3, Presence, 2026-10-21).
- Profile status: `users.profile.set` with a `profile` of `status_text`, `status_emoji` and `status_expiration` sets self's status, and `setStatus({ user, text, emoji, expiration?, quiet? })` sets anyone's, as from their own client; both change the stored user (`updated` too) and send every socket a `user_change` with the whole user, except a `quiet` one, which only a later `users/info` carries (as for a client Slack does not tell). That Slack sends self a `user_change` after its own `users.profile.set` is how the official client is written to expect it (research section 3, "Profile status"), not a live observation. The fake never clears an expired status itself.
- Controls, each also reachable as `POST /control/<name>` for tests that drive a built app: `injectMessage`, `editMessage`, `deleteMessage`, `markRead`, `markThreadRead`, `followThread`, `unfollowThread` (self, from another client), `setSelfUsergroups`, `putUsergroup` (adds or changes a group; emits `subteam_created` or `subteam_updated`), `addReaction`, `removeReaction`, `addGroupDm` (a group DM with given people and no messages; `open: false` makes it closed), `joinChannel`, `leaveChannel`, `renameChannel`, `typing`, `emitFrame`, `dropSocket`, `goOffline` and `goOnline` (sockets are dropped and refused in between, so events reach no client), `force429`, `clear429`, `forceError` (the next calls of a method answer `ok: false` with a given error, before the handler runs), `clearError`, `holdNext` (the next calls of a method run their handler, or take their forced error, but answer only on `release`, so a test can land events while a page is in flight; with `before` they wait before the handler runs, so Slack has not seen them yet), `release`, `heldCount`, `heldCalls`, `loseResponse` (the next calls of a method run their handler, then the connection closes with no answer: an accepted call whose answer was lost), `holdFrames` and `releaseFrames` (frames of given types wait, then are sent in order or dropped, so an event can arrive late or never), `heldFrames`, `delayFiles` (file downloads answer after a delay, so images arrive late), `setLatency` (every Web API and edge call waits a fixed time before it runs, like a real network; also the `latencyMillis` start option), `failUploads` (the next upload POSTs answer HTTP 500 and keep nothing, so a client can fail and retry), `failFiles` (the next file downloads answer a status, 503 unless given, with no bytes, and `Retry-After` seconds on a 429, so a client can show a failed picture and retry; file downloads are recorded in `calls` with kind `file`, the file id as the method), `holdThumbnails` (files uploaded from now on, and `injectMedia` files, have an empty `mimetype` and `filetype`, no thumbnails, no poster and no size on the message and in `files.info`, as a fresh upload's echo has live before Slack processes it) and `releaseThumbnails` (the held files get them, stored messages too, with a `file_thumbnail_generated` frame each; `event: 'file_change'`, `'file_created'` or `'none'`), `injectMedia` (another user's message with images and videos of given sizes; a video has a PNG poster at `?thumb=video`, `thumb_video` with its size and `mp4`; with `partial`, the socket event carries each file as Slack's partial copy, `file_access: "check_file_info"`, while history and `files.info` have it whole), `injectFiles` (another user's message with files the media viewer opens, by kind, from `src/fileSamples.ts`: a 12-page `pdf`, an `html` email export with a `<script>` that marks the page and a tracking pixel, a `markdown` snippet (`mode: "snippet"`, a `preview` cut short with `preview_is_truncated`, `lines`), a 40-column `csv`, a `json` file, a 2,000-line `log`, a 5-minute `audio` WAV with `duration_ms`, a `voice` clip (`subtype: "slack_audio"`, `aac` at `?aac=1`, the same bytes) and a `zip`; each served with its type on `GET /files/<id>/<name>`; `name` and a clip's `seconds` can be set; registered by `src/features/files.ts`), `setPresence`, `setStatus`, `presenceSubscriptions`, `expireSession`, `advanceClock`, `setNow`, `resetCalls`.
- Where the fake is stricter than it looks, because real Slack is (research sections 2 and 10): `subscriptions.thread.getView` returns at most 10 threads per page whatever `limit` says; `search.modules.messages` orders by relevance (a stable shuffle) unless asked for `sort=timestamp`, pages by number without a cursor, and includes `thread_ts` and root `reply_count` when `extra_message_data=1` (otherwise a reply names its thread only in the permalink), and carries files, reactions, attachments, bot profiles and extracts (with highlight markers when requested), plus global From/In facet counts; it omits the module-level `total` field and honours only page counts 20, 50 and 100; `client.counts` with `counts_last_fetched` returns `{ id, last_read }` for unchanged conversations and full rows for changed ones; a reply by self follows the thread and sends `thread_subscribed`; `channel_rename` and `group_rename` carry a partial channel object (`id`, `name`, `name_normalized`, `created`).
- In-process only, for tests that choose the order in which Slack decides each call (the conformance replay, `packages/engine/test/conformance`): `gate(where)` stops every API call `where` matches twice, before its handler runs and before its answer; `gated()` lists the waiting calls, each with one id for both stops; `decide(id, decision)` runs, refuses (`{ error, status?, retryAfter? }`) or drops a call at its first stop, and answers or loses it at its second; `gate()` with no argument lets waiting calls go on. `holdFramesWhere(where)` and `releaseFramesWhere(where, drop)` hold and send, or drop, the frames a predicate picks.

- `demoSeed` (with `teamName: DEMO_TEAM_NAME`) is an invented company, Kestrel, in an ordinary week, for screenshots and recordings (`bun run web --demo`): ten channels, two DMs and a group DM, unread threads, mentions, questions waiting on you and two design mocks drawn in code (`src/seeds/demoImages.ts`). `seedFrom(workspace, avatarBase, data)` builds a workspace from people, groups, prefs and conversations, as both seeds do. `teamName` renames the workspace for any seed.
- A default seeded workspace (`PEOPLE`, `CONVERSATIONS`); replace it with the `seed` option. It includes public channels the self user is not a member of (`members` without `SELF_ID`), because the real `client.userBoot` lists every channel of the workspace.
- `conversations.join` and `conversations.leave` (`src/features/membership.ts`) send self `channel_joined` or `channel_left` and everyone `member_joined_channel` or `member_left_channel`, as the `joinChannel` and `leaveChannel` controls do for another client. They refuse as Slack does (research section 3, "Browsing, previewing, joining and leaving channels"): joining a channel that is not public, `method_not_supported_for_channel_type` (seen live on a private channel); an archived channel, `is_archived`; #general, `cant_leave_general`; the last member leaving a private channel, `last_member` (seen live). A repeat join answers `already_in_channel: true`, and leaving a channel you are not in `not_in_channel: true`, as Slack's public reference says. `conversations.history` reads a public channel you are not in, as it does live; there is no browse method, since Juno lists channels from `client.userBoot`.

Which events Slack does send then is not known. `conversations.*` and the `channel_joined` family return the fuller channel object with `is_member`. The socket sends `hello` with `start: true`, then a complete `reconnect_url` after 200 ms and every 30 s.
- `bun run --cwd packages/fake-slack start` runs it on its own.

## Features

Add a module in `src/features/` and one entry to the `features` list in `src/features/index.ts`. Each module exports `{ methods, controls } satisfies FakeFeature` (from `src/features/registry.ts`). Methods use the existing `Handlers` type, keyed by `MethodName` from `@juno/slack-schema`; the merged map must cover every method. Controls take `(fake, input)` and return their result. Control inputs keep the existing HTTP boundary cast.

Startup merges both maps before opening a port and throws on a duplicate method or control name. `reactions.ts` is the small example, and `files.ts` one with controls only: `reactions.add`, `reactions.remove`, `reactions.get`, `addReaction`, `removeReaction` and `seedManyReactions`. `drafts.ts` registers the `drafts.*` methods and the `putDraft` and `removeDraft` controls. The remaining methods stay in `methods.ts`, registered by `core.ts` alongside the remaining controls. Public in-process controls stay on `FakeSlack`.

## Must not

- Import the engine, the client (`@juno/slack`) or any UI package. It depends on `@juno/slack-schema` only, and encodes its responses with those schemas so it cannot drift from the client.
- Be imported from `src` of another package. It is a `devDependency` for tests (`testDeps`).
- Contain real Slack tokens, cookies or message content. Fixtures are invented.

## Testing

The Slack client and engine tests exercise the fake through real HTTP and websockets: pagination, posting and echoes, uploads, reconnects and mutation recovery. Test the real client against this boundary; do not add tests of the fake itself. Recorded Slack responses and live research establish the protocol shapes.

`holdNext`, `heldCount` and `release` also cover edge methods using the `edge:` prefix, for example `edge:users/info`. This lets desktop tests delay sender resolution independently of history. Use `file:bytes` to hold thumbnail or download bytes until the test explicitly releases them, and `picture:small`, `picture:large` or `picture:<file name>` to hold Juno's picture files.

`unfurlFixtures(base)` supplies invented X image/text posts, failed images, YouTube, GitHub, Google Docs and generic previews. `tableBlock(rows, columnSettings?)` builds a `table` block as Slack sends it: each cell a `rich_text` block from words or inline elements, `null` for an empty cell. `sharedMessage(base, channel, message, author)` turns a posted message into the attachment Slack sends when it is shared into another conversation. Avatar responses require the fake session cookie, so desktop tests exercise the authenticated image path.

Mutation recovery (`docs/research/slack-catchup.md`): counts expose independent
`updated` and `history_invalid` markers. The fake advances `updated` for thread replies,
edits and reactions; a new Main message changes only `latest`.
Deletion advances `history_invalid`. History and replies
accept `cached_latest_updates`, return changed bodies with `latest_updates`,
unchanged ids in `unchanged_messages`, and an empty `deleted` list, as the
controlled self-DM deletion test returned. Versions live in a separate map, not
on Message bodies. Deleting a reply also changes its root version; deleting the
final root advances only `history_invalid`.
Paging counts unchanged messages too. These rules match the controlled self-DM test,
not a completeness guarantee for every workspace and event. Tests can override
marker/version maps to model backwards or unchanged values, and `retainedSince`
omits older messages while marking history and replies `is_limited`.

In-process tests can set `workspace.mutationMarkers = false` to model counts that
omit both markers. The uncovered outbox conformance schedule uses this alongside
zero fallback topics to model no observation of a deleted original. The separate
send-copy test keeps markers enabled: repair can observe deletion and keep the
surviving copy, but only the fallback certifies coverage for deleting a duplicate.

`holdFrames` can hold `pong` as well as message frames. Holding both models a
half-open socket while HTTP counts still succeeds; the real client timeout detects
it. The hidden-old-root `thread_not_found` scenario is injected as a refusal in a
test, not asserted as measured Slack behavior.

Large-workspace reads build a request-local index of followed roots and replies. `getView` chooses its page before expanding thread bodies; unread counts scan messages once. No result is cached across requests, so edits, read marks and follow changes are visible on the next page. Seed posts already in timestamp order append without sorting the whole conversation again.

Huddle controls also keep a `sh_room_created` message with room start, end and participant history, so normal history sync can recover an offline missed huddle.

In-process malformed getView tests set `workspace.threadViewRowOverrides` by root timestamp. These rows replace only the getView entry, preserving its original position and paging. They are synthetic fault injection, not measured Slack shapes.

`workspace.addUser(user, { profileOnly: { pendingAnswers } })` adds a Slack Connect person the edge has only a profile for: `users/info` lists them in `failed_ids` unless the call sets `include_profile_only_users`, and then in `pending_ids` for `pendingAnswers` answers before `results`, as observed live.

Search parses identity references, exclusions, repeated OR conversations, phrases, local-calendar dates, content filters and thread filters independently from Juno's parser. Bot exclusion uses `search_exclude_bots`; rewriting is accepted but never performed. `has:pin` reads the fake message's Slack `pinned_to` field, never a Juno topic pin.
